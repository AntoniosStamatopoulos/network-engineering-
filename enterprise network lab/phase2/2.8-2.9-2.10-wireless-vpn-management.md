# 2.8 Wireless Logical Design

This sub-stage defines how wireless access integrates into the logical structure
established in 2.1–2.7. Wireless is not a separate network: it is an additional
means of reaching the same segments, and a user must arrive in the same VLAN
whether they connect by cable or over the air (§8).

Access point placement, radio channels, transmit power and coverage are **RF
design** questions and belong to the physical design phase. This sub-stage covers
SSIDs, VLAN mapping, authentication method, and how wireless traffic reaches the
rest of the network.

> **Revised after implementation.** Points marked with a reference such as *(D9)*
> were amended following the build. The amendment record at the end of this
> document lists every change; the deviations themselves are set out in 3.6.

---

## 2.8.1 Requirements

From §8:

- Corporate Wi-Fi available to employees, placing each employee into the network
  of their own department
- Guest Wi-Fi completely isolated from the corporate network, providing Internet
  access only
- The authentication and VLAN assignment method is explicitly left to be decided
  at this stage

## 2.8.2 SSID Plan

| SSID | VLAN | Segment | Authentication | Access |
|------|-----:|---------|----------------|--------|
| `CORP-HR` | 10 | Z1 HR | WPA2-PSK | Per department policy |
| `CORP-FINANCE` | 20 | Z2 Finance | WPA2-PSK | Per department policy |
| `CORP-SALES` | 30 | Z3 Sales | WPA2-PSK | Per department policy |
| `CORP-IT` | 40 | Z4 IT | WPA2-PSK | Per department policy |
| `GUEST` | 60 | Z6 Guest | Open *(portal not implemented — D9)* | Internet only |

Each SSID maps to the VLAN its department already occupies in the wired design. A
wireless HR user therefore lands in VLAN 10 and is subject to exactly the same
core ACL rules as a wired HR user — no wireless-specific policy exists or is
needed.

**Verified by test.** A wireless client joining each corporate SSID in turn was
placed in that department's VLAN, with the correct gateway and DNS server obtained
by DHCP. This is the requirement of §8 and it is the one wireless requirement that
had to be demonstrated rather than argued.

## 2.8.3 Decision 1 — Static VLAN Assignment

**Selected: static VLAN assignment, one SSID per department, WPA2-PSK.**

### The alternative considered

**Dynamic VLAN assignment** places all corporate users on a single SSID and
determines their VLAN at authentication time: the access point challenges the user
via 802.1X, a RADIUS server checks a directory and returns both the authorisation
and the VLAN to place the user in. One SSID serves every department, and placement
follows identity rather than which network name the user selected.

It is the technically superior mechanism, and it was not selected.

### Why static was chosen

**Scale.** The network serves 42 users at a single site (§2). Dynamic assignment
solves a problem that appears when user populations are large and mobile enough
that per-SSID management becomes unworkable. At this size, four department SSIDs
remain manageable.

**Required infrastructure does not exist in scope.** Dynamic assignment needs two
components this design does not contain: a **RADIUS server** to perform
authentication, and a **directory or user database** mapping each user to a
department. §3 defines the server infrastructure as DNS and Web, with a File
Server as a future addition. Introducing RADIUS would mean adding a server to the
device list, an address to the addressing plan, new traffic flows to the traffic
characterization, new ACL rules, and a new single point of failure — since a
RADIUS outage would prevent all wireless authentication. That is a scope
expansion the requirements do not ask for.

**Predictability and troubleshooting.** Static mapping is deterministic: an SSID
always leads to the same VLAN, and a connectivity problem is traced by checking
which SSID the client joined. Dynamic assignment introduces the authentication
exchange as an additional failure point between the client and the network, which
is valuable at scale but adds diagnostic complexity disproportionate to a network
of this size.

### What is given up — stated explicitly

This choice carries real costs, and recording them is what makes it a decision
rather than an omission:

**A shared passphrase per department.** If one leaks, it must be changed for
everyone in that department. With per-user credentials, a single account would be
disabled instead.

**No individual accountability.** Logs can establish that a device connected to
`CORP-FINANCE`, not which employee was using it. Attribution to an individual is
not possible.

**Nothing binds a user to their own department.** A Sales employee who learns the
Finance passphrase can join `CORP-FINANCE` and be placed in VLAN 20. The access
point verifies knowledge of a passphrase, not entitlement. Segregation therefore
depends on passphrases not circulating between departments — an administrative
control rather than a technical one. Dynamic assignment would remove this weakness
entirely, because placement would follow verified identity rather than SSID
selection.

**Five SSIDs exceeds the usual guidance.** Access points broadcast beacons for
every SSID, consuming airtime; three to four is the commonly cited practical
limit. Five is above it. The cost is measurable but tolerable at this user count
and access point density, and it is accepted knowingly.

### Migration trigger

The choice should be revisited when any of the following occurs:

| Trigger | Why it changes the calculation |
|---------|-------------------------------|
| A directory service or RADIUS server is introduced for another purpose | The main obstacle — missing infrastructure — disappears |
| User count grows substantially, or departments are added | Passphrase management and SSID count stop being manageable |
| Individual accountability becomes a requirement | Static assignment cannot provide it at all |

At that point the design would move to a single corporate SSID with 802.1X and
RADIUS-assigned VLANs. The VLAN structure already in place requires no change —
only the assignment mechanism does, which is why this migration is
straightforward rather than a redesign.

**The same weakness reappears in the VPN.** The shared-secret problem described
above is not confined to wireless: the remote-access implementation authenticates
with a group key shared by everyone in a department, for the same reason and with
the same consequence (2.9.5). One infrastructure addition resolves both.

## 2.8.4 Decision 2 — Guest Traffic Path

**Selected at logical design: a dedicated uplink from each access switch to the
firewall carrying VLAN 60 only.**

**Superseded at physical design (3.4.4): Layer 2 transit through the core.** The
original decision and its reasoning are retained below, because the reasoning is
sound and the constraint that overrode it is specific. What changed is recorded
after them.

### The problem

Access points connect to access switches. The Guest gateway lives on the firewall,
not the core (DD-2, 2.1). Guest traffic must therefore reach the firewall without
being routed by the core.

### The alternative considered

**Layer 2 transit through the core.** VLAN 60 would traverse the core switch on
its way to the firewall, but the core would hold no SVI for it. The core would
forward VLAN 60 frames between trunks as a Layer 2 switch while being unable to
route them, because it has no address within that VLAN.

This is sound and uses fewer physical links. It was not selected at this stage.

### Why the dedicated uplink was chosen

Both options provide structural isolation — in neither does a route to internal
networks exist. The difference is **how much that isolation depends on
configuration remaining correct**.

With Layer 2 transit, VLAN 60 is present on the core. If an SVI were later added
for it — by mistake, or by someone unfamiliar with the design — the isolation
would break **silently**. Nothing would fail; Guest would simply gain a route into
the internal network, and the only indication would be in logs nobody was
examining.

With a dedicated uplink, VLAN 60 never reaches the core at all. An SVI cannot be
created for a VLAN the device does not carry. The failure mode is removed rather
than guarded against.

### Why the physical design reversed it

The dedicated-uplink arrangement brings one VLAN 60 cable from **each** access
switch to the firewall. Two cables mean two firewall interfaces, and two
interfaces in the same broadcast domain must be bridged into one Layer 2 domain —
a bridge group with a BVI — for the design's single Guest subnet and single
gateway to survive.

**The implemented firewall provides no bridge-group or BVI capability.** Without
it, two interfaces mean two separate Guest networks: two subnets, two gateways,
two DHCP scopes, where 2.4.3 defines one. That is a change to the addressing plan
and to the Guest model, not merely to the cabling.

Layer 2 transit preserves the single subnet and the single gateway, using the
access-to-core trunk each switch already has. The core forwards VLAN 60 frames and
never routes them. The resulting path is:

```text
                              ┌──────────────┐
                              │   FIREWALL   │
                              │              │
                              │ Guest iface  │
                     ┌────────┤ 10.0.60.1/24 │
                     │ VLAN 60│              │
                     │ access │ inside iface ├──────┐
                     │ port   └──────────────┘      │
                     │                              │
              ┌──────┴──────────────────────────────┴──┐
              │              CORE SWITCH               │
              │     carries VLAN 60 · no SVI for it    │
              └──────┬──────────────────────────┬──────┘
                     │                          │
            trunk (10,20,30,40,60,99)   trunk (10,20,30,40,60,99)
                     │                          │
              ┌──────┴───────┐           ┌──────┴───────┐
              │ ACCESS SW 1  │           │ ACCESS SW 2  │
              └──┬────┬──────┘           └──┬────┬──────┘
                 │    │                     │    │
                AP   wired                 AP   wired
                     clients                    clients
```

Each access switch now has one uplink rather than two, and the former Guest uplink
port is parked in VLAN 999.

### What this costs, stated plainly

**The failure mode the original decision removed is back.** VLAN 60 is present on
the core, so an SVI can be created for it, and if one were, Guest would gain a
route inward without anything appearing to fail. The isolation now rests on a
condition that must be maintained — *the core must not have a VLAN 60 SVI* — rather
than on a physical impossibility.

The reasoning in "Why the dedicated uplink was chosen" was therefore correct, and
it is retained above for that reason. It was overridden by a constraint rather than
refuted by an argument.

### Relationship to firewall rule 6

Firewall rule 6 (2.7.3) denies Guest traffic toward RFC 1918 address space. It was
written as defence in depth against precisely the misconfiguration the original
decision made impossible.

**Its status has changed with the decision.** It is no longer a second layer behind
an impossibility; it is the second layer behind a condition. That makes it more
important than when it was written, not less — and it is the reason the reversal is
acceptable rather than merely necessary. During Guest isolation testing it recorded
12 hits.

## 2.8.5 Access Point Connectivity

Each access point requires a trunk carrying every VLAN its SSIDs serve.

| Link | VLANs carried | Native VLAN | Purpose |
|------|---------------|------------:|---------|
| AP → Access switch | 10, 20, 30, 40, 60, 99 | **99** *(D8)* | All SSIDs served by that AP, plus the management VLAN the access point is addressed in |
| Access switch → Core | 10, 20, 30, 40, 60, 99 | 999 | Routed VLANs plus Guest in Layer 2 transit |
| Core → Wireless controller | 10, 20, 30, 40, 60, 99 | **99** *(D8)* | WLAN VLANs and controller management |
| Core → Firewall (Guest) | 60 only, untagged | — | Access port, not a trunk *(D3)* |
| All other trunks | — | 999 | Unused; mitigates VLAN hopping (2.3.4) |

The access point tags each frame with the VLAN corresponding to the SSID the
client joined. The access switch then forwards every VLAN toward the core, which
routes the corporate VLANs and passes VLAN 60 through to the firewall.

An access point is a bridge rather than a router: it applies a VLAN tag and hands
frames to the switch. All routing and policy decisions are made by the core and
the firewall exactly as they are for wired clients, which is why wireless requires
no parallel policy design.

### How the implementation reaches this behaviour *(D10)*

The design above describes autonomous access points. The implementation uses a
controller and two lightweight access points, substituted because the simulated
autonomous model exposes only one SSID (3.3.7).

Lightweight access points normally tunnel all client traffic to the controller,
which is not what the table above describes. The implemented access points operate
in **FlexConnect mode** and cannot be changed to Local mode. Each WLAN was
therefore configured with **FlexConnect Local Switching** and **FlexConnect Local
Auth**, and the access-point switch ports were converted from access ports to
802.1Q trunks.

The result is closer to this sub-stage than the controller architecture suggests:
the access point switches client traffic locally and delivers it tagged to the
switch, which is precisely what the table specifies. The controller handles
configuration and association rather than carrying traffic.

**The native VLAN exception** in the table is not optional. With VLAN 99 tagged on
their switch ports, both access points dropped to `DOWN` and lost their addresses;
the controller was unreachable with native VLAN 999 on its trunk. Both devices send
management traffic untagged. The residual risk is recorded in 2.3.7.

## 2.8.6 Guest Wireless Controls

Three controls apply to the Guest SSID and not to the corporate SSIDs.

**Client isolation.** Guest devices cannot communicate with one another, even
within VLAN 60. Without this, one visitor could scan for and attack another — a
client's laptop in reception, for example. It is not applied to corporate SSIDs,
where users may have legitimate reasons to reach each other's devices.

**Captive portal.** Presented on association, requiring acceptance of terms of
use. This serves a legal purpose — a record that the visitor accepted the terms —
and provides a basic access control point.

**Bandwidth limiting.** A per-client rate limit prevents visitor traffic from
consuming capacity that employees depend on. Guest traffic is best-effort by
classification (Phase 1, §3.2) and should not compete with corporate traffic on
the shared Internet link.

Guest DNS is provided by a public resolver rather than the internal DNS server, as
established in 2.4.7: the internal resolver sits in VLAN 50, which Guest has no
path to.

### Implementation status

| Control | Status | Note |
|---------|--------|------|
| Client isolation | **Not verified** | The controller does not expose a per-SSID client isolation setting (W6) |
| Captive portal | **Not implemented** *(D9)* | The controller presents the Web Policy setting under Layer 3 security and states that the feature is not supported |
| Bandwidth limiting | **Not verified** | No per-client rate limit is exposed (W7) |
| Public DNS resolver | Configured | The scope is stored on the firewall but never served *(D5)*; Guest clients are addressed statically with the same resolver |

**What the missing portal costs.** Guest access itself is unaffected: isolation
from internal resources is enforced by the firewall rule and by the absence of a
core SVI, not by the portal. What is lost is the portal's **primary** purpose — a
record that the visitor accepted the terms of use. That is a legal artefact rather
than a security control, and nothing else in the design produces it.

**What the missing client isolation costs.** This is the more consequential of the
two. Without it, a visitor can reach other visitors on the same SSID. The zone
model treats Z6 as untrusted precisely because its occupants are unknown to the
organisation, and two unknown devices sharing a broadcast domain with no isolation
between them is the scenario the control exists for. It should be verified on
equipment that exposes the setting before the design is considered complete.

## 2.8.7 Wireless-Specific Security Considerations

Wireless introduces exposure that the wired design does not have. Unlike a wired
network, which requires physical access to a socket inside the building, a
wireless network radiates beyond its walls — there is no physical boundary.

| Concern | Treatment in this design |
|---------|--------------------------|
| **Eavesdropping** | WPA2 encryption on all corporate SSIDs. The Guest SSID is open by design, so guest traffic is unencrypted at the radio layer — acceptable because Guest carries no corporate data and reaches only the Internet, but a limitation to be aware of |
| **Rogue access points** | Not detectable automatically in the current design. Unused switch ports are assigned to VLAN 999 (2.3.4), which prevents an unauthorised AP plugged into a spare socket from reaching anything. Detection of rogue APs broadcasting from outside the network is not addressed |
| **Evil twin** | Not addressed. A duplicate SSID broadcast by an attacker cannot be prevented by this design; users would need to be aware of it. Mitigation would require WPA2-Enterprise with server certificate validation — which returns to the 802.1X migration trigger in 2.8.3 |
| **Passphrase disclosure** | The primary residual risk of static assignment, discussed in 2.8.3. Managed administratively through periodic passphrase rotation |
| **Guest-to-guest attack** | **Not mitigated in the implementation.** Client isolation is specified in 2.8.6 and not exposed by the controller |

Two of these — evil twin resistance and individual accountability — are addressed
by the same change: moving to WPA2-Enterprise. This strengthens the case for the
migration trigger, and is recorded here so the security benefit is visible
alongside the operational one.

# 2.9 VPN Logical Design

This sub-stage defines how remote access is provided to the departments permitted
it by §9 — Finance and IT — and how the difference in their access scope is
enforced.

Several decisions were established in earlier sub-stages: remote Finance and
remote IT are modelled as separate zones Z8 and Z9 (2.6.2); their access scopes
are defined in the zone interaction matrix (2.6.3) and implemented as firewall
rules 7 and 8 (2.7.3); and all VPN activity is logged in full (2.7.6).

What remains is the mechanism: addressing, tunnelling mode, authentication, and
protocol.

---

## 2.9.1 Requirements

From §9:

- Remote access available only to Finance and IT
- Remote Finance users reach Finance resources and required server resources, and
  must not receive unrestricted access to other departments
- Remote IT users have broader access for administration and troubleshooting,
  including IT, servers, other departments where required, and network
  infrastructure devices
- Remote users must not automatically receive unrestricted access to the entire
  corporate network

The last point is the governing principle: remote access is narrower than on-site
access by design, not equal to it.

---

## 2.9.2 Termination Point

**Design decision DD-1: VPN terminates on the firewall.**

**Implementation: the tunnel terminates on the edge router** *(D11)*. The intent of
DD-1 is preserved by other means, which are set out below. This is the most
significant relocation in the implementation and the one with the clearest security
consequences, so it is recorded in full rather than summarised.

### Why the firewall was chosen

The firewall is already the single policy enforcement point for the network.
Terminating VPN there means remote traffic is subject to the same controls as all
other traffic **by construction**, rather than by a separate mechanism that must be
kept consistent.

The failure mode this avoids is significant. If VPN terminated on the edge router
or on a dedicated concentrator placed inside the perimeter, remote users would
enter the network **behind** the enforcement point and bypass the policy that
applies to everyone else — and the remote population is precisely the one arriving
from an untrusted network.

### Why it could not be implemented there

The implemented firewall accepts `tunnel-group <name> type remote-access` but
provides **no mechanism for assigning addresses to remote clients**. There is no
`ip local pool` at global configuration level; tunnel-group general attributes
offer only `default-group-policy` and no `address-pool`; group-policy attributes
offer only `vpn-tunnel-protocol` and `webvpn`; and the WebVPN subcommand set
contains only `url-list`, which presents a page of links and establishes no tunnel.

Without address assignment there is no remote-access VPN. 2.9.3 depends entirely
on address pools, so this is not a cosmetic shortfall.

### Why the obvious alternative was rejected

Terminating on the edge router **with direct access to the internal network** was
considered and rejected. It is the straightforward way to make a VPN work on this
equipment, and it is exactly the failure mode described above: remote users would
enter behind the enforcement point.

That option was not taken at any point, including as a temporary measure.

### How DD-1's intent is preserved

The tunnel terminates on the edge router. **Policy enforcement does not move.**

The mechanism is routing rather than rules. The edge router holds one route toward
internal addresses — `10.0.0.0/8 → 203.0.113.5`, the firewall's outside interface
(2.5.4). It has no route to any internal VLAN that does not pass through the
firewall. Every packet from a VPN client toward an internal destination is
therefore sent to the firewall and evaluated against rules 7 and 8, exactly as
DD-1 intended.

```text
Remote user → Internet → ISP
  → EDGE ROUTER      tunnel terminates; address assigned from pool
  → FIREWALL         rule 7 or rule 8 evaluated        ← enforcement, unmoved
  → CORE             routed to destination VLAN
```

**This is a structural control, not a rule.** The restriction holds because a route
does not exist, in the same way that Guest isolation holds because an SVI does not
exist. It is recorded as such in 2.6.6 and 2.5.7. It is arguably stronger than the
arrangement it replaced, because it cannot be mis-ordered or deleted the way a rule
can — though it can be undone by adding a route, which is the condition that has to
be maintained.

**Verified by test.** A remote Finance user reached the DNS server and was denied
the management VLAN; the same workstation, connecting with IT credentials, received
an address from the other pool and reached the management VLAN. Requirement F9 —
identified in 3.1.3 as the requirement whose failure carries the greatest security
consequence — is satisfied.

### What does change

**Encryption now occurs on a device outside the firewall.** The tunnel endpoint is
not itself protected by the firewall, which in a real deployment would warrant
review: the device performing decryption is the one most exposed to the Internet.

**The edge router now carries a third role.** It is the Internet path, the network
time reference, and the VPN endpoint. Failure testing confirmed the consequence: a
single failure removes all three (SPOF-1), and the SPOF severity ranking was revised
upward for this device as a result.

## 2.9.3 Address Pools

**Two separate pools, one per zone.**

| Zone | Pool | Assigned range | Serves |
|------|------|----------------|--------|
| Z8 VPN-FINANCE | `10.0.201.0/24` | `.100 – .199` | Remote Finance users (UC6) |
| Z9 VPN-IT | `10.0.202.0/24` | `.100 – .199` | Remote IT users (UC7) |

### Why separate pools rather than one

This is not an organisational preference; it is what makes the §9 scope difference
implementable.

Firewall rules 7 and 8 (2.7.3) grant different access to the two groups. For those
rules to function, the firewall must be able to distinguish a remote Finance user
from a remote IT user. With a shared pool it cannot: a packet from an address in
the common range identifies neither group, and no rule can be written that applies
to one and not the other.

With separate pools, **the address is the identity**:

```text
Traffic from 10.0.201.x  →  remote Finance  →  firewall rule 7 applies
Traffic from 10.0.202.x  →  remote IT       →  firewall rule 8 applies
```

The differentiated scope required by §9 depends entirely on this separation.

**This survived the relocation of the termination point.** The pools moved from the
firewall to the edge router, but the firewall still sees the addresses and still
applies the two rules. The mechanism that makes §9 implementable is unaffected by
where the tunnel ends — which is worth noting, because it is the reason the
relocation was acceptable at all.

### Why these ranges

The addressing plan (2.4) allocates the third octet by VLAN ID and reserves ranges
for growth (2.3.3): 51–59 for additional server VLANs, 70–90 for additional
departments, and 100–199 for additional sites. The block from 200 upward is
unallocated, so VPN pools occupy it without colliding with any current or reserved
use. Ranges 203–253 remain available for further pools.

`10.0.254.0/24` is not used, as it is reserved for internal point-to-point links
(2.4.4).

### Consequence for the firewall routing table

Because the pools fall inside `10.0.0.0/16`, which the firewall routes to the core,
each pool required a more specific route pointing back at the edge router. Without
them, replies to remote clients would be sent inward instead of outward (2.5.4).
This is a direct consequence of choosing pool addresses inside the summarized
internal block — a choice that remains correct for the reasons above, but which has
an implication the original sub-stage did not trace.

### Sizing

A /24 provides 254 addresses for a concurrent user population that will be a
subset of 8 Finance and 6 IT staff. This is deliberate over-provisioning, for the
same reason given in 2.4.3: uniform /24 boundaries keep the third octet meaningful
and the scheme readable, and address space in a private range is not scarce.

## 2.9.4 Tunnelling Mode

**Selected: full tunnel.** All traffic from a connected client passes through the
tunnel, including traffic destined for the Internet.

### The alternative considered

**Split tunnel** would send only corporate-destined traffic through the tunnel,
with general Internet traffic going directly from the client. It reduces load on
the corporate link and improves the user's browsing performance.

### Why full tunnel was chosen

**Consistency with the enforcement model.** The entire design rests on a single
policy enforcement point: internal traffic is routed by the core under ACL
control, and everything leaving the network passes the firewall. Split tunnelling
would create a category of traffic from an authenticated corporate session that
passes through no enforcement point at all. That is an exception to the principle
applied everywhere else in the design, and exceptions to a security model are
where the model fails.

**The dual-attachment risk.** Under split tunnelling the client is simultaneously
attached to two networks — the Internet directly, and the corporate network
through the tunnel. A machine compromised from the Internet side already holds an
open path inward. This risk applies to any remote user, but it is more serious
here than usual: remote IT users hold administrative access to the infrastructure
(rule 8), which makes their endpoints the highest-value targets in the design.

**Scale makes the cost acceptable.** The objection to full tunnelling is link
load. The concurrent remote population is a subset of fourteen people. Their
combined Internet traffic is well within what the site's connection carries for
forty-two on-site users, so the argument that normally favours split tunnelling
does not apply at this size.

### What this means operationally

Remote users' Internet traffic traverses the corporate link in both directions and
is subject to firewall rule 4 and to the same translation as internal traffic
(2.5.6). Their browsing is therefore logged and filtered identically to on-site
users, which is the intended consequence rather than a side effect.

The trade-off is honest: users on poor connections experience slower browsing
while connected, because traffic takes an indirect path. This is accepted.

## 2.9.5 Authentication

### Design requirement

**The design requires multi-factor authentication for remote access.**

The reasoning is specific to VPN rather than general. The VPN is the only service
in this design that permits a connection to be initiated from the Internet into
the internal network — firewall rule 9 denies everything else inbound. It is
therefore the single doorway inward, and an attacker who passes it is inside the
network having bypassed every perimeter control. A stolen password alone should
not be sufficient to open that door from anywhere in the world.

Multi-factor means two factors from **different** categories: something known (a
password), something held (a device or token), or something inherent (biometric).
Two passwords are not multi-factor.

The architecture that would deliver it:

```text
Client → Firewall → RADIUS server → password verification
                          ↓
                    second factor check (TOTP or push)
                          ↓
                    accept or reject
```

### What was implemented *(F10 not met)*

**A shared group key combined with per-user credentials.**

| Factor | Type | Mechanism |
|--------|------|-----------|
| Group key, one per department | Shared secret | Required to establish the tunnel; identical for every member of that group |
| User credentials | Something known | Verified per user against the local database on the edge router |

The original version of this sub-stage recorded the current implementation as
**certificate-based authentication combined with user credentials**. That is not
what was built, and the difference matters enough to correct rather than gloss.

### Why it is weaker than the design intended

A per-user certificate is *something held*: it is issued to one person and
installed on one machine, so an attacker holding a stolen password must also
compromise that machine.

**A group key is not something held — it is something shared.** Every remote
Finance user presents the same key. It fails in exactly the way a wireless
passphrase fails (2.8.3): if it leaks, it must be changed for everyone in that
department, and possession of it proves membership of a group rather than identity
of a person. The two factors are therefore *a shared secret* and *a password*,
which is closer to one and a half factors than to two.

What remains true is that a stolen password alone is not sufficient — the attacker
also needs the group key. That is a real improvement on credentials alone, and it
is the honest limit of the claim.

### Why neither certificates nor MFA were implemented

**No PKI exists in the environment.** Certificate-based authentication requires a
certificate authority to issue and revoke per-user certificates. The implementation
environment provides none, so the design's stated mechanism could not be built even
in its weaker form.

**MFA requires infrastructure that is out of scope.** It needs a RADIUS server, an
MFA mechanism (TOTP, push notification, or hardware tokens), and a user database
holding each user's second factor. §3 defines the server infrastructure as DNS and
Web, with a File Server as a future addition. Introducing them would mean adding a
server to the device list, an address to the addressing plan, new traffic flows,
new firewall rules, and a new single point of failure — a RADIUS outage would
prevent all remote access.

**The environment provides no MFA mechanism at all** — no TOTP, no push
notification, no token support — so the requirement could not be demonstrated even
if the infrastructure were added.

### Migration trigger

MFA is introduced when authentication infrastructure — a RADIUS server and a
directory or user database — is added to the design. Certificate authentication
requires a certificate authority, which the same addition would normally bring.

This is **the same trigger** as the move from static wireless VLAN assignment to
802.1X (2.8.3), and that is not a coincidence. Both limitations stem from the same
missing component, and both currently rest on a shared secret for the same reason.
A single infrastructure addition resolves three separate constraints, which
strengthens the case for the trigger being a genuine planned step rather than a way
of deferring an inconvenient requirement.

**Selected: IPsec.**

| Protocol | Assessment |
|----------|------------|
| **IPsec** | **Selected** — standardised, widely supported, suitable for remote access with a client, and supported in the implementation environment |
| SSL/TLS VPN | Traverses restrictive networks more easily; would be preferable if clients frequently connected from networks blocking IPsec |

## 2.9.7 Access Scope Summary

The scope difference required by §9, expressed as it is enforced:

| | Z8 VPN-FINANCE | Z9 VPN-IT |
|---|---|---|
| **Pool** | 10.0.201.0/24 | 10.0.202.0/24 |
| **Reaches** | VLAN 20; DNS and Web servers | VLANs 10–50 and 99 |
| **Management plane** | No | Yes |
| **Firewall rule** | 7 | 8 |
| **Tunnel terminates on** | Edge router *(D11)* | Edge router *(D11)* |

| **Rationale** | Finance work requires Finance resources and shared services, nothing further | Administration and troubleshooting require infrastructure access |

Remote Finance access is deliberately narrower than the same users hold on site.
An on-site Finance user reaches the servers and the Internet; a remote Finance

trust context is not, and the scope follows the context rather than the person.

The last two rows were added after implementation to make the separation explicit:
the tunnel and the policy now live on different devices, and the table should say
so rather than let a reader assume they are the same place.

### Accepted risk

Remote IT access (Z9) is the broadest grant in the design, and it originates from
outside the network. A compromised remote IT session would yield access to the
internal VLANs and the management plane. This is inherent in the requirement — §9
explicitly grants IT broad remote access for administration — but it is recorded
as a known concentration of risk.

Two mitigations available within the current scope: full logging of all Z9
sessions (specified in 2.7.6), and the option of restricting management access to
specific administrative accounts rather than the whole VPN-IT pool. MFA would
materially reduce this risk, which is a further reason it is recorded as a design
requirement rather than an optional enhancement.

**The first mitigation does not exist in the implementation.** No device can record
a rule match *(D16)*, so VPN sessions are not logged anywhere. The broadest grant in
the design is also the least observed — a combination worth stating plainly, because
the risk was accepted on the basis of a mitigation that is not present.

# 2.10 Management and Monitoring Design

This sub-stage defines how infrastructure is administered and observed. It covers
the management access path, the protocols used, what is monitored and how, and the
logging configuration.

Management and monitoring are treated as distinct concerns throughout. Management
**changes** the network and is therefore restricted to as few people and paths as
possible; monitoring **observes** it and needs broad reach to be useful. Their
security requirements point in opposite directions.

---

## 2.10.1 Requirements

From §10:

- Management of network infrastructure restricted to the IT department
- IT must be able to manage routers, switches, the firewall, and servers
- HR, Finance, Sales and Guest must not have direct access to management
  interfaces
- Initial monitoring: ping / basic availability checks, Syslog, SNMP
- A future monitoring dashboard may display device availability, interface status,
  traffic, CPU utilisation, packet loss, and server availability

---

## 2.10.2 Management Access Path

**Selected: in-band management using a dedicated management VLAN (VLAN 99).**

### The two approaches

**In-band management** carries management traffic over the same physical
infrastructure as user traffic, isolated in its own VLAN. Access is restricted by
access control lists on the core. It requires no additional hardware.

**Out-of-band management** uses a physically separate network — its own switch,
its own cabling, and a dedicated management port on each device. Management
traffic shares no path with user traffic.

### Why in-band was chosen

**The network is a single site.** The principal argument for out-of-band
management is that when the production network fails, remote management fails with
it, and recovery then requires physical presence. That cost depends on distance.
With one site (§1), an administrator is either in the building or a short journey
away, and console access provides a working fallback. The same reasoning would not
hold for equipment in another city, where an on-site visit means hours of
additional outage.

**The device count does not amortise the cost.** Out-of-band management is not
only the price of a switch. It is cabling to every device, ports consumed on both
ends, a second network to document and maintain, and an additional component that
can itself fail. Across dozens of devices this overhead is proportionate. Across
the five infrastructure devices specified in §11, it is not.

**Complexity has its own cost.** A second network means a second thing to
configure correctly, keep documented, and hand over to whoever administers the
network next. In an organisation of this size, where network administration is
likely one responsibility among several rather than a dedicated role, simplicity
has real operational value. A design that is understood is maintained correctly;
one that is not tends to drift.

**The requirements do not call for it.** §10 requires that management be
restricted to IT and that other networks have no direct access to management
interfaces. A dedicated VLAN with access control lists satisfies both. Nothing in
the requirements specifies physical separation, and adding it would be a
scope decision taken on the designer's own initiative rather than a response to a
stated need.

### What is given up

Recording the cost is what makes this a decision rather than a default:

**A core failure removes remote management.** VLAN 99 is routed by the core, so a
core failure takes down routing and the ability to diagnose it remotely at the
same time — one fault producing two problems. This compounds SPOF-3, already the
most severe single point of failure in the design.

*Failure testing confirmed this and found it to be worse than described.* A core
failure removes inter-VLAN routing, DHCP, server access, name resolution, Internet
access, the Guest network, infrastructure management **and the entire wireless
estate**, since the controller connects to the core. The only communication that
survives is between hosts in the same VLAN on the same access switch. Management is
one of eight capabilities lost rather than the second of two.

**Management isolation is rule-based, not structural.** A path exists from every
user VLAN to VLAN 99 and is closed by core ACL rules 1 and 2 (2.7.2). Should those
rules be mis-ordered, deleted, or overridden by a broader rule placed above them,
the management plane becomes reachable. This differs from the Guest network, where
isolation is enforced by the absence of a route and cannot fail this way.

*This risk materialised during implementation.* The rules were correct and the
direction they were applied in was not: an outbound list on VLAN 99 does not filter
traffic addressed to the core's own interface in that VLAN, so the management
address remained reachable from the user zones until an inbound deny was added
(2.7.2a). It was found by testing, not by review — which is the argument for
testing isolation rather than inspecting the rules that implement it.

Both costs are accepted knowingly rather than overlooked. The mitigations within
current scope are the ones already specified: rules 1 and 2 are logged, so
attempts from other zones are recorded, and console access provides recovery when
the network path is unavailable.

*The first mitigation does not exist in the implementation.* Per-rule logging is
unavailable on every device in the build *(D16)*, so attempts against the management
plane are not recorded. Console access remains.

### Console access

Console access is retained on every device as the final fallback. It works when
the network does not, because it depends on neither routing nor switching.

It requires physical presence, which is both its limitation and a security
property: console access cannot be exercised remotely by an attacker. Physical
access to network equipment is restricted to IT, which makes the console path
subject to the same restriction as every other management path.

Given that management is in-band, console access is not a formality. It is the
documented recovery path for exactly the scenario in which in-band management
fails, and it should be verified as working rather than assumed.

*It was used in practice.* An access switch became unreachable after a credential
change and was recovered through the console. The fallback is therefore not
theoretical in this build; it is the path by which a device was actually brought
back.

### Migration trigger

Out-of-band management should be introduced when any of the following occurs:

| Trigger | Why it changes the calculation |
|---------|-------------------------------|
| **A branch office is added (§5)** | Remote equipment makes on-site recovery expensive, which is the case out-of-band management exists to address |
| **Device count grows substantially** | The fixed overhead of a second network is amortised across more devices |
| **High availability is implemented (§12)** | A design that invests in eliminating single points of failure should not leave management dependent on the core |

The first and third are already planned extensions, so this is a foreseeable step
rather than a hypothetical one. The management VLAN and its addressing require no
change when it happens: only the path changes, not the structure.

## 2.10.3 Management Access

| Target | Protocol | Source | Notes |
|--------|----------|--------|-------|
| Core and access switches | SSH (TCP 22) | IT management workstations | Telnet disabled |
| Edge router | SSH (TCP 22) | IT management workstations, via the firewall | Reached at `203.0.113.6`, not in VLAN 99 *(D18)* |
| Firewall | SSH (TCP 22) | IT management workstations | HTTP disabled |
| Wireless controller | HTTPS (TCP 443) | IT management workstations | Administered through a web interface; core ACL permits IT to `10.0.99.40` |
| Access points | Through the controller | — | Not administered directly; recorded here because W11 requires them to appear among managed devices |
| Servers | SSH (TCP 22) | IT management workstations | **Not available** — the implemented servers provide no SSH service *(D17)* |
| All devices | Console | Physical access | Fallback only |

**Telnet and HTTP are disabled on every device.** Both transmit credentials in
clear text, so anyone able to observe traffic on the path obtains full
administrative access. SSH and HTTPS provide equivalent function with encryption.
This is not a preference between comparable options: unencrypted management
protocols are a defect, and their availability on a device is itself a risk even
when they are not used.

**This principle decided a later question.** When SNMP proved to be available only
in its clear-text versions and with no collector to read it, the same reasoning
applied: an agent that serves no purpose while exposing a clear-text community
string is a defect, not a partial implementation. See 2.10.5.

Remote IT users reach management through the VPN (Z9, firewall rule 8) rather than
through the management network directly, since the management network has no
external connection by design.

**The edge router is the exception to the VLAN 99 model**, and deliberately so. It
sits outside the firewall; giving it an interface in the management VLAN would
create a path from an Internet-facing device into the management plane, bypassing
the enforcement point and violating requirement E2. It is reached over SSH at its
firewall-facing address, which means its management traffic is subject to the
firewall rather than to the core ACL. The reasoning is recorded in 2.4.6.

## 2.10.4 Monitoring Architecture

The monitoring and Syslog collector is DS3 at `10.0.50.30` (2.4.6), in the server
segment.

### Two collection models

Both are specified, because they answer different questions.

**Polling** — the collector queries devices at intervals for current values.
Produces steady, predictable traffic. Suited to metrics that change continuously,
and confirms a device is alive between events. Its limitation is detection
latency: a fault occurring just after a poll is not seen until the next one.

**Event-driven** — devices send a message when something happens. Produces bursty
traffic: silence under normal conditions, several messages at once when something
breaks. Suited to conditions that must be known immediately. Its limitation is
that a device which fails completely sends nothing at all.

Neither is sufficient alone. Polling provides the baseline that makes a silent
device distinguishable from a healthy one; events provide timely notification.

### What is monitored

| Category | Metrics | Mechanism | Implemented |
|----------|---------|-----------|-------------|
| **Availability** | Device reachability | ICMP polling (§10) | ✅ |
| **Performance** | CPU, memory, interface utilisation | SNMP polling | ❌ *(D15)* |
| **Faults** | Interface state changes, hardware conditions | SNMP traps + Syslog | Partially — Syslog only |
| **Security** | Authentication failures, configuration changes, VPN sessions, denied traffic | Syslog | Partially — see below |

Security monitoring is listed explicitly because it is the category most often
omitted from designs that otherwise monitor thoroughly. The firewall and ACL deny
rules specified in 2.7.6 feed this category directly.

### What the implementation actually collects

The honest position is narrower than the table above, and the gap is concentrated
in the two categories that matter most.

**Of the two collection models, only one exists.** SNMP is not implemented on any
device *(D15)*, so there is no polling of performance metrics and no event-driven
notification by trap. What remains is ICMP reachability and device Syslog.

**Of the four categories, availability is complete, performance is absent, and the
other two are partial.** Faults are reported by Syslog from the switches and
routers — an interface changing state does produce a message — but not from the
firewall, which sends nothing *(D16)*. Security monitoring is the thinnest: logins
and configuration changes are recorded, while denied traffic, VPN sessions and
policy matches are not, because no device can record a rule match.

The architecture in this sub-stage is correct and the reasoning for using both
models stands. What is missing is one of the two mechanisms, and its absence
removes rather more than half of what the design intended to see.

## 2.10.5 SNMP Configuration

**Version: SNMPv3.**

| Version | Assessment |
|---------|------------|
| v1, v2c | **Rejected** — the community string is transmitted in clear text and is effectively an unencrypted password. Anyone observing the traffic can then query the device themselves, and where write access is enabled, reconfigure it |
| **v3** | **Selected** — provides authentication and encryption |

| Function | Port | Direction |
|----------|-----:|-----------|
| Polling (GET) | UDP 161 | Collector → device |
| Traps | UDP 162 | Device → collector |

SNMP write access is not enabled. Configuration changes are made through SSH
sessions, which are authenticated per user and logged; SNMP is used for reading
metrics only. Enabling write access would create a second configuration path with
weaker accountability than the primary one.

### Implementation: SNMP is not enabled anywhere *(D15)*

Three findings, each independently disqualifying:

1. The devices accept only `snmp-server community`. There is no `snmp-server group`
   or `snmp-server user`, so **v3 cannot be configured** — only the versions this
   sub-stage rejects.
2. There is no `snmp-server host` and no `enable traps`, so **no device can send a
   notification**.
3. The implemented monitoring server provides no SNMP service, so **there is
   nothing to receive** either polls or traps.

### Why nothing was configured rather than something

The available option was a v2c agent with a clear-text community string, reachable
by anyone observing the network, serving a collector that does not exist.

**That is worse than not configuring it.** 2.10.3 states the principle directly:
unencrypted management protocols are a defect, and the availability of a service on
a device is itself a risk even when it is not used. The same reasoning disabled
Telnet and HTTP. Enabling an agent so that the configuration *looks* complete,
while leaving it unreadable by any collector and exposed to any observer, trades a
documented gap for an undocumented attack surface.

This is recorded as a decision rather than a limitation. The limitation is that v3
is unavailable; the decision is what to do about it.

### Consequence

Performance monitoring does not exist, and no device reports an event as it occurs.
Monitoring rests on Syslog and ICMP reachability alone. Sub-stage 3.3.8 identified
the monitoring server as the least certain element of the design, and 3.3.10
recorded that if its services proved unavailable the monitoring design would be
specified but not demonstrated. That is what happened.

## 2.10.6 Syslog Configuration

**Collector:** DS3 at `10.0.50.30`, UDP port 514.

**Severity level: 6 (informational)** — meaning levels 0 through 6 are forwarded,
and level 7 is not.

| Level | Name | Included | Typical content |
|------:|------|:--------:|-----------------|
| 0 | Emergency | ✓ | System unusable |
| 1 | Alert | ✓ | Immediate action required |
| 2 | Critical | ✓ | Critical hardware or software condition |
| 3 | Error | ✓ | Interface down, process failure |
| 4 | Warning | ✓ | Threshold exceeded, degraded condition |
| 5 | Notice | ✓ | Logins, configuration changes |
| 6 | Informational | ✓ | Interface up, routine state changes |
| 7 | Debug | ✗ | Per-packet detail |

### Why level 6

**Level 3 or lower would lose context.** An interface failure appears at level 3,
but the warning that preceded it — a rising error rate, a temperature threshold —
appears at level 4. Capturing the failure without what led to it makes diagnosis
harder, not easier.

**Level 7 would produce unusable volume.** Debug output can reach thousands of
messages per minute per device. The consequences are compounding: collector
storage fills, significant messages are buried among routine detail, and logging
itself loads the device.

Level 6 captures what the criterion in 2.7.6 asks for — what would be needed after
an incident. Logins and configuration changes (level 5), warnings (level 4), and
failures (level 3 and below) together reconstruct a sequence of events. Per-packet
debug detail does not contribute to that reconstruction.

**Level 7 is used temporarily.** When diagnosing a specific problem, debug logging
is enabled on the relevant device and returned to level 6 afterwards. It is a
diagnostic tool rather than a standing configuration.

### Implementation

| Device | Status |
|--------|--------|
| Core switch, access switches, edge router | Operating to `10.0.50.30` at severity 6 |
| Firewall | **Nothing.** The device does not recognise `logging` in any form *(D16)* |

**Timestamps require explicit configuration.** Messages arrived at the collector
with an empty Time column until `service timestamps log datetime msec` was
configured on the sending devices. Diagnosed by capturing a message in simulation
mode and reading the inbound PDU, which showed the message carrying no timestamp
field at all.

This is worth recording because of what it implies. A Syslog collector displays the
time the *sender* claims, not the time of receipt. Without timestamps configured,
the messages still arrive and still contain their text — the collection appears to
be working — while the one property that makes them useful for reconstructing a
sequence is silently absent. It is the kind of defect that is invisible until the
moment someone needs the logs.

**What the firewall's absence costs** is set out in 2.7.6: device events are
collected and policy events are not, and the firewall generates most of the latter.

## 2.10.7 Time Synchronisation

Established in 2.6.5: the edge router obtains time from an approved external NTP
source, and all internal devices synchronise from the edge router.

Its significance for this sub-stage is specific. **Log correlation depends on
agreed time.** Incident analysis is the reconstruction of a sequence of events; if
one device reports at 13:45:22 and another at 13:47:10 with clocks that disagree by
an unknown amount, neither the order nor the causal relationship can be
established.

The property that matters is **consistency rather than absolute accuracy**. All
devices sharing a single source share the same offset, so relative intervals remain
correct even if that source drifts. Devices synchronised independently to different
sources may each be individually accurate and still disagree with one another —
which is the case that breaks analysis.

This is the reason the centralised design was chosen, beyond the reduction in
outbound flows.

### Implementation *(D19)*

**There is no external time source in the environment.** The edge router's clock is
set manually and it operates as a **stratum 3 local reference**; every other device
synchronises from it and reports stratum 4.

The property this sub-stage depends on holds: all devices agree with one another,
so events can be ordered. Absolute time is correct only until the simulation is
reopened, which this sub-stage already identifies as the lesser requirement.

**Failure testing exposed the cost of the centralisation.** Losing the edge router
moved the core to `unsynchronized, stratum 16` and left every device free-running.
The logs generated during that outage cannot be reliably ordered — which is
precisely when ordering matters most. The argument for an external source is
therefore stronger than accuracy alone: it decouples time distribution from the
Internet path, so that losing one does not remove the other. This is recorded in
2.6.5 and belongs in the Phase 2 work.

## 2.10.8 Access Restriction

Management access is restricted to IT (§10). With in-band management, this is
enforced by access control rules on the core rather than by topology:

| Zone | Reaches VLAN 99 | Mechanism |
|------|:---------------:|-----------|
| Z1 HR | ✗ | Core ACL rule 2 (deny), plus the inbound deny in 2.7.2a |
| Z2 Finance | ✗ | As above |
| Z3 Sales | ✗ | As above |
| Z4 IT | ✓ | Core ACL rule 1 (permit, SSH and SNMP) |
| Z6 Guest | ✗ | No route — Guest has no SVI on the core |
| Z9 VPN-IT | ✓ | Firewall rule 8 |

Guest is denied structurally, as it is for every internal destination: the core
holds no SVI for VLAN 60, so no route exists regardless of any rule.

The three corporate user zones are denied by **rule** rather than by topology,
because VLAN 99 is routed by the core and a path therefore exists. Core ACL rules
1 and 2 close it, and their order matters: the permit for IT must precede the deny
for everyone else, or IT traffic would match the deny first and management access
would fail entirely (2.7.2).

**A second rule proved to be necessary.** Rule 2 applied outbound on VLAN 99 does
not filter traffic addressed to the core's own interface in that VLAN, because such
traffic terminates on the interface and is never forwarded out of it. The core's
management address remained reachable from HR until an inbound deny was added to
each user VLAN (2.7.2a). The table above now reflects both.

Both rules are logged. Access to the management plane is the most privileged
activity in the network, and an attempt originating from HR, Finance or Sales is
either a misconfiguration or something worse — either way, worth knowing about.

*In the implementation they are not*, because no device can record a rule match
*(D16)*. The restriction is enforced and verified by test; it is not observed.

## 2.10.9 Future Monitoring Expansion

§10 anticipates a monitoring dashboard displaying device availability, interface
status, network traffic, CPU utilisation, packet loss, and server availability.

This is outside current scope. The original version of this sub-stage recorded that
the infrastructure specified here supports it without change, because every metric
listed is already collected: availability by ICMP polling, interface status and CPU
by SNMP polling, state changes by SNMP traps and Syslog. A dashboard would present
data DS3 already holds rather than requiring new collection.

**That claim holds for the design and not for the implementation.** Of the six
metrics §10 names, the implementation collects device availability by ICMP and
interface status by Syslog. Network traffic, CPU utilisation, packet loss and
server availability all depend on SNMP polling, which does not exist *(D15)*. A
dashboard built on what is collected today would show two of six.

The design point is unchanged and worth keeping: **no additional instrumentation
would be needed — only a presentation layer — once SNMP is available.** That is a
consequence of collecting by category (2.10.4) rather than collecting whatever
happened to be convenient. The correction is that SNMP availability is a
precondition rather than something already in place, and the original wording did
not distinguish between the two.
