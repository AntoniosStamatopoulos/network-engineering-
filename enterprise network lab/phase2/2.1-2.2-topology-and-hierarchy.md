# 2.1 Logical Topology & 2.2 Hierarchical Structure

> **Revised after implementation.** The topology was built, tested and amended.
> Three of the decisions recorded here were superseded during physical design and
> implementation: VPN termination moved from the firewall to the edge router, the
> Guest segment reaches the firewall across the core at Layer 2 rather than by a
> direct attachment, and the firewall's failure impact was corrected by failure
> testing. The original reasoning is retained in place, followed by what
> superseded it and why. All changes are listed in the Amendment Record at the end
> of this document and cross-referenced to `3.6-implementation-deviations.md`.

This document defines the **shape** of the network: which logical segments exist,
how they connect, and how they map onto a hierarchical model. No hardware models
are selected here — that is Phase 3.

---

# 2.1 Logical Topology

## 2.1.1 Logical Segments

Segments are derived directly from the Phase 1 analysis: user communities become
user segments, data stores become the server segment, and specific requirements
create the management, edge and guest segments.

| ID | Segment | Derived from | Role |
|----|---------|--------------|------|
| S1 | HR | UC1 | HR staff endpoints (8 users) |
| S2 | Finance | UC2 | Finance staff endpoints (8 users) |
| S3 | Sales | UC3 | Sales staff endpoints (20 users) |
| S4 | IT | UC4 | IT staff endpoints (6 users) |
| S5 | Servers | DS1, DS2, DS3 | DNS, Web, Monitoring/Syslog |
| S6 | Guest | UC5 | Visitors — untrusted, Internet only |
| S7 | Management | §10 | Device management interfaces |
| S8 | WAN Edge | §7 | Edge router ↔ ISP boundary |
| S9 | External | DS4 | The Internet |

**S4 and S7 are deliberately separate.** S4 contains IT *users* — people with
workstations. S7 contains the *management interfaces of infrastructure devices*.
These are different things at different trust levels. Neither contains the other;
they are related only by a permitted access relationship (§10), which is defined
in sub-stage 2.6, not by topology.

The Guest VLAN crosses the core as **Layer 2 transit**. The core switches the
frames but has no interface in VLAN 60 and therefore cannot route them. The

**How to read it.** The diagram shows **connectivity only** — which segments are
physically/logically attached to what. It deliberately does **not** show who is
permitted to talk to whom; access relationships are defined in 2.6 (Security
Zones). Mixing the two on one diagram is what makes topology diagrams misleading.

## 2.1.3 Topology Principles

**Single policy enforcement point.** All Internet-bound traffic and all VPN
traffic passes through the firewall. One control point means one place to express
and audit policy (§7). *(General security principle: policy enforcement point.)*

This principle survived the implementation unchanged, but it had to be defended
rather than assumed. When VPN termination moved to the edge router, the obvious
failure mode was that decrypted remote traffic would enter the network *behind*
the firewall. It does not: the edge router has no route into the internal network
except through the firewall, so decrypted VPN traffic is forced across the
enforcement point like any other inbound traffic. See 2.5 and D11.

**Guest is an untrusted zone, not an internal subnet.** S6 terminates on a
dedicated firewall interface at security level 0 and is **never routed by the
core**. The core carries VLAN 60 as Layer 2 transit only and holds no SVI for it,
so the core has no address in the Guest subnet and no way to forward a Guest
packet toward an internal segment.

This is **structural isolation**: there is no path to internal resources that must
be blocked, because no path exists. It is stronger than rule-based isolation,
where a misconfigured ACL would open a route. It also reflects the correct trust
model — a visitor is not an internal user who merely has restrictions; a visitor
is untrusted. *(Requirement §4: Guest must remain isolated from all internal
corporate resources.)*

> **What changed, and why the principle did not.** The original text read
> "S6 connects to a dedicated firewall interface and never traverses the core."
> The second half of that sentence is false in the built network — the frames do
> traverse the core. The *property that mattered* is not that the frames avoid the
> core but that the core never routes them, and that property is enforced by the
> absence of an SVI. The amended wording states the property instead of the path.
> Testing produced unplanned numeric evidence for it: a Guest host reaching the
> Internet shows TTL 125 while a corporate host reaching the same destination
> shows TTL 124 — one hop fewer for Guest, because the core decrements nothing for
> traffic it switches but does not route. See
> `enterprise-network-lab-test-results.md`.

**No direct paths between user segments.** S1, S2 and S3 have no direct
adjacency. Any communication between them would have to traverse the core, which
is exactly where it is denied. *(Requirement §6.)*

**Management is a separate plane.** S7 is an equal-rank segment reachable only
from S4. Placing device management on the same plane as ordinary user traffic is
a known weakness; separating it is standard hardening practice. *(General
principle: management plane separation. Requirement §10.)*

**VPN terminates at the edge of the network, not inside it.** Remote users (UC6,
UC7) enter from S9, are terminated on the edge router, and are then subjected to
the same policy enforcement point as everyone else, bypassing nothing. *(Design
decision DD-1, as amended — see below, and D11.)*

## 2.1.4 Design Decisions

Recorded explicitly, because alternatives existed and a reviewer may reasonably
ask why these were chosen.

**DD-1 — VPN termination on the firewall.** *(Superseded at implementation — see
below.)*
Alternatives: a dedicated VPN concentrator, termination on the edge router, or a
cloud VPN gateway. The firewall was chosen because a dedicated firewall already
exists in the design, it keeps a single policy enforcement point, and it keeps the
lab tractable. This is a choice, not a requirement.

> **Superseded — VPN terminates on the edge router (D11).** The chosen platform's
> simulated firewall does not support remote-access VPN termination, so the design
> intent — *every remote user crosses the enforcement point* — had to be achieved
> by another means. Termination moved to the edge router, and the intent is
> preserved structurally rather than by placement: the edge router holds no route
> into the internal network except through the firewall, so decrypted VPN traffic
> cannot reach an internal segment without being inspected. The remaining
> difference from the original plan is one of ordering, not of coverage —
> decryption now happens one device earlier. The constraint that drove the
> original decision ("the VPN must not bypass the firewall") was treated as
> binding throughout and was verified by test. See `2.9`, `2.5` and D11.

**DD-2 — Guest on a dedicated firewall interface.** *(Amended at physical
design — see below.)*
Alternative: treat Guest as another VLAN off the core and isolate it with ACLs.
The firewall-attached option was chosen for structural rather than rule-based
isolation, and because it models Guest correctly as an untrusted zone.

> **Amended — dedicated firewall interface, reached across the core at Layer 2.**
> The decision itself stands: Guest does terminate on its own firewall interface
> at security level 0, and its isolation is structural, not rule-based. What
> changed is the cabling. The original wording implied a direct physical
> attachment from the Guest access port to the firewall; the built topology
> carries VLAN 60 over the existing access-to-core trunk and from the core to the
> firewall's guest interface, with **no SVI for VLAN 60 anywhere on the core**.
> The alternative that was rejected — "another VLAN off the core, isolated with
> ACLs" — is still rejected, and the distinction is exactly the missing SVI. See
> `3.4-physical-topology.md` §3.4.4.

**DD-3 — Management as its own segment.**
Alternative: fold management addresses into the IT segment. Rejected because
device management interfaces and user workstations sit at different trust levels
and require different access control.

## 2.1.5 Traffic Flow Paths

Each Phase 1 flow mapped onto the topology, confirming the shape supports the
analysis. Paths below are the **as-built** paths; where they differ from the
original design, the difference is noted.

| Flow (Phase 1) | Path |
|----------------|------|
| Users → Servers (§3.1) | S1–S4 → Core → S5 |
| Users → Internet (§3.2) | S1–S4 → Core → Firewall → Edge Router (PAT) → S8 → S9 |
| Guest → Internet (§3.2) | S6 → Core *(Layer 2 transit, not routed)* → Firewall → Edge Router (PAT) → S8 → S9 |
| IT → Departments (§3.3) | S4 → Core → S1/S2/S3 |
| IT → Network devices (§3.4) | S4 → Core → S7 |
| Devices → Monitoring (§3.5) | Infrastructure → Core → S5 |
| Remote VPN (§3.6) | S9 → Edge Router *(VPN termination, D11)* → Firewall → Core → destination |

Two rows were corrected after implementation. The Guest row previously read
"S6 → Firewall → S8 → S9 *(never touches core)*", which is wrong in the built
network — the frames do touch the core, they are simply not routed by it. The
Remote VPN row previously placed termination at the firewall. In both cases the
corrected path still crosses the firewall exactly once, which is what the
requirement asked for.

# 2.2 Hierarchical Structure

## 2.2.1 The Model

The design follows a hierarchical model, simplified for a single-site network of
this size. The classic three-layer model is Core / Distribution / Access. In a
small single-site network, the core and distribution functions are commonly
**collapsed** into a single layer.

| Layer | Function in this design | Contains |
|-------|-------------------------|----------|
| **Edge / Perimeter** | Internet connectivity, address translation, VPN termination and security enforcement | Edge router (S8), firewall |
| **Core (collapsed core/distribution)** | Inter-VLAN routing, central aggregation point, Layer 2 transit for Guest | Core layer |
| **Access** | Endpoint connectivity | Access switches serving S1–S4, S5, S6, S7 |

## 2.2.2 Why a Collapsed Core

A separate distribution layer is justified when there are many access switches,
multiple buildings, or scale that makes a two-tier aggregation necessary. This
design has **42 users, one site, and two access switches** (§2, §11). A distinct
distribution layer would add cost and complexity with no benefit at this size.

Collapsing core and distribution keeps the hierarchy honest: there is still a
clear separation between *where endpoints attach* (access) and *where routing and
aggregation happen* (core), which is the functional point of the hierarchy.

## 2.2.3 Layer Responsibilities

**Edge / Perimeter**
- Terminates the ISP connection (S8 → S9)
- Translates internal addresses to the public address (PAT, on the edge router)
- Terminates VPN for remote users (UC6, UC7) — on the **edge router**, with no
  route inward except through the firewall (D11)
- Enforces all security policy (firewall)
- Provides the dedicated untrusted gateway for Guest (S6) at security level 0

**Core**
- Routes between VLANs/segments S1–S5 and S7
- Single aggregation point for all internal segments
- Enforces inter-segment restrictions that do not require the firewall
- Carries the Guest VLAN as **Layer 2 transit only** — no SVI, no routing

**Access**
- Attaches endpoints to their assigned segment
- Assigns endpoints to the correct VLAN (including wireless — see 2.8)
- Two access switches limit the blast radius of a single switch failure (SPOF-5)

## 2.2.4 Scalability of the Hierarchy

The requirement (§12) is that the network must grow without redesign. The
hierarchy supports this:

- **More users / switches** → add access switches to the existing core
- **More departments** → add segments/VLANs at the access layer; the core and
  addressing scheme already accommodate them (see 2.3, 2.4)
- **Additional sites** (Branch Office, Phase 2 extension) → attach at the edge
  layer, which is already the site's connectivity boundary
- **High availability** (Phase 2 extension) → the SPOF analysis ranks core,
  firewall and edge router as the top three single points of failure; the
  hierarchy allows each to be duplicated in place without restructuring

## 2.2.5 Hierarchy and the SPOF Analysis

The layer model makes the documented SPOFs legible. The consequences below are the
**measured** ones; they were corrected after the failure-testing campaign, which
did not agree with the predictions in every case.

| Layer | SPOF | Consequence if lost (measured) |
|-------|------|--------------------------------|
| Edge | SPOF-1 Edge Router, SPOF-4 ISP link | Internet and remote VPN lost; all internal routing survives |
| Perimeter | SPOF-2 Firewall | Internet lost for every segment, and the Guest segment loses its only gateway; **internal inter-segment routing survives**, because it happens on the core |
| Core | SPOF-3 Core | All inter-segment routing lost, and Guest loses its transit path — widest impact |
| Access | SPOF-5 Access switch | One user group only |

The SPOF-2 row previously read "Internet and all policy-controlled transit lost",
which overstated the impact: the firewall carries no internal transit in this
design, so internal segments keep talking to each other and to the servers when it
fails. Correcting that row changed the severity ranking — the edge router and the
firewall exchange places relative to the Phase 1 prediction. The revised ranking,
the test method and the per-device results are in
`enterprise-network-lab-spof-analysis.md`, which supersedes the Phase 1 ordering.

What the layer model got right is the general shape: impact widens as the failure
moves up the hierarchy, which is why the Phase 2 high-availability extension
addresses core, firewall and edge first.
