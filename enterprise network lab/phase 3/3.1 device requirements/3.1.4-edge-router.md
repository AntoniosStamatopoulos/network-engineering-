# 3.1.4 Device Requirements — Edge Router

Quantity: **1** (§11)

This document specifies what the edge router must be capable of. It does not
select a model — that is 3.3. Each requirement is derived from a decision already
made in Phase 1 or Phase 2, and the derivation is shown so that no requirement
rests on assumption.

The edge router carries fewer requirements than any other infrastructure device in
this design. That is a consequence of how responsibilities were allocated, not an
oversight — see the closing note.

## Derivations

### E1 — At least 2 interfaces

**Source:** 2.1.2 (topology), 2.5.4 (routing table).

Calculated by counting what attaches to the edge router:

| Interface | Connects to | Source |
|-----------|-------------|--------|
| WAN / outside | ISP | 2.1.2 — S8 WAN Edge ↔ S9 Internet |
| LAN / inside | Firewall | 2.1.2, and the `10.0.254.4/30` link in 2.5.4 |

Two is the minimum and, for the current topology, the exact figure. Nothing else
attaches to this device: the core, the access switches and the servers all sit
behind the firewall.

**Consequence for device selection.** The **type** of WAN interface matters more
than the count. It must match what the service provider delivers, which is a
constraint imposed from outside the design rather than derived from it. This
should be confirmed rather than assumed, since a mismatch cannot be resolved by
configuration.

### E2 — Static routes, with no path bypassing the firewall

**Source:** 2.5.4 — the edge router routing table.

```text
Directly connected:
  10.0.254.4/30    link to firewall
  <ISP subnet>     link to ISP

Static:
  10.0.0.0/8   →   10.0.254.5   (firewall)
  0.0.0.0/0    →   <ISP gateway>
```

Static routing support is the straightforward part. The requirement carries a
second element that is a **design constraint rather than a device capability**, and
2.5.4 states it explicitly:

> *"The route back toward the internal network points at the firewall, not past
> it. Return traffic is therefore subject to the same enforcement point as
> outbound traffic, and the edge router has no path that bypasses it."*

This matters because of what the edge router is **not** asked to do. Sub-stage
2.1.3 establishes the firewall as the single policy enforcement point, and that
only holds if no route exists around it. A route from the edge router directly to
an internal network — added for convenience, or inherited from a template — would
create a path that reaches the internal network without inspection, and it would
do so silently.

**Consequence for device selection.** No special capability is required. The
constraint applies to how the device is configured, and it should be recorded in
the configuration documentation so that a future engineer does not add the
"missing" route.

Dynamic routing is not required at present — 2.5.2 documents why — but see E6.

### E3 — NTP client and server

**Source:** 2.6.5 (the time synchronisation decision), 2.10.7.

This is the one requirement unique to this device, and it is unusual: the edge
router acts in **both roles simultaneously**.

```text
              external NTP source
                      ↓
                 Edge Router          ← client (receives)
                      ↓
        ┌─────────────┼─────────────┐ ← server (distributes)
        ↓             ↓             ↓
      Core        Switches      Servers
```

Sub-stage 2.6.5 rejected the alternative of each device querying an external
source independently, for two reasons.

**Fewer outbound flows.** Four external dependencies become one. Every outbound
connection is a path that must be permitted and could be misused, and 2.7.3 rule 3
grants that permission to this device alone.

**A common time source.** This is the more important reason, and 2.10.7 explains
why the distinction is not pedantic. The purpose of synchronised time is log
correlation — reconstructing the order of events during an investigation. Devices
synchronised independently to different sources can each be individually accurate
and still disagree with one another, which is the case that makes ordering
ambiguous. Devices taking time from a single internal source share whatever offset
that source carries, so their **relative** intervals remain correct even if the
absolute time drifts.

**Consequence for device selection.** The device must operate as an NTP server,
not only as a client. Serving time is a distinct function from consuming it, and a
device that supports only the client role cannot fulfil this design.

**Consequence for availability.** This concentrates a dependency. If the edge
router is unavailable, internal devices gradually drift apart. Sub-stage 2.6.5
notes that whether a dedicated internal time service would be preferable is an
implementation question to revisit if the network grows or if time accuracy
acquires compliance weight.

### E4 — SSH server; Telnet disableable

**Source:** 2.10.3 — *"| Routers | SSH (TCP 22) | IT management workstations |
Telnet disabled |"*

Two requirements follow from one line: SSH must be supported, and Telnet must be
capable of being **disabled** rather than merely left unconfigured. Sub-stage
2.10.3 treats unencrypted management protocols as a defect rather than an option,
noting that their availability on a device is itself a risk even when unused.

**Why this carries more weight here than elsewhere.** The edge router sits outside
the firewall and receives unfiltered traffic from the Internet. Telnet transmits
credentials in clear text; on an internal switch that is poor practice, but on a
device with an interface facing the public Internet it is a severe exposure.

The same reasoning extends beyond Telnet. Management access should not be reachable
from the WAN interface at all, and services the design does not use should be
disabled rather than left running. This is a configuration requirement rather than
a capability one, but it belongs with the device because the exposure is a property
of its position.

### E5 — SNMPv3 agent, Syslog client

**Source:** 2.10.5, 2.10.6.

- **SNMPv3** — 2.10.5 rejects v1 and v2c because the community string travels in
  clear text, and disables SNMP write access so that configuration changes occur
  only through authenticated, logged SSH sessions
- **Syslog** to 10.0.50.30 at severity level 6 (2.10.6), forwarded to a remote
  collector rather than held locally

Core ACL rule 6 (2.7.2) permits infrastructure devices to reach the monitoring
server, and the edge router is within that category.

NTP is covered separately by E3, since this device's role differs from every other
device's.

**A note on scope.** The SNMPv3 requirement applies identically to the core
switch (C10), the access switches (A8) and the firewall (F14). If the
implementation environment supports only v2c, the shortfall affects the entire
estate rather than one device, and should be recorded once as an estate-wide
limitation rather than four times.

### E6 — Dynamic routing (future requirement)

**Source:** 2.5.2 — the migration trigger.

Static routing was selected because the topology has exactly one path to every
destination. Sub-stage 2.5.2 states the criterion plainly: dynamic routing
protocols exist to decide *which of the available paths should be used, and what
happens when one fails*, and where only one path exists that problem does not
arise.

It stops holding at either planned extension. A branch office (§5) introduces
multiple networks requiring manual routes at both ends, growing with every new
segment. High availability (§12) introduces genuine alternative paths, at which
point automatic failover becomes the entire purpose. Sub-stage 2.5.2 recommends
**OSPF** at that stage — an open standard, quick to converge, selecting paths by
bandwidth-derived cost, with a single-area deployment sufficient at the size this
network would then be.

**Why a future capability belongs in a present requirement list.** A router
without OSPF support would have to be **replaced** when the trigger arrives rather
than reconfigured. The cost of omitting this from selection is measured in
hardware, not effort.

This requirement is identical in kind to C14 on the core switch. Both devices
would need to participate in the same routing domain, so both must support it or
neither transition is possible.

### E7 — Ability to form a redundant pair (future requirement)

**Source:** §12 (high availability extension), 2.5.2.

The architecture sketched in §12 pairs devices rather than adding interfaces:

```text
                 Internet
                /        \
             ISP 1      ISP 2
               |          |
          Edge-R1      Edge-R2
               \        /
             FW-1    FW-2
                \    /
              Core Network
```

Sub-stage 2.5.2 confirms this reading: *"A second edge router, second firewall and
second ISP create genuine alternative paths."*

**What this means for the current selection.** The second ISP connection arrives
with a **second router**, not on a spare interface of the existing one. The
requirement is therefore not additional WAN interfaces, but the ability to
participate in a redundant pair.

Two mechanisms can provide this:

| Mechanism | How it works |
|-----------|--------------|
| **First-hop redundancy protocol** (HSRP, VRRP) | Two routers present a single virtual address; the firewall points at the virtual address and failover is transparent |
| **Dynamic routing** | The firewall learns routes from both routers and selects between them |

The first is the more common approach for first-hop redundancy specifically, and
is typically simpler where the downstream device is a firewall rather than a
router.

**Consequence for device selection.** As with E6, a device that cannot participate
in a redundant pair would need replacing rather than supplementing when redundancy
is added. Both E6 and E7 are consequences of the same future decision, and a model
supporting neither commits the design to a hardware replacement at the high
availability extension.

## What This Device Does Not Do

The edge router carries seven requirements where the firewall carries fifteen and
the core switch fourteen. This is worth stating explicitly, because a short list
can be mistaken for an incomplete one.

| Function | Where it lives | Source |
|----------|----------------|--------|
| Security policy enforcement | Firewall | 2.1.3 — single policy enforcement point |
| Network address translation | Firewall | 2.5.6 |
| VPN termination | Firewall | DD-1, 2.9.2 |
| Inter-VLAN routing | Core switch | 2.5.3 |
| Access control lists | Core switch and firewall | 2.7.2, 2.7.3 |
| DHCP | Core switch and firewall | 2.4.7, C8, F12 |

The edge router performs exactly two functions: **connectivity to the provider**
and **time distribution**. Everything else was deliberately assigned elsewhere.

A narrow role is evidence of clear responsibility allocation rather than an
underused device. Each function in this design has one home, which means the
answer to "where is this enforced?" has one answer — and that property is what
makes the design auditable.

## Selection Priority

| Priority | Requirements | Consequence if unmet |
|----------|--------------|----------------------|
| **Essential** | E1, E2 | The device cannot be connected, or traffic has no path |
| **Essential** | E3 (server role) | No internal time source; every device must obtain time externally, adding outbound flows and losing the common reference that makes log correlation reliable |
| **Important** | E4, E5 | Management is exposed over an unencrypted protocol, or the device cannot be monitored |
| **Future** | E6, E7 | Functions today; requires hardware replacement at the migration trigger |

E3 is listed as essential rather than important because its absence does not
merely remove a convenience. Without an internal time server, either every device
acquires an external dependency — contradicting the decision in 2.6.5 and
requiring new firewall rules — or devices go unsynchronised, which undermines the
log correlation the monitoring design exists to support.

Any requirement that cannot be met should be recorded as an implementation
limitation in 3.3, with its consequence stated — not silently dropped.
