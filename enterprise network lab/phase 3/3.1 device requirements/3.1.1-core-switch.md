# 3.1.1 Device Requirements — Core Switch

Quantity: **1** (§11)

This document specifies what the core switch must be capable of. It does not
select a model — that is 3.3. Each requirement is derived from a decision already
made in Phase 1 or Phase 2, and the derivation is shown so that no requirement
rests on assumption.

**The test applied to every entry:** if a requirement cannot be traced to a
documented decision, it does not belong here. A requirement without a source is a
habit rather than a need.

## Derivations

### C1 — Layer 3 switching with SVIs

**Source:** 2.5.3 — *"Method: Layer 3 core switch with SVIs."*

Sub-stage 2.5.3 placed inter-VLAN routing for the routed internal VLANs on the
core and rejected two alternatives: router-on-a-stick, because all inter-VLAN
traffic would traverse a single link and become a bottleneck; and routing on the
firewall, because it would load the firewall with internal traffic requiring no
policy inspection. VLAN 60 is the explicit exception established in 2.8.4: the
core carries it only at Layer 2, has no VLAN 60 SVI, and its gateway remains on
the firewall.

**Consequence for device selection.** A Layer 2 switch cannot create switched
virtual interfaces and therefore cannot route between VLANs at all. This is the
single requirement that disqualifies the largest number of candidate models, and
it should be checked first.

### C2 — Support for at least 8 VLANs

**Source:** 2.3.3 — the VLAN plan defines 10, 20, 30, 40, 50, 60, 99 and 999.

Eight VLANs are in use. In practice any managed switch supports far more, so this
is rarely a constraint, but it is recorded because 2.3.3 also reserves ranges for
growth — 51–59 for additional server VLANs, 70–90 for additional departments, and
100–199 for additional sites (§12). A model with a low VLAN ceiling would
constrain that expansion even though it satisfies today's count.

### C3 — 802.1Q trunking

**Source:** 2.3.7 — *"Core ↔ access trunks carry VLANs 10, 20, 30, 40, 60, 99."*

Multiple VLANs share a single physical link between the core and each access
switch. Without 802.1Q tagging, frames from different VLANs would be
indistinguishable on that link and the segmentation would not survive the trunk.

### C4 — Configurable native VLAN

**Source:** 2.3.7 — *"The native VLAN on all trunks is set to 999, not the default
VLAN 1, to mitigate VLAN hopping."*

The native VLAN is the one carried untagged across a trunk. Left at the default of
VLAN 1, it enables a double-tagging attack in which crafted frames jump into
another VLAN. Setting it to an unused VLAN removes the destination that attack
depends on.

**Consequence for device selection.** The switch must permit the native VLAN to be
changed. A device that hard-codes VLAN 1 as native cannot implement this control.

### C5 — Static routes and a default route

**Source:** 2.5.4 — the core routing table.

```text
Directly connected:
  10.0.10.0/24
  10.0.20.0/24
  10.0.30.0/24
  10.0.40.0/24
  10.0.50.0/24
  10.0.99.0/24
  10.0.254.0/30  (link to firewall)
Static:
  0.0.0.0/0 → 10.0.254.2 (firewall)
```

There is deliberately no Layer 3 entry for 10.0.60.0/24 on the core. VLAN 60
crosses the core only as a Layer 2 transit VLAN and is directly connected to the
firewall, where 10.0.60.1/24 is the gateway.

The default route carries more weight than its single line suggests. Sub-stage
2.5.4 identifies it as the mechanism enforcing the single policy enforcement point
established in 2.1: anything the core does not recognise as internal is sent to
the firewall, so all external traffic is compelled through the control point.

Dynamic routing protocols are not required now — 2.5.2 documents why — but see
C14.

### C6 — Extended ACLs, applied per interface

**Source:** 2.7.2 — the core access control list, ten rules.

The requirement is specifically for **extended** ACLs rather than standard ones.
This is not stated in 2.7.2 and is inferred from the rules themselves:

```text
| 1 | VLAN 40 (IT) | VLAN 99 (MGMT) | SSH 22, SNMP 161 | permit |
                                       ↑ filters on protocol and port
```

A standard ACL matches on source address only. Several rules in 2.7.2 match on
destination, protocol and port together, which requires extended ACL support.

**Consequence for device selection.** Rule order is also load-bearing here.
Sub-stage 2.7.2 notes that rules 1 and 2 carry the entire management boundary and
must be evaluated in sequence, so the switch must apply ACLs top-to-bottom with
first-match semantics — the standard behaviour, but worth confirming.

### C7 — Per-rule ACL logging

**Source:** 2.7.6 — the logging policy; 2.7.2 — the Log column.

Seven of the ten core rules are marked for logging: all deny rules, management
access, and privileged access to servers. Routine user traffic is deliberately not
logged, because volume would obscure meaningful entries.

**Consequence for device selection.** Logging must be configurable **per rule**,
not globally. A device that logs all matches or none cannot implement the
selective policy 2.7.6 specifies.

### C8 — DHCP server, four scopes

**Source:** 2.4.7 — five DHCP scopes; VLAN 60 is served by the firewall (2.4.3),
leaving four for the core.

```text
VLAN 10, 20, 30, 40 → pool .100–.199, 8-hour lease
```

**Design decision — DHCP server rather than relay.**

DHCP clients begin with no address and broadcast to discover a server. Broadcasts
do not cross routed boundaries, so each VLAN needs either a server present within
it or a relay agent to forward the request elsewhere. Two options were considered.

*Relay to a central DHCP server* was rejected. It would require infrastructure
that does not exist: §3 defines the server infrastructure as DNS and Web, with a
File Server as a future addition, and no DHCP server is specified. Adding one
would mean a device list entry, an address allocation, new traffic flows and new
firewall rules — and a new single point of failure, since its loss would prevent
every VLAN from issuing addresses. It also solves a problem this network does not
have: central management is valuable across many scopes and multiple sites, and
this design has four scopes at one site.

*A DHCP server on the core* was selected. The core already holds an SVI in each of
the four VLANs (2.5.3), so it receives their broadcasts directly with no
additional forwarding configuration. It introduces no new device and no new
failure point, and it remains available if the server segment is unavailable.

**What this accepts.** Scopes live in the switch configuration rather than in a
single console, which is manageable at four scopes and would not be at forty. The
core also gains a further responsibility alongside routing and ACLs, which
compounds SPOF-3 — although since a core failure already removes all routing, the
marginal impact of also losing DHCP is small.

**Migration trigger.** Revisit when a branch office is added (§5), when VLAN count
grows substantially, or when DHCP reservations are needed at scale.

### C9 — SSH server; Telnet disableable

**Source:** 2.10.3 — *"Telnet and HTTP are disabled on every device."*

Sub-stage 2.10.3 states that unencrypted management protocols are a defect and
that their availability on a device is itself a risk even when unused. This yields
two distinct requirements: the switch must support SSH, and it must permit Telnet
to be disabled rather than merely left unconfigured.

### C10 — SNMPv3 agent, read-only

**Source:** 2.10.5 — SNMPv3 selected; v1 and v2c rejected.

Versions 1 and 2c transmit their community string in clear text, so anyone
observing the traffic can subsequently query the device themselves. Version 3
provides authentication and encryption.

Sub-stage 2.10.5 also states that SNMP write access is not enabled: configuration
changes are made through authenticated, logged SSH sessions, and enabling SNMP
write would create a second configuration path with weaker accountability.

**Consequence for device selection.** SNMPv3 specifically. A model supporting only
v2c cannot meet this requirement, and the shortfall would need to be recorded as
an implementation limitation rather than quietly accepted.

### C11 — Syslog client, remote, configurable severity

**Source:** 2.10.6 — collector at 10.0.50.30, UDP 514, severity level 6.

The switch must forward log messages to a remote collector rather than only
storing them locally, and the severity threshold must be configurable. Level 6
was chosen in 2.10.6 to capture logins, configuration changes, warnings and
failures while excluding per-packet debug output; a device with a fixed severity
level could not implement that balance.

Central collection matters beyond convenience: 2.10.6 notes that logs held locally
on a device can be deleted by an attacker who compromises it, while messages
already forwarded are beyond reach.

### C12 — NTP client

**Source:** 2.10.7 and 2.6.5 — internal devices synchronise from the edge router.

Sub-stage 2.10.7 explains why this is not a minor detail: incident analysis
depends on establishing a sequence of events, and timestamps that disagree by an
unknown amount make both ordering and causation undeterminable. The property that
matters is consistency rather than absolute accuracy, which is why all devices
take time from a single internal source.

### C13 — At least 9 ports, of which 2 at 10 Gbps

**Source:** 2.1.2 (topology), §11 (device count), and a decision taken here.

This requirement is **calculated rather than read**. The logical topology in 2.1.2
shows segments, not devices — S1 through S5 and S7 are VLANs and do not each
consume a physical port. What consumes ports is the set of devices that attach to
the core.

**Design decision — servers attach directly to the core.**

Two options were considered for the three servers (DS1, DS2, DS3).

*Connecting them to an access switch* would keep the core at three ports. It was
rejected because it would materially worsen an existing single point of failure.
SPOF-5 is currently recorded as local in scope: an access switch failure affects
only the user group attached to it, and the design deliberately uses two access
switches to limit that blast radius. Placing the servers behind one of those
switches would mean a single access switch failure also removes DNS, the web
server and monitoring for the entire site — converting SPOF-5 from local to
site-wide and undoing a mitigation already made.

*Connecting them directly to the core* was selected. It preserves the scope of
SPOF-5, removes one hop from every server access — relevant because DNS is
classified as high criticality in the Phase 1 traffic characterization — and is
consistent with the trust model, in which Z5 (Servers) sits at a higher protection
level than the user zones (2.6.2).

**Port count:**

```text
Firewall inside link  1
Firewall Guest link   1
Access Switch 1       1
Access Switch 2       1
DNS Server (DS1)      1
Web Server (DS2)      1
Monitoring (DS3)      1
                    ───
                      7  current
File Server (DS5)     1  Phase 2 extension (§3)
spare                 1
                    ───
                      9  minimum
```

The second firewall connection is the VLAN 60 handoff introduced by the Layer 2
transit decision in 2.8.4. The File Server is listed as a planned extension in §3
and §12; providing for its port now avoids a switch replacement later. In
practice most Layer 3 switches offer 24 or more ports, so this is unlikely to
constrain selection — but the figure should be verified rather than assumed.

The Packet Tracer implementation adds one WLC connection because its autonomous
AP model cannot provide five SSIDs. That implementation-only port is not part of
the autonomous real-design minimum above; the selected 24-port core has ample
capacity for it.

**Port speeds.** Sub-stage 3.2.2 selects 10 Gbps for the access-to-core uplinks,
giving a 2.4:1 oversubscription ratio rather than the 24:1 that 1 Gbps uplinks
would produce. The core must therefore provide:

```text
2 ports at 10 Gbps    access switch uplinks
7 ports at 1 Gbps     two firewall links, three servers, File Server, spare
```

This matters at selection in a way the port count alone does not convey: a switch
offering eight Gigabit ports and no 10 Gbps interfaces satisfies the count while
failing the specification. Port speed should be checked alongside port count
rather than after it.

### C14 — OSPF support (future requirement)

**Source:** 2.5.2 — the migration trigger from static to dynamic routing.

Static routing was selected in 2.5.2 because the topology has exactly one path to
every destination, and a dynamic protocol would add configuration complexity, CPU
and bandwidth overhead, and an attack surface requiring authentication in exchange
for no operational benefit. That reasoning holds today.

It stops holding when either planned extension arrives. A branch office (§5)
introduces multiple networks requiring manual routes at both ends; high
availability (§12) introduces genuine alternative paths, at which point automatic
failover becomes the entire point. Sub-stage 2.5.2 recommends OSPF at that stage.

**Why this belongs in a present-day requirement list.** The capability is not
needed now, but a switch that cannot run OSPF would have to be **replaced** when
the trigger arrives, rather than reconfigured. A future decision therefore
constrains a present selection, and the cost of ignoring it is measured in
hardware rather than effort.

## Selection Priority

If no available model satisfies every requirement, these are the ones that cannot
be compromised without breaking the design:

| Priority | Requirements | Consequence if unmet |
|----------|--------------|----------------------|
| **Essential** | C1, C3, C5, C6 | Inter-VLAN routing, segmentation or the security policy does not function at all |
| **Essential** | C13 | Devices cannot physically be connected, or the access uplinks are constrained to 24:1 oversubscription |
| **Important** | C4, C7, C8, C9, C10, C11 | A specific control or service is lost; the design functions but a documented decision is not implemented |
| **Baseline** | C2, C12 | Almost universally supported; verify rather than evaluate |
| **Future** | C14 | Functions today; requires hardware replacement at the migration trigger |

Any requirement that cannot be met should be recorded as an implementation
limitation in 3.3, with its consequence stated — not silently dropped.
