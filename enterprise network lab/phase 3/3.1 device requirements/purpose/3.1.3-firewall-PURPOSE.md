# 3.1.3 — Purpose

Why the firewall requirement list exists, and what it is used for.

> Companion to `3.1.3-firewall.md`.

---

## What this list does

It defines what the firewall must be capable of — fifteen requirements, more than
any other device in the design.

## Why the count is highest here

Three roles converge on one device:

| Role | Established in |
|------|----------------|
| Single policy enforcement point | 2.1.3 |
| Boundary of an untrusted internal zone (Guest) | DD-2, 2.8.4 |
| VPN termination point | DD-1, 2.9.2 |

Each role brings its own requirements. The second is unusual — most designs give a
firewall an inside and an outside; this one adds a third zone terminating on its
own interface.

---

## The requirement that is not like the others

**F1 — stateful inspection.**

It is the only requirement in the entire phase derived from an **implicit
assumption**. No document states that the firewall must be stateful. Sub-stage
2.7.4 states that rules are written only for the direction that initiates a
connection — which is unworkable without it.

### Why it is placed above "essential"

Every other unmet requirement **removes** something: a control is lost, a service
does not function, a device cannot be connected.

An unmet F1 **adds** something. Return traffic would match no rule and be dropped,
so every permitted flow would need a reverse rule — granting servers and external
hosts the ability to initiate inbound connections, which is precisely what the
asymmetric policy in 2.6.3 was written to withhold.

And it would do so **without any visible failure**. The rule list would read
correctly. This is why it is listed in a band of its own.

---

## Where it is used

**At selection (3.3).** F1 and F2 are the primary filters: stateful inspection,
and at least four interfaces. A firewall with two interfaces cannot express the
zones this design defines.

**At implementation.** F3 matters more here than on the core. Sub-stage 2.7.3 notes
that reversing firewall rules 1 and 2 would **silently** break external name
resolution — the DNS server would match the deny first and the permit would never
execute.

**At defence.** F9 carries §9 entirely. If asked how remote Finance is prevented
from reaching the management plane, the answer is per-pool policy, enabled by the
separate address pools in 2.9.3.

---

## Where implementation gaps are expected

This is the device most likely to reveal a difference between design and
environment. Four requirements are flagged for early verification in the main
document:

| Requirement | If unavailable |
|-------------|----------------|
| **F9** per-pool policy | Implement one VPN only; do not implement both with identical access |
| **F10** certificates | Fall back to credentials, recording **both** levels of degradation |
| **F14** SNMPv3 | An estate-wide limitation, not a firewall-specific one |
| **F6** log granularity | Function retained, visibility reduced |

The F9 guidance is the one that matters most. A missing capability is preferable to
a capability present with wrong permissions — remote Finance users with
management-plane access would violate §9 directly, while a missing Finance VPN is
simply an unimplemented feature.
