# 3.1.2 — Purpose

Why the access switch requirement list exists, and what it is used for.

> Companion to `3.1.2-access-switches.md`.

---

## What this list does

It defines what each access switch must be capable of — eleven requirements,
identical for both devices.

## Why both switches share one list

Users are distributed across the two switches rather than grouped by department
(A9). Neither is a special case, so one requirement set covers both.

That distribution was itself a decision taken in this document. Grouping by
department would have been intuitive and would have concentrated failure: a single
switch failure would have removed an **entire** department rather than a portion of
each. The requirement list surfaced the question by requiring a port count.

---

## The one requirement that saves money

**A1 — Layer 3 is not required.**

This is a **negative** requirement, and it is worth stating explicitly because it
narrows selection and reduces cost. All routing lives on the core (2.5.3), so the
access switches forward frames and nothing more.

Specifying Layer 3 capability here would pay for a function the design does not
use, and would create the possibility of routing being configured somewhere the
documentation does not account for.

---

## Where it is used

**At selection (3.3).** A4 and A10 are the discriminating requirements. A4 —
access and trunk ports on the same switch — excludes unmanaged switches entirely.
A10 requires two uplinks, which is not obvious from the topology diagram.

**At physical design (3.4).** A9 and A10 together determine how many ports each
switch needs and where they lead.

**At implementation.** A6 is a configuration step that is easy to skip: every
unused port assigned to VLAN 999. It costs one command and closes the rogue-device
path described in 2.3.4.

---

## Two corrections this list produced

**A2 was initially wrong.** The first draft specified eight VLANs, copied from the
core. Counting what actually reaches an access switch gives **seven** — VLAN 50
never arrives there, because servers attach directly to the core.

**A10 was initially wrong.** The first draft specified one uplink, based on the
topology diagram in 2.1.2, which shows a single line from each access switch to
the core. The second uplink comes from 2.8.4 — the dedicated path carrying VLAN 60
to the firewall.

Both errors came from the same cause: reading the topology diagram rather than
scanning every document. The topology shows segments, not cables, and it does not
show decisions taken in later sub-stages.

---

## The requirement to verify carefully

**A9 — port count.** The calculation gives 22 access-side connections per switch.
Whether that fits a 24-port model depends on something the datasheet may not make
obvious: some models provide dedicated uplink interfaces **in addition to** 24
access ports, while others count everything together.

The difference is two spare ports versus none — and §12 requires headroom for
growth.
