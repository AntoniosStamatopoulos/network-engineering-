# 3.1.1 — Purpose

Why the core switch requirement list exists, and what it is used for.

> Companion to `3.1.1-core-switch.md`. The requirements and their derivations are
> in that file; this one explains what the list is for.

---

## What this list does

It defines what the core switch must be capable of — fourteen requirements, each
traced to a Phase 2 decision.

## Why this device carries the most requirements

Phase 2 assigned the core more functions than any other internal device:

| Function | Assigned in |
|----------|-------------|
| Inter-VLAN routing | 2.5.3 |
| Access control lists — ten rules | 2.7.2 |
| DHCP for four scopes | 2.4.7 + decision in C8 |
| Trunk termination | 2.3.7 |
| Management, monitoring, time | 2.10 |

The length of the list is therefore **evidence about the design**, not about the
device. It shows where responsibility was concentrated.

That concentration is worth noticing rather than assuming. It is why SPOF-3 — the
core — is the most severe single point of failure in the analysis: its loss
removes routing, access control, and address assignment simultaneously.

---

## Where it is used

**At selection (3.3).** C1 disqualifies more candidates than any other
requirement: a Layer 2 switch cannot create SVIs and therefore cannot route between
VLANs at all. Check it first and most candidates resolve immediately.

**At physical design (3.4).** C13 produces the port count, and that figure comes
with a decision embedded in it — servers attach directly to the core rather than
through an access switch, to keep SPOF-5 local in scope. The physical topology
must reflect that.

**At implementation.** The list becomes a configuration checklist. Fourteen
requirements, each either configured or deliberately not.

**At defence.** If asked why the core needs to run DHCP, the answer is C8 — with
the alternative considered, the reason it was rejected, and the migration trigger.

---

## The requirement most likely to be overlooked

**C14 — OSPF support.** It is not needed today, and 2.5.2 explains at length why
static routing is correct for the current topology.

It appears in the list because a switch without OSPF would need to be **replaced**
when a branch office or high availability arrives, rather than reconfigured. The
cost of omitting it from selection is measured in hardware.

The same requirement appears as E6 on the edge router. Both devices would need to
participate in the same routing domain, so either both support it or neither
transition is possible.

---

## What C13 revealed

The port count required a decision that no Phase 2 document had taken: where the
servers attach.

Connecting them through an access switch would have converted SPOF-5 from local to
site-wide — a single access switch failure would have removed DNS, web and
monitoring for every user. The requirement list surfaced that question by forcing
a number to be produced.

This is a general property of calculated requirements: they expose decisions that
prose left implicit.
