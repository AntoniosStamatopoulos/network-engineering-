# 3.1.6 — Purpose

Why the server requirement list exists, and what it is used for.

> Companion to `3.1.6-servers.md`.

---

## What this list does

It defines what each server must be capable of — and, uniquely in this phase, what
two of them must **not** be capable of.

## Why this list is structured differently

The five preceding documents cover **infrastructure** — devices that carry traffic.
This one covers **destinations**, and that changes two things.

### Requirements are not uniform

Both access switches have identical requirements. The three servers do not:

```text
DNS:        forwarding, authoritative records, four VLANs — four requirements
Web:        HTTP and HTTPS — one requirement
Monitoring: Syslog, SNMP polling, traps, ICMP, storage — five requirements
```

The document is therefore split into **common** and **per server** sections.

### Negative requirements appear

S8 does not state what a device must do. It states that DS2 and DS3 must have **no
outbound Internet access**.

Nothing like this appears in the earlier lists.

---

## Why a negative requirement has to be written down

The mechanism enforcing S8 is the **absence** of a permit rule. Nothing in the
firewall configuration will mention DS2 or DS3 — they fall through to the default
deny.

An absence cannot be reviewed. Without this entry, the constraint would exist only
as something that is not there, and a future engineer adding outbound access "so
the server can update itself" would not be contradicting anything written down.

It also carries an implementation consequence a firewall rule cannot express: the
servers must **function** without outbound access. Software expecting to reach
update repositories or licence servers during normal operation behaves
unpredictably when those connections fail silently.

---

## The consequence that leaves the network layer

S8 produces a **procedural** requirement from a network constraint:

```text
No outbound access
        ↓
cannot download updates
        ↓
patching must be performed manually
        ↓
a documented maintenance procedure is required
```

Sub-stage 2.6.4 accepts the approach **on condition** that this procedure exists
and is performed on a schedule. That condition is part of the design, not an
optional practice — and an unpatched server is a greater exposure than a server
with narrowly controlled outbound access.

This is the only place in Phase 3 where a requirement lands outside the network
and in operational documentation.

---

## Where it is used

**At implementation.** The list tells you which services to enable — and, more
usefully, which to leave disabled:

```text
DS2 Web Server:
  ✓ HTTP, HTTPS
  ✗ DNS, FTP, mail, anything else
```

Every enabled service the design does not require is attack surface. The list is
the record of what is required, so everything absent from it can be turned off
with confidence.

**At diagnosis.** The list gives an ordered check sequence. If external names stop
resolving: S1b (is forwarding configured?), S1c (are the forwarders correct?),
firewall rule 1 (is the outbound path permitted?). Three points, in order, rather
than searching.

**At defence.** If asked why the web server cannot reach the Internet, the answer
is S8 — with the trade-off from 2.6.4 and the procedural requirement it creates.

---

## What the list revealed

**S9 is an inference.** No document states that servers run an SNMP agent. It
follows from core ACL rule 6 (infrastructure devices reach the monitoring server)
and from 2.10.4 listing server availability among monitored metrics.

Monitoring CPU and memory requires an agent; without one, only ICMP reachability
can be established — which answers whether the machine responds, not whether it is
working.

The main document recommends amending 2.10.5 to include servers explicitly. This
is the second such gap found by scanning, after W11 in 3.1.5.

**S3e is open.** Log retention is implied by 2.10.6 but no period is defined. This
is recorded as an open decision rather than filled in arbitrarily — a retention
period chosen deliberately is preferable to one that emerges from whatever the
storage happens to hold.
