# 3.1.4 — Purpose

Why the edge router requirement list exists, and what it is used for.

> Companion to `3.1.4-edge-router.md`.

---

## What this list does

It defines what the edge router must be capable of — seven requirements, fewer
than any other infrastructure device.

## Why the count is lowest here

Because Phase 2 assigned nearly every function elsewhere:

| Function | Where it lives |
|----------|----------------|
| Security policy | Firewall (2.1.3) |
| Address translation | Firewall (2.5.6) |
| VPN termination | Firewall (DD-1) |
| Inter-VLAN routing | Core (2.5.3) |
| Access control lists | Core and firewall (2.7) |
| DHCP | Core and firewall (2.4.7) |

The edge router performs **two** functions: connectivity to the provider, and time
distribution.

### Why a short list is a good sign

A short requirement list can be mistaken for an incomplete one. It is the opposite.

Each function in this design has **one home**, which means the answer to "where is
this enforced?" has one answer. That property is what makes the design auditable —
and the edge router's narrow role is direct evidence of it.

The main document includes a table of what this device does *not* do, for exactly
this reason.

---

## The requirement unique to this device

**E3 — NTP client and server.**

Most devices are NTP clients. This one is **both**: it obtains time externally and
distributes it internally. It is the only device in the design with an external
time dependency (firewall rule 3 permits it and nothing else).

### Why it is essential rather than important

Without an internal time server, one of two things happens. Either every device
acquires its own external dependency — contradicting the decision in 2.6.5 and
requiring new firewall rules — or devices go unsynchronised.

The second is worse than it sounds. Sub-stage 2.10.7 explains that log correlation
depends on devices agreeing about time, and that devices synchronised to different
sources can each be individually accurate while disagreeing with one another. That
is the case that makes event ordering undeterminable during an investigation.

---

## Where it is used

**At selection (3.3).** E1 is unusual: the interface **type** matters more than the
count. It must match what the service provider delivers — a constraint imposed from
outside the design, which cannot be resolved by configuration.

**At implementation.** E2 carries a constraint that no capability check will catch:
the router must have **no route that bypasses the firewall**. Sub-stage 2.5.4 makes
this explicit, and it should appear in the configuration documentation so a future
engineer does not add the "missing" route to an internal network.

**At defence.** If asked why the edge router performs no filtering, the answer is
2.1.3 — the firewall is the single policy enforcement point, and splitting policy
across two devices would mean the answer to "what can reach this system?" requires
reading two configurations.

## The correction this list produced

**E7 was initially wrong.** The first draft specified a second WAN interface, on
the assumption that dual-ISP redundancy would arrive on a spare port.

Reading §12 and 2.5.2 shows otherwise: the architecture pairs **devices**, not
interfaces. A second ISP arrives with a second router.

The correct requirement is therefore the ability to participate in a redundant
pair — through a first-hop redundancy protocol or dynamic routing — not additional
WAN ports.

The correction matters because the two requirements would lead to different
purchases.
