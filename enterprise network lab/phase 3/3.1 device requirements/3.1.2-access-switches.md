# 3.1.2 Device Requirements — Access Switches

Quantity: **2** (§11)

This document specifies what each access switch must be capable of. It does not
select a model — that is 3.3. Each requirement is derived from a decision already
made in Phase 1 or Phase 2, and the derivation is shown so that no requirement
rests on assumption.

Both switches carry identical requirements. The user population is distributed
across them rather than divided by department (see A9), so neither is a special
case.

## Derivations

### A1 — Layer 2 switching; Layer 3 not required

**Source:** 2.5.3 — *"Method: Layer 3 core switch with SVIs."*

This is a **negative** requirement, and it is worth stating explicitly because it
narrows selection and reduces cost.

Sub-stage 2.5.3 placed the routed internal VLAN gateways on the core. VLAN 60 is
the explicit exception established in 2.8.4: it has no SVI on the core and its
gateway is 10.0.60.1 on the firewall. The access switches therefore forward
frames within a VLAN and make no routing decisions; their single core uplink also
carries VLAN 60 so that the core can forward it at Layer 2 to the firewall.

**Consequence for device selection.** A Layer 2 switch is sufficient. Selecting
Layer 3 capability here would pay for a function the design does not use, and
would create the possibility of routing being configured in a place the
documentation does not account for.

### A2 — At least 7 VLANs, with headroom

**Source:** 2.3.3 — the VLAN plan.

Counting only the VLANs that actually reach an access switch:

| VLAN | Reason it is present |
|-----:|----------------------|
| 10 | HR users connect here |
| 20 | Finance users connect here |
| 30 | Sales users connect here |
| 40 | IT users connect here |
| 60 | Carried from the access point (2.8.5) |
| 99 | Management, carried in-band (2.10.2) |
| 999 | Unused ports are parked here (2.3.4) |

Seven. **VLAN 50 is absent**: the servers connect directly to the core rather than
through an access switch (3.1.1, C13), so the server VLAN never appears here.

**Consequence for device selection.** Any managed switch supports far more than
seven, so this will not disqualify a candidate. It is recorded for completeness
and because 2.3.3 reserves ranges for expansion — 51–59, 70–90 and 100–199 — which
a model with a low VLAN ceiling would constrain even while satisfying today's
count.

### A3 — 802.1Q trunking

**Source:** 2.3.7 (uplink) and 2.8.5 (access point).

The switch terminates trunks in two directions, which is easy to overlook when
reading only the topology:

```text
Uplink:   Access switch → Core       VLANs 10, 20, 30, 40, 60, 99
Downlink: Access point  → switch     VLANs 10, 20, 30, 40, 60
```

The second is a trunk toward an end device rather than toward infrastructure. The
access point tags each frame according to the SSID its client joined (2.8.5), and
the switch must honour those tags rather than treating the port as a single-VLAN
access port.

### A4 — Access and trunk ports on the same switch

**Source:** 2.8.5.

Two kinds of device attach to the same switch and require opposite port
configurations:

| Device | Port type | Behaviour |
|--------|-----------|-----------|
| Workstation | **Access** | Sends untagged frames; the switch assigns the VLAN by port |
| Access point | **Trunk** | Sends tagged frames; the switch honours the tag |

A workstation has no VLAN awareness — its VLAN is decided by which port it is
plugged into. An access point decides the VLAN itself, per client, based on the
SSID.

**Consequence for device selection.** The switch must support both port modes
simultaneously. This is standard on managed switches and absent on unmanaged ones,
which is one reason an unmanaged switch cannot be used anywhere in this design.

### A5 — Configurable native VLAN

**Source:** 2.3.7 — *"The native VLAN on all trunks is set to 999, not the default
VLAN 1, to mitigate VLAN hopping."*

The native VLAN is carried untagged across a trunk. Left at the default of VLAN 1,
it enables a double-tagging attack in which crafted frames reach another VLAN.
Setting it to an unused VLAN removes the destination the attack depends on.

Each access switch terminates **two** trunks in the autonomous-AP design, and the
setting applies to both:

```text
→ Core         (corporate VLANs plus Layer 2 Guest transit)
→ Access point (SSID VLANs)
```

### A6 — Per-port VLAN assignment

**Source:** 2.3.4 — *"Every unused port is assigned to VLAN 999."*

This requirement lands specifically on the access switches, because they are where
unused physical sockets exist. Sub-stage 2.3.4 describes the scenario it defends
against: a visitor or contractor finds a free network socket, plugs in a laptop,
receives an address and is on the network — with no password and no check.

Parking unused ports in a VLAN with no SVI anywhere means a device can link up and
reach nothing.

**Consequence for device selection.** The switch must allow VLAN assignment on a
per-port basis, including to a VLAN that carries no traffic. This is normal
managed-switch behaviour but is the mechanism the control depends on.

### A7 — SSH server; Telnet disableable

**Source:** 2.10.3 — *"Telnet and HTTP are disabled on every device."*

Sub-stage 2.10.3 treats unencrypted management protocols as a defect rather than
an option, noting that their availability on a device is itself a risk even when
unused. Two requirements follow: SSH must be supported, and Telnet must be
capable of being **disabled**, not merely left unconfigured.

### A8 — SNMPv3 agent, Syslog client, NTP client

**Source:** 2.10.5, 2.10.6, 2.10.7; confirmed by 2.7.2 rule 6.

Core ACL rule 6 permits infrastructure devices to reach the monitoring server:

```text
| 6 | Infrastructure devices | 10.0.50.30 | SNMP 162, Syslog UDP 514 | permit |
```

Access switches are within "infrastructure devices", so each must:

- run an **SNMPv3** agent — v1 and v2c are rejected in 2.10.5 because the
  community string travels in clear text
- forward **Syslog** to 10.0.50.30 with a configurable severity level, set to 6
  (2.10.6)
- act as an **NTP client**, synchronising from the edge router (2.10.7)

The NTP requirement is not incidental. Sub-stage 2.10.7 explains that log
correlation depends on devices agreeing about time: a switch whose clock disagrees
with the firewall's by an unknown amount makes it impossible to establish the
order of events during an investigation.

### A9 — At least 22 access ports

**Source:** §2 (42 users), §11 (two access switches), 2.8.5 (one access point per
switch), and a decision taken here.

**Design decision — users distributed across switches rather than grouped by
department.**

Two options were considered.

*Grouping by department* would place HR and Finance on one switch and Sales and IT
on the other. It is intuitive, and it was rejected for two reasons.

It produces an unbalanced port requirement: HR (8) plus Finance (8) is sixteen
ports, while Sales (20) plus IT (6) is twenty-six — requiring different switch
sizes for what §11 describes as two access switches.

More significantly, it concentrates failure. SPOF-5 records an access switch
failure as local in scope, affecting only the user group attached to it, and the
design uses two access switches specifically to limit that blast radius. Grouping
by department would mean a single switch failure removes an **entire department** —
all twenty Sales users at once.

*Distributing users across both switches* was selected. Port requirements are
balanced at roughly 21 users each, and a switch failure affects a portion of every
department rather than eliminating any one of them. No department is left entirely
without service.

It is also more consistent with what is already documented: 2.3.7 specifies that
**both** core-facing trunks carry VLANs 10, 20, 30, 40, 60 and 99, which is only
correct if both switches host users from all four departments. Grouping by
department would have required revising that trunk specification.

VLANs decouple logical grouping from physical location, so a user's department is
determined by their port's VLAN assignment rather than by which switch they
happen to be connected to. Distribution costs nothing in segmentation terms.

**Port calculation, per switch:**

```text
Users (42 ÷ 2)         21
Access point            1
                      ───
                       22  access-side ports minimum
```

**A caution for model selection.** The uplink is counted separately in A10, but
whether it consumes an access port depends on the model. Many 24-port switches
provide dedicated uplink interfaces in addition to 24 access ports, in which case
22 access-side connections leave two spare. Others count all ports together, in
which case 22 plus one uplink consumes 23 of 24 ports and leaves one spare. **This
should be verified per candidate model rather than assumed.**

§2 also notes that the lab need not contain one endpoint per employee — a smaller
number of representative endpoints may be used while the addressing plan supports
the full count. The port requirement above is therefore the figure for a real
deployment; the implementation may connect fewer.

### A10 — One 10 Gbps uplink to the core

**Source:** 2.8.4 — the Guest traffic path decision.

Sub-stage 2.8.4 selects Layer 2 transit for VLAN 60. Each access switch therefore
uses one uplink to the core, carrying the corporate VLANs, management and Guest:

```text
Uplink → Core switch    VLANs 10, 20, 30, 40, 60, 99
```

The core forwards VLAN 60 at Layer 2 to the firewall and does not host an SVI for
it. This removes the separate access-switch-to-firewall cable and frees the second
Gigabit uplink on each access switch.

**Consequence for device selection.** At least one 802.1Q-capable uplink is
required. Sub-stage 3.2.2 sets its design speed at **10 Gbps**, because it
aggregates up to 24 Gigabit access ports and would otherwise present a 24:1
oversubscription ratio. The implementation model provides only 1 Gbps and records
that difference as a limitation.

### A11 — PoE on ports serving access points

**Source:** 2.8.5 places access points on the access switches; the power method is
not specified there.

**Design decision — Power over Ethernet.**

The access point requires power. Two options were considered.

*Local power* means a mains socket adjacent to each access point. It imposes no
requirement on the switch and is the cheaper option in switch terms.

*Power over Ethernet* delivers power through the network cable itself, so a single
cable provides both connectivity and power.

PoE was selected. Access points are normally mounted where radio coverage is best
— ceilings, high on walls, open areas — and these are rarely locations with
convenient mains sockets. Requiring a socket at every access point either
constrains placement to where power exists, which compromises coverage, or
requires electrical work at each location. PoE removes that constraint entirely
and is standard practice for wireless deployments for exactly this reason.

It also simplifies future expansion: adding an access point becomes a matter of
running one cable rather than coordinating a network drop and an electrical
outlet.

**What this accepts.** PoE-capable switches cost more than equivalent non-PoE
models, and the switch must have sufficient **power budget** for the devices it
supplies. With one access point per switch the budget requirement is small, but it
should be confirmed during model selection rather than assumed — a switch may
support PoE on only a subset of its ports, or offer a total budget below what a
higher-power access point draws.

**Scope note.** PoE is a physical-layer characteristic with no representation in
the implementation environment. It is specified here because 3.1 describes the
requirements of the design rather than of the simulation, and it would be a real
purchasing constraint.

## Selection Priority

If no available model satisfies every requirement, these are the ones that cannot
be compromised without breaking the design:

| Priority | Requirements | Consequence if unmet |
|----------|--------------|----------------------|
| **Essential** | A3, A4 | Access points cannot be connected, or VLANs cannot cross the uplink; segmentation fails |
| **Essential** | A9, A10 | Devices cannot physically be connected, VLANs cannot reach the core, or the uplink is constrained to 24:1 oversubscription |
| **Important** | A5, A6, A7, A8 | A documented control or service is lost — VLAN hopping mitigation, rogue device parking, encrypted management, or monitoring |
| **Baseline** | A1, A2 | Satisfied by any managed switch; verify rather than evaluate |
| **Physical** | A11 | Access points require local power instead, constraining their placement |

Any requirement that cannot be met should be recorded as an implementation
limitation in 3.3, with its consequence stated — not silently dropped.
