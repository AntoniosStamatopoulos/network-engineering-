# 3.1.3 Device Requirements — Firewall

Quantity: **1** (§11)

This document specifies what the firewall must be capable of. It does not select a
model — that is 3.3. Each requirement is derived from a decision already made in
Phase 1 or Phase 2, and the derivation is shown so that no requirement rests on
assumption.

The firewall carries more requirements than any other device in the design, for a
structural reason: it is the single policy enforcement point (2.1.3), the boundary
of an untrusted internal zone (DD-2), and the VPN termination point (DD-1). Three
roles converge on one device.

## Derivations

### F1 — Stateful inspection

**Source:** 2.7.4 — *"The firewall performs stateful inspection: when a permitted
connection is established, the response is recognised as belonging to a known
session and allowed automatically."*

This is the most important requirement in the document and the easiest to
overlook, because **no document states it as a requirement**. It is a property the
entire policy assumes.

Sub-stage 2.7.4 continues: *"Rules are therefore written only for the direction
that initiates a connection."* The zone interaction matrix (2.6.3) depends on this
throughout — Z1 → Z5 is permitted while Z5 → Z1 is denied, meaning users may open
connections to servers but servers may not open connections toward users.

**What happens if the firewall is not stateful.** A packet filter evaluates each
packet independently and has no memory of established sessions. Return traffic
would match no rule and be dropped, so every permitted flow would need a second
rule in the reverse direction — which is precisely the initiation right the design
withholds. Sub-stage 2.7.4 states this directly: *"Writing rules in both
directions would grant exactly the initiation right the design intends to
withhold."*

**Consequence for device selection.** A router with access lists is not a
substitute. If a candidate is a packet filter rather than a stateful firewall, the
security model does not degrade — it inverts, because servers and external hosts
gain the ability to initiate inbound connections.

### F2 — At least 4 interfaces

**Source:** 2.1.2 (topology), 2.8.4 (Guest uplink), 2.10.3 (management).

Calculated by counting what attaches to the firewall:

| Interface | Connects to | Source |
|-----------|-------------|--------|
| outside | Edge router | 2.1.2 |
| inside | Core switch | 2.1.2 |
| guest | VLAN 60 handed off by the core at Layer 2 | DD-2, 2.8.4 |
| management | Management access | 2.10.3 |

The guest interface is the one that would be missed by reading a conventional
firewall description. Most designs give a firewall an inside and an outside;
DD-2 adds a third zone terminating on its own interface, so that Guest traffic
reaches the firewall without being routed by the core.

Under the Layer 2 transit decision in 2.8.4, both access switches carry VLAN 60
over their normal core trunks. The core has no VLAN 60 SVI and hands that VLAN to
one dedicated Guest interface on the firewall. Whether that Core→ASA handoff uses
an access port or a tagged trunk/subinterface remains an implementation decision
for 3.4/3.5; it does not change the requirement for one separate Guest zone.

The management interface remains a fourth, separate interface. The Layer 2
transit change does not merge management with the inside interface and does not
alter the management architecture or addressing.

### F3 — Ordered rule-based policy, first-match

**Source:** 2.7.3 — the firewall policy, ten rules.

The requirement is not simply "supports rules" but that rules are evaluated
**top-to-bottom, stopping at the first match**. Sub-stage 2.7.3 makes the
dependency explicit when describing rules 1 and 2:

> *"Reversing these two rules would silently break external name resolution. The
> DNS server would match rule 2 first and be denied, and rule 1 would never
> execute."*

**Consequence for device selection.** The evaluation order must be both
deterministic and controllable by the administrator. A device that reorders rules
internally, or evaluates by specificity rather than position, would produce
behaviour the policy does not describe — and the failure would be silent, which is
the worst kind.

### F4 — Per-rule logging

**Source:** 2.7.6 (logging policy); 2.7.3 (the Log column).

Seven of the ten firewall rules are marked for logging and three are not. Routine
user and Guest Internet traffic is deliberately excluded because, as 2.7.6 states,
high-volume logging would obscure meaningful entries.

**Consequence for device selection.** Logging must be configurable **per rule**. A
device offering only global logging — all matches or none — cannot implement the
selective policy, and would force a choice between losing visibility of denials
and burying them in routine traffic.

### F5 — PAT (NAT overload)

**Source:** 2.5.6 — *"Method: PAT (NAT overload) — many internal addresses share
one public address, distinguished by port number."*

Appropriate because the design assumes a single public address from the ISP and
requires no inbound connections: §7 denies Internet-to-internal by default, and
2.5.6 records that no static translations are defined because no internal service
is published externally.

### F6 — Separate translation contexts

**Source:** 2.5.6 — *"Separate translation contexts for corporate and Guest
traffic."*

The stated purpose is that Guest activity remains identifiable in translation and
firewall logs, and that different treatment — rate limiting, or a separate public
address — can be introduced later without redesign.

**Note on feasibility.** This requirement is likely satisfied by the architecture
rather than by a special capability. Translation is normally configured per
interface pair, and Guest already has its own interface (F2), so `guest → outside`
and `inside → outside` are naturally distinct translations. What should be
verified during implementation is whether the resulting logs carry enough detail
to distinguish the two in practice.

### F7 — IPsec VPN termination

**Source:** 2.9.2 (termination on the firewall, DD-1); 2.9.6 (IPsec selected).

Sub-stage 2.9.2 explains why termination belongs here: the firewall is already the
policy enforcement point, so remote traffic is subject to the same controls as all
other traffic by construction. It also names the failure this avoids — terminating
VPN behind the enforcement point would let remote users bypass the policy that
applies to everyone else, and remote users are precisely the population arriving
from an untrusted network.

Sub-stage 2.9.6 selects IPsec and notes it is *"supported in the implementation
environment"*, so this requirement is not expected to present difficulty. PPTP is
explicitly excluded as cryptographically broken.

### F8 — At least 2 VPN address pools

**Source:** 2.9.3.

```text
Z8 VPN-FINANCE → 10.0.201.0/24
Z9 VPN-IT      → 10.0.202.0/24
```

Two distinct pools are required, not one pool subdivided.

### F9 — Per-pool access policy

**Source:** 2.9.3 and 2.7.3 (rules 7 and 8).

This is the requirement that implements §9, and it is worth stating why the two
preceding requirements exist at all. Sub-stage 2.9.3:

> *"With separate pools, the address is the identity."*

The firewall has no knowledge of user identity (2.6.1 places identity-based access
out of scope), so the only available means of distinguishing a remote Finance user
from a remote IT user is the address they were assigned. Firewall rules 7 and 8
then apply different scope to each:

| Rule | Source | Reaches |
|-----:|--------|---------|
| 7 | VPN-FINANCE pool | VLAN 20; DNS and Web servers only |
| 8 | VPN-IT pool | VLANs 10–50 and 99, including management |

**Consequence if unmet.** This is the requirement whose failure carries the
greatest security consequence. If the firewall cannot apply different policy to
different pools, remote Finance users would receive the same access as remote IT —
which includes the management plane. §9 states that remote users *"should not
receive unrestricted access"*, and a single shared policy would violate it
directly.

Should the implementation environment prove unable to support two tunnel groups
with distinct pools, the correct response is to implement **one** VPN and document
that the second was designed but not implemented — not to implement both with
identical access. A missing capability is preferable to a capability present with
wrong permissions.

### F10 — Certificate-based authentication

**Source:** 2.9.5 — *"Certificate-based authentication combined with user
credentials."*

Sub-stage 2.9.5 records this as a substitute for multi-factor authentication,
which the design requires but does not implement. Its honest assessment is
retained here:

> A certificate is stronger than credentials alone, because an attacker needs a
> machine with the certificate installed rather than only a stolen password. It is
> weaker than true multi-factor authentication, because a certificate is a file
> and files can be copied.

**Consequence if unmet.** If certificate authentication is unavailable in the
implementation environment, authentication falls back to credentials alone. This
is a **second** level of degradation and must be recorded as such:

```text
Design requirement:  MFA — two factors, one of them non-copyable
Documented (2.9.5):  Certificate + credentials — two factors, both copyable
If unavailable:      Credentials alone — one factor
```

Presenting only the final state without the two steps above would misrepresent the
design as having ignored remote-access security.

### F11 — Full tunnel mode

**Source:** 2.9.4 — *"Selected: full tunnel. All traffic from a connected client
passes through the tunnel, including traffic destined for the Internet."*

The firewall must be able to push a default route to connected clients rather than
only routes for corporate networks.

Sub-stage 2.9.4 gives the reasoning: split tunnelling would create a category of
traffic from an authenticated corporate session that passes through no enforcement
point, which is an exception to the principle applied everywhere else in the
design. It also notes the dual-attachment risk — a split-tunnelled client is
attached to the Internet and the corporate network simultaneously, so a machine
compromised from the Internet side already holds an open path inward.

### F12 — DHCP server for VLAN 60

**Source:** inferred from 2.4.3 and 2.4.7.

**No document states that the firewall runs DHCP.** The requirement follows from
combining two facts:

- 2.4.3 places the Guest gateway on the **firewall interface** rather than the
  core: `| 60 | GUEST | 10.0.60.0/24 | 10.0.60.1 | Firewall interface |`
- 2.4.7 defines a DHCP scope for VLAN 60: pool `.100–.199`, public DNS resolver,
  2-hour lease

DHCP clients broadcast to discover a server, and broadcasts do not cross routed
boundaries. Since the only routed interface in VLAN 60 belongs to the firewall,
the firewall must serve that scope — nothing else is present in the broadcast
domain to answer.

The scope parameters carry two deliberate differences from the corporate scopes,
both following from Guest's untrusted status (2.4.7): a **public DNS resolver**
rather than the internal server, because the internal server sits in VLAN 50 which
Guest has no path to; and a **2-hour lease** rather than 8, because visitors leave
and addresses should return to the pool promptly.

### F13 — SSH and HTTPS management

**Source:** 2.10.3 — *"Firewall | SSH (TCP 22) / HTTPS (TCP 443) | IT management
workstations | HTTP disabled."*

Both are listed because firewalls are commonly administered through a web
interface as well as a command line. The requirement is that **both encrypted
forms** are available and that their unencrypted equivalents — Telnet and HTTP —
can be disabled rather than merely left unconfigured.

Sub-stage 2.10.3 treats unencrypted management as a defect rather than an option:
*"unencrypted management protocols are a defect, and their availability on a
device is itself a risk even when they are not used."*

### F14 — SNMPv3, Syslog, NTP

**Source:** 2.10.5, 2.10.6, 2.10.7.

- **SNMPv3** — 2.10.5 rejects v1 and v2c because the community string travels in
  clear text, and disables SNMP write access so that configuration changes occur
  only through authenticated, logged SSH sessions
- **Syslog** to 10.0.50.30 at severity level 6 (2.10.6)
- **NTP client**, synchronising from the edge router (2.10.7)

The Syslog requirement carries particular weight for this device. The firewall
generates the security-relevant events the monitoring design exists to capture —
denied traffic, VPN sessions, policy matches — and 2.10.6 notes that logs held
locally on a compromised device can be deleted, while messages already forwarded
to a collector cannot.

### F15 — Static routes

**Source:** 2.5.4 — the firewall routing table.

```text
10.0.0.0/16  →  10.0.254.1   (core)
0.0.0.0/0    →  10.0.254.6   (edge router)
```

A single summarised entry covers every internal VLAN rather than seven separate
routes — a direct consequence of the hierarchical addressing chosen in 2.4, and
the same property that will allow a branch office to be added as one further route
rather than several.

## Requirements to Verify Early

Four requirements should be confirmed against the implementation environment
before configuration begins, because discovering a gap after the network is built
is more expensive than discovering it now. These are noted as **unverified**
rather than unsupported — the environment's current capabilities are not assumed
here.

| Requirement | Why it warrants early verification | If unavailable |
|-------------|-----------------------------------|----------------|
| **F9** per-pool policy | Carries §9 entirely; failure means remote Finance gains management access | Implement one VPN only, and document the second as designed but not implemented |
| **F10** certificates | Requires PKI-like handling that simulations often omit | Fall back to credentials, recording both levels of degradation (see F10) |
| **F14** SNMPv3 | Affects **every** device (C10, A8, E5), not only the firewall | Record as a limitation across the estate; community string exposure is the consequence |
| **F6** log granularity | Translation separation is likely; log detail may not be | Functionality retained, visibility reduced |

The handling principle is unchanged from earlier sub-stages: the design is not
rewritten to match the tool. Where a capability is unavailable, it is recorded in
3.3 as an implementation limitation with its consequence stated — the same
treatment already applied to multi-factor authentication (2.9.5), dynamic wireless
VLAN assignment (2.8.3), and dynamic routing (2.5.2).

## Selection Priority

| Priority | Requirements | Consequence if unmet |
|----------|--------------|----------------------|
| **Fundamental** | F1 | The security model inverts rather than degrades; servers and external hosts gain inbound initiation rights |
| **Essential** | F2, F3, F5, F15 | Devices cannot be connected, rule order is unreliable, internal hosts cannot reach the Internet, or traffic has no path |
| **Essential** | F9 | §9 is violated — remote Finance would reach the management plane |
| **Important** | F4, F7, F8, F11, F12 | A documented service or control is lost; the design functions but a requirement is unimplemented |
| **Important** | F13, F14 | Management or monitoring is degraded, or exposed over unencrypted protocols |
| **Documented substitute** | F10 | Already a substitute for MFA; its loss is a second degradation and must be recorded as such |
| **Visibility** | F6 | Function retained, log clarity reduced |

F1 is listed above "essential" deliberately. Every other unmet requirement removes
something. An unmet F1 **adds** something — connection-initiation rights that the
policy was written to withhold — and does so without any visible failure.
