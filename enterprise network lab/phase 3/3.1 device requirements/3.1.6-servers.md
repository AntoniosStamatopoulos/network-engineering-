# 3.1.6 Device Requirements — Servers

Quantity: **3** (§3) — DNS, Web, Monitoring/Syslog. A File Server is planned as a
future addition.

This document specifies what each server must be capable of, and — for the first
time in this phase — what each must **not** be capable of. It does not select
software or operating systems; those are systems design questions. It records what
the network design requires of these machines.

Unlike the infrastructure devices covered in 3.1.1–3.1.5, the three servers do not
share a common requirement set. Their roles differ substantially, so the
requirements are presented as **common** and **per server**.

## Derivations — Common Requirements

### S5 — Static address

**Source:** 2.4.6 — the static assignment table.

```text
DNS Server                  10.0.50.10
Web Server                  10.0.50.20
Monitoring / Syslog Server  10.0.50.30
File Server (future)        10.0.50.40
```

Sub-stage 2.4.6 states the reasoning directly: *"other systems point at them...
An address that other systems depend on must not change."*

The dependency is concrete and appears in several places. Every DHCP scope
distributes `10.0.50.10` as the DNS server (2.4.7). Every infrastructure device
forwards Syslog to `10.0.50.30` (2.10.6). Core ACL rules 3, 4 and 6 reference
these addresses explicitly (2.7.2).

**The failure mode is misleading.** If a server's address changed, the symptom
would present as the service malfunctioning rather than as an addressing problem —
clients would report that name resolution had stopped working, not that the DNS
server had moved.

**Consequence for implementation.** Manual static configuration rather than DHCP
reservation. A reservation would work, but it would make these servers dependent
on the DHCP service, and the DNS server in particular must function when other
services do not.

### S6 — NTP client

**Source:** 2.10.7, 2.6.5 — internal devices synchronise from the edge router.

Common to all three, but **most consequential for DS3**. Sub-stage 2.10.7 explains
why: log correlation depends on devices agreeing about time, and a collector whose
own clock disagrees with the devices reporting to it produces records that cannot
be ordered reliably.

A monitoring server with an inaccurate clock does not fail visibly. It continues
collecting, and the defect only becomes apparent during an investigation — which
is the worst possible moment to discover it.

### S7 — SSH server for administration

**Source:** 2.7.2 rule 5.

```text
| 5 | VLAN 40 (IT) | VLAN 50 | SSH 22 | permit | ✓ |
```

This is distinct in kind from the rules permitting user access. Rules 3 and 4
permit **use** of a service — DNS queries, web pages. Rule 5 permits
**administration** of the host.

The distinction matters because they are different privilege levels arriving from
different sources. A policy that permitted users to reach VLAN 50 without
specifying a service would grant administrative access at the same time, leaving
credentials as the only remaining barrier.

Rule 5 is logged; rules 3 and 4 are not (2.7.6). Administrative access to a
protected host is worth recording; routine service use is not.

### S9 — SNMP agent, v3

**Source:** inferred from 2.7.2 rule 6 and 2.10.4.

**No document states that servers run an SNMP agent.** Sub-stage 2.10.5 describes
SNMP configuration for infrastructure devices without listing servers explicitly.
The requirement is inferred from two facts.

Core ACL rule 6 permits infrastructure devices to reach the monitoring server:

```text
| 6 | Infrastructure devices | 10.0.50.30 | SNMP 162, Syslog UDP 514 | permit |
```

And 2.10.4 lists **server availability** among the metrics the monitoring design
covers, with performance monitored by SNMP polling.

Monitoring a server's CPU, memory and interface state requires an agent on that
server. Without one, only ICMP reachability can be established — which answers
whether the machine responds, not whether it is functioning.

**Version 3 specifically**, for the reason given in 2.10.5: v1 and v2c transmit
their community string in clear text.

**Recommended follow-up.** Sub-stage 2.10.5 should state explicitly that servers
are included in the SNMP regime, so that a future reader does not have to repeat
this inference. Recorded here rather than changed silently — the same treatment
applied to access points in 3.1.5 (W11).

## Derivations — DS1, DNS Server

### S1a — Authoritative for internal records

**Source:** 2.6.4.

> *"An internal DNS server continues to resolve its own records without any
> Internet access — internal name resolution is unaffected."*

The server holds records for internal systems and answers queries for them
directly. This function is independent of external connectivity, which is the
point 2.6.4 makes: losing upstream access degrades the service rather than
breaking it.

### S1b — Forwarding of external queries

**Source:** 2.6.4.

> *"What is lost is the resolution of **external** names, because the server does
> not hold those records and must query an upstream resolver to obtain them."*

When a client requests a name the server is not authoritative for, it must forward
the query rather than fail. Without forwarding, every user VLAN would be permitted
Internet access (firewall rule 4) while being unable to resolve any external name —
a state in which the network appears broken despite functioning correctly.

### S1c — Configurable upstream forwarder list

**Source:** 2.7.3 rule 1.

```text
| 1 | 10.0.50.10 (DNS) | Approved upstream resolvers | UDP/TCP 53 | permit | ✓ |
```

The firewall rule constrains the **destination**, not merely the protocol.
Sub-stage 2.7.3 explains why: permitting port 53 to any address leaves a viable
data-exfiltration channel, since a compromised DNS server could encode data in
queries directed at a nameserver the attacker controls.

That control is only effective if the DNS server itself is configured with a
defined forwarder list. A server that queries root servers directly, or that
accepts an arbitrary forwarder configuration, would either fail against the
firewall rule or work around the control it implements.

**Consequence for implementation.** The forwarder addresses must be recorded in
the configuration documentation, since they appear in two places — the server
configuration and the firewall rule — and must match.

### S1d — Serves queries from four VLANs

**Source:** 2.4.7 — the DHCP scopes.

All four corporate scopes distribute `10.0.50.10` as the DNS server. The server
therefore accepts queries from VLANs 10, 20, 30 and 40.

**VLAN 60 is excluded.** Guest clients receive a public resolver instead (2.4.7),
because the internal DNS server sits in VLAN 50 and Guest has no path to it. This
is not an oversight: pointing Guest clients at the internal server would either
fail, or require opening a path the design deliberately does not have.

The DNS server should therefore not be configured to accept queries from VLAN 60 —
it will not receive any, and configuring for them would suggest a path exists.

## Derivations — DS2, Web Server

### S2a — HTTP and HTTPS

**Source:** 2.7.2 rule 4.

```text
| 4 | VLAN 10, 20, 30, 40 | 10.0.50.20 (Web) | TCP 80, 443 | permit | — |
```

Both ports are permitted. HTTPS is the appropriate protocol for any content
warranting protection; HTTP remains permitted, which is worth noting as a
deliberate choice rather than an omission — if all content were to be served over
HTTPS, rule 4 could be narrowed to port 443 alone and the policy would be tighter.

This is the only requirement specific to DS2. The web server is the simplest of
the three, and its requirement list reflects that.

## Derivations — DS3, Monitoring / Syslog Server

DS3 carries more requirements than the other two combined, because it performs
three distinct collection functions.

### S3a — Syslog collector, UDP 514

**Source:** 2.10.6.

The collector receives messages from every infrastructure device at severity level
6 (2.10.6). It must accept remote Syslog over UDP 514 and store what it receives.

Sub-stage 2.10.6 gives the reason central collection matters: logs held locally on
a device can be deleted by an attacker who compromises it, while messages already
forwarded are beyond that reach.

### S3b — SNMPv3 manager, polling UDP 161

**Source:** 2.10.5, 2.10.4.

DS3 acts as the **manager** in the SNMP model, querying agents on infrastructure
devices for CPU, memory and interface utilisation (2.10.4).

Note the direction: this is **outbound** from DS3 toward infrastructure devices,
which is the reverse of most server traffic. Core ACL rule 6 covers devices
reporting inward; polling travels the other way.

### S3c — Receives SNMP traps, UDP 162

**Source:** 2.10.5.

Traps are the event-driven half of SNMP: devices send them unprompted when a
condition occurs, rather than waiting to be polled.

Sub-stage 2.10.4 explains why both mechanisms are needed. Polling establishes a
baseline and confirms devices are alive, but has detection latency — a fault
occurring just after a poll is not seen until the next. Traps report immediately
but say nothing about a device that has failed completely.

### S3d — ICMP polling for availability

**Source:** 2.10.4, and §10 which requires *"ping / basic availability checks"*.

The simplest of the three mechanisms and the one that answers the most basic
question: is the device reachable at all.

### S3e — Log storage and retention

**Source:** 2.10.6.

Storage is implied rather than stated as a figure. Sub-stage 2.10.6 notes that
logs are only useful for as long as they are kept, and that incidents are
frequently discovered weeks after they begin.

**No retention period is defined in Phase 2.** This is a gap worth recording: a
retention period chosen deliberately is preferable to one that emerges from
whatever the storage happens to hold. The decision belongs to the implementation
or operations phase, but it should be a decision rather than a default.

## The Negative Requirement

### S8 — DS2 and DS3 have no outbound Internet access

**Source:** 2.7.3 rule 2, with the reasoning in 2.6.4.

```text
| 2 | VLAN 50 (Servers) | any | any | deny | ✓ |
```

This is the first **constraint** rather than capability in this phase. Every other
entry in 3.1 states what a device must be able to do; this states what two of the
servers must not do.

**Only DS1 is exempt**, and narrowly: rule 1 permits it DNS queries to approved
resolvers and nothing else. DS2 and DS3 have no permit rule at all and fall
through to rule 2.

### Why it is stated as a requirement

The absence of a permit rule is the mechanism, so nothing in the firewall
configuration will mention DS2 or DS3. Without recording it here, the constraint
would exist only as an absence — and absences are not reviewable.

It also has an implementation consequence that a firewall rule cannot express: the
servers must **function** without outbound access. Software that expects to reach
update repositories, licence servers, or telemetry endpoints during normal
operation will behave unpredictably when those connections fail.

### The operational consequence

Sub-stage 2.6.4 records the trade-off honestly:

> *This removes an outbound path but introduces an operational risk: manual
> patching depends on a process being followed. An unpatched server is a greater
> exposure than a server with narrowly controlled outbound access.*

This produces a **procedural requirement** derived from a network constraint:

```text
IT downloads and verifies updates
        ↓
controlled transfer to the server
        ↓
update applied on a defined schedule
```

Sub-stage 2.6.4 accepts the approach **on condition** that this procedure is
documented and performed on a defined schedule. That condition is a requirement of
the design, not an optional practice, and it belongs in the operational
documentation produced alongside the build.

At production scale the approach would differ — an internal update repository
would serve many servers without giving each one Internet access. For three
servers it is proportionate and keeps the security policy legible.

## Selection and Implementation Priority

| Priority | Requirements | Consequence if unmet |
|----------|--------------|----------------------|
| **Essential** | S5 | Every reference to a server address breaks; failures present as service malfunctions |
| **Essential** | S1a, S1b | Name resolution fails internally, or externally for every user VLAN |
| **Essential** | S2a, S3a | The service the server exists to provide does not function |
| **Important** | S1c | The destination constraint in firewall rule 1 cannot be enforced from the server side |
| **Important** | S3b, S3c, S3d | A monitoring category is lost; §10 is partially unmet |
| **Important** | S6 | Log timestamps cannot be correlated — the defect surfaces during investigation |
| **Important** | S7, S9 | Servers cannot be administered or monitored consistently with the rest of the estate |
| **Constraint** | S8 | Two servers gain an outbound path the design deliberately withholds |
| **Open** | S3e | Retention period undefined; should be decided rather than defaulted |

S6 is placed above its apparent importance for the reason given in its derivation:
an inaccurate clock on the monitoring server causes no visible failure and is
discovered only when the logs are needed.
