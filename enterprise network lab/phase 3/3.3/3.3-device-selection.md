# 3.3 Device Selection

This sub-stage selects specific models for each device type, evaluated against the
requirements established in 3.1 and the specifications in 3.2.

Selection is made from the catalogue available in the implementation environment
(Cisco Packet Tracer), as established in the Phase 3 approach. A constrained
catalogue is not an artificial limitation: in practice, selection is routinely
bounded by an approved vendor list, an existing platform standard, a budget
ceiling, or a support contract. What matters is that selection follows from
requirements rather than preference.

---

## 3.3.1 Method

For each device type:

1. List the candidates the catalogue offers
2. Evaluate each against the requirement list from 3.1
3. Select, with the reasoning stated
4. Record any requirement the selection does not meet, with its consequence

Step 4 is the one that matters most. A gap recorded with its consequence is a
documented limitation; a gap left unrecorded is a defect nobody will notice until
it matters.

**A note on certainty.** Device capabilities in a simulation environment differ
from the physical products they represent, and they vary between versions of the
software. Where a requirement depends on a capability that cannot be confirmed
from the catalogue alone, it is marked **to verify** rather than asserted either
way. These are resolved during implementation, not by assumption here.

### The significant finding

The catalogue includes **ASA firewalls**. This resolves the largest open risk in
Phase 3.

Requirement F1 — stateful inspection — is the one requirement whose absence would
not degrade the security model but **invert** it (3.1.3). Had the catalogue offered
no firewall, the perimeter would have had to be built from a router and access
lists, which is a packet filter: return traffic would match no rule, every
permitted flow would need a reverse rule, and servers and external hosts would gain
the ability to initiate inbound connections the policy was written to withhold.

The availability of a stateful firewall platform removes that outcome.

### Why 3650 over 3560

Both are Layer 3 and both satisfy C1. The 3650 is the later platform, which
matters for C14: OSPF support is a future requirement, and a newer platform is more
likely to carry forward.

The industrial models (IE series) were excluded not on capability but on fit —
they are hardened for temperature, vibration and electrical conditions that an
office environment does not present, and that hardening is what they cost extra
for.

### C13 — the shortfall

Sub-stage 3.2.2 specified two 10 Gbps ports for the access uplinks, giving a 2.4:1
oversubscription ratio rather than 24:1.

**The catalogue appears to offer no switch with 10 Gbps interfaces.** This is
recorded as an implementation limitation in 3.3.9 rather than resolved by revising
the design: the reasoning in 3.2.2 stands on its own, and a simulation constraint
is not a reason to specify an uplink at the edge of acceptable oversubscription in
a real deployment.

The port **count** is satisfied — 24 ports against a requirement of 9. The ninth
port accounts for the additional Core→ASA Guest handoff introduced by the VLAN 60
Layer 2 transit decision.

documented decision. The 2960 is the correct choice because the requirements say
so.

directly.

The 5506 is also the later platform, which matters for the VPN requirements
(F7–F11) where capability differences between generations are most likely.

E6 and E7 are both future requirements, and 3.1.4 explains why they belong in a

reconfiguration when the trigger arrives.

makes it the more likely to support those capabilities when they are configured.
The 2911 would also satisfy every present requirement and is common in teaching
material; it was not selected because there is no advantage in choosing the older
platform when both are available.

The third interface is useful beyond the two E1 requires: it provides a management
connection without consuming one of the two data interfaces.

## 3.3.7 Wireless

**Design target: two autonomous 802.11ac access points**  
**Packet Tracer implementation: Cisco 3504 WLC × 1 + LAP-PT × 2**

### Candidates

| Model | Architecture | Assessment |
|-------|--------------|------------|
| **AP-PT-AC** | Autonomous | Matches the Phase 2 design, but the Packet Tracer model exposes only one SSID |
| AP-PT-N | Autonomous | 802.11n only; older standard |
| AP-PT, AP-PT-A | Autonomous | Older standards |
| 3702i | Autonomous or lightweight | Viable alternative |
| **LAP-PT + 3504** | Controller-based | **Selected for implementation** — supports the five-WLAN configuration and per-WLAN VLAN mapping |
| Meraki | Cloud-managed | Requires a cloud management model this design does not have |

### Evaluation against 3.1.5

| # | Requirement | Met | Note |
|---|-------------|:---:|------|
| W1 | **At least 5 simultaneous SSIDs** | ✓ | Verified on the 3504 WLC |
| W2 | Per-SSID VLAN assignment | ✓ | Verified: the WLAN interface/group field mapped to `vlan10` |
| W3 | 802.1Q trunk uplink | implementation differs / configure | In the design each autonomous AP trunks to its switch; in the lab the WLC must carry the WLAN VLANs and the LAPs use their controller path. Exact port configuration remains TBD |
| W4 | WPA2-PSK | ✓ | |
| W5 | Open SSID with captive portal | **verify** | Captive portal frequently requires a controller |
| W6 | Client isolation per SSID | **verify** | Often global-only — see 3.1.5 |
| W7 | Per-client bandwidth limiting | **verify** | |
| W8 | PoE powered | **n/a** | Not modelled |
| W9 | WPA2-Enterprise (future) | **verify** | |
| W10 | Configurable native VLAN | **verify** | Applies to the WLC trunk in the lab implementation |
| W11 | SSH, SNMPv3, Syslog, NTP | **verify** | Centralised on the controller in the lab implementation |

### Why 802.11ac

Sub-stage 3.2.4 specified Wi-Fi 5 as the minimum and dual-band as mandatory. The
AP-PT-AC is the 802.11ac option; AP-PT-N implements the earlier 802.11n standard.

Dual-band matters specifically here: with five SSIDs broadcasting (W1), having both
bands available is what makes the airtime cost tolerable. Single-band operation
would concentrate all five SSIDs into one band and compound a cost already
acknowledged as above guidance in 2.8.3.

### Implementation resolution

The Phase 2 design decision remains unchanged: with only two access points, an
autonomous architecture avoids an otherwise unnecessary controller and its single
point of failure. Packet Tracer's AP-PT-AC model, however, exposes only one SSID,
so it cannot implement the five SSIDs required by W1.

The lab therefore uses the controller-based path: one 3504 WLC and two LAP-PTs.
W1 was verified by creating five WLANs. W2 was verified by associating a WLAN
with a dynamic interface — the `Interface/Interface Group(G)` field displayed
`vlan10`. This is an implementation limitation and not a reversal of the real
design choice.

The change adds one device and one physical connection to the core and makes the
WLC an implementation-only wireless SPOF. The exact WLC/LAP management VLAN,
addresses, and port modes have not been selected here; they remain explicitly TBD
in 3.4 and 3.5.

DS1 and DS2 require services that simulation environments commonly provide — DNS
and HTTP are standard.

reception, SNMP management, and log storage. If the environment does not provide
them, the monitoring design in 2.10 can be **specified but not demonstrated**.

That would be a significant limitation and is recorded in 3.3.10.

## 3.3.9 Implementation Limitations

Requirements the selection does not satisfy, with their consequences. The design
is not revised to match the environment; the difference is recorded.

| Requirement | Design | Implementation | Consequence |
|-------------|--------|----------------|-------------|
| **C13, A10** | 10 Gbps access uplinks | 1 Gbps | Oversubscription of 24:1 rather than 2.4:1. In a real deployment this would constrain the access layer as user count grows and would require switch replacement — which is why 3.2.2 specified 10 Gbps. In simulation, traffic volume does not exercise the limit |
| **A11, W8** | PoE+ (802.3at) | Not modelled | Access points function regardless. The specification stands as a purchasing requirement; it cannot be demonstrated |
| **W1, W2, W11** | Two autonomous APs with five SSIDs and static per-SSID VLAN assignment | One 3504 WLC and two LAP-PTs | The Packet Tracer autonomous AP exposes only one SSID. The controller implementation satisfies W1 and W2 but adds one core connection and a wireless SPOF; it does not alter the real design target |
| **C10, A8, F14, E5, S9** | SNMPv3 | Possibly v2c only — **to verify** | If only v2c is available, the community string is transmitted in clear text on every device. This is an **estate-wide** limitation rather than a per-device one, and should be recorded once |

The SNMP entry is flagged for early verification because it affects five
requirements across several device types. Confirming it first avoids recording the
same limitation five times, or discovering it after configuration is underway.

## 3.3.10 To Verify at Implementation

Requirements whose satisfaction cannot be determined from the catalogue. Listed in
order of consequence.

| Requirement | Question | If unavailable |
|-------------|----------|----------------|
| **F9** | Can the firewall apply different policy to two VPN pools? | Implement one VPN only and document the second as designed but not implemented. **Do not implement both with identical access** — remote Finance would gain management-plane access, violating §9 directly |
| **S3a, S3b, S3c** | Does the server provide Syslog collection and SNMP management? | The monitoring design is specified but not demonstrated; §10 is partially unmet |
| **C10 and related** | Is SNMPv3 available, or only v2c? | Estate-wide limitation; record once |
| **F10** | Is certificate-based authentication available? | Falls back to credentials alone — a **second** level of degradation below the substitute already documented in 2.9.5, and both steps must be recorded |
| **W5, W6, W7** | Captive portal, per-SSID isolation, rate limiting | Guest controls in 2.8.6 are partially unimplemented |
| **F6, C7, F4** | Logging and translation granularity | Function retained, visibility reduced |

### The handling principle

Unchanged from earlier sub-stages: **the design is not rewritten to match the
tool**. Where a capability is unavailable, it is recorded with its consequence
stated.

The F9 guidance deserves emphasis because it is the one case where the wrong
response is worse than the limitation. A missing capability is an unimplemented
feature; a capability present with wrong permissions is a security failure that
looks like success.
