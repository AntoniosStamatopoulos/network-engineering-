# 3.1.6 Απαιτήσεις συσκευής — Servers

Ποσότητα: **3** (§3) — DNS, Web, Monitoring/Syslog. Ένας File Server έχει
προγραμματιστεί ως μελλοντική προσθήκη.

Το παρόν έγγραφο καθορίζει τις δυνατότητες που πρέπει να διαθέτει κάθε server
και — για πρώτη φορά σε αυτή τη φάση — τι **δεν** πρέπει να μπορεί να κάνει.
Δεν επιλέγει software ή operating systems· αυτά είναι ζητήματα systems design.
Καταγράφει τι απαιτεί ο network design από αυτά τα μηχανήματα.

Σε αντίθεση με τις infrastructure devices που καλύπτονται στα 3.1.1–3.1.5, οι
τρεις servers δεν μοιράζονται ένα κοινό σύνολο απαιτήσεων. Οι ρόλοι τους
διαφέρουν σημαντικά, οπότε οι απαιτήσεις παρουσιάζονται ως **κοινές** και **ανά
server**.

## Παραγωγή απαιτήσεων — Κοινές απαιτήσεις

### S5 — Static address

**Πηγή:** 2.4.6 — ο πίνακας static assignment.

```text
DNS Server                  10.0.50.10
Web Server                  10.0.50.20
Monitoring / Syslog Server  10.0.50.30
File Server (future)        10.0.50.40
```

Το υποστάδιο 2.4.6 εξηγεί άμεσα τη λογική: *«άλλα συστήματα δείχνουν σε
αυτούς... Μια διεύθυνση από την οποία εξαρτώνται άλλα συστήματα δεν πρέπει να
αλλάζει.»*

Η εξάρτηση είναι συγκεκριμένη και εμφανίζεται σε πολλά σημεία. Κάθε DHCP scope
διανέμει το `10.0.50.10` ως DNS server (2.4.7). Κάθε infrastructure device
προωθεί Syslog στο `10.0.50.30` (2.10.6). Οι core ACL rules 3, 4 και 6 αναφέρουν
ρητά αυτές τις διευθύνσεις (2.7.2).

**Η μορφή της αστοχίας είναι παραπλανητική.** Αν άλλαζε η διεύθυνση ενός
server, το σύμπτωμα θα εμφανιζόταν ως δυσλειτουργία της υπηρεσίας και όχι ως
πρόβλημα addressing — οι clients θα ανέφεραν ότι σταμάτησε το name resolution,
όχι ότι μετακινήθηκε ο DNS server.

**Συνέπεια για την υλοποίηση.** Χειροκίνητο static configuration αντί για DHCP
reservation. Μια reservation θα λειτουργούσε, αλλά θα έκανε τους servers να
εξαρτώνται από την DHCP service, και ειδικά ο DNS server πρέπει να λειτουργεί
όταν οι άλλες services δεν λειτουργούν.

### S6 — NTP client

**Πηγή:** 2.10.7, 2.6.5 — οι εσωτερικές συσκευές συγχρονίζονται από τον edge
router.

Η απαίτηση είναι κοινή και για τους τρεις, αλλά **με τη μεγαλύτερη συνέπεια για
τον DS3**. Το υποστάδιο 2.10.7 εξηγεί γιατί: η συσχέτιση logs εξαρτάται από τη
συμφωνία των συσκευών ως προς τον χρόνο και ένας collector του οποίου το ρολόι
διαφέρει από τα devices που του αναφέρουν γεγονότα παράγει records που δεν
μπορούν να ταξινομηθούν αξιόπιστα.

Ένας monitoring server με ανακριβές ρολόι δεν αποτυγχάνει εμφανώς. Συνεχίζει να
συλλέγει δεδομένα και η αδυναμία γίνεται αντιληπτή μόνο κατά τη διερεύνηση — τη
χειρότερη δυνατή στιγμή για να ανακαλυφθεί.

### S7 — SSH server για administration

**Πηγή:** κανόνας 5 του 2.7.2.

```text
| 5 | VLAN 40 (IT) | VLAN 50 | SSH 22 | permit | ✓ |
```

Αυτό διαφέρει ως προς το είδος από τους κανόνες που επιτρέπουν πρόσβαση χρηστών.
Οι κανόνες 3 και 4 επιτρέπουν **χρήση** μιας service — DNS queries, web pages. Ο
κανόνας 5 επιτρέπει **administration** του host.

Η διάκριση έχει σημασία επειδή πρόκειται για διαφορετικά επίπεδα privilege που
έρχονται από διαφορετικές πηγές. Μια policy που επέτρεπε στους users να φτάνουν
το VLAN 50 χωρίς να καθορίζει service θα παραχωρούσε ταυτόχρονα administrative
access, αφήνοντας τα credentials ως το μόνο υπόλοιπο εμπόδιο.

Ο κανόνας 5 καταγράφεται, ενώ οι κανόνες 3 και 4 όχι (2.7.6). Η administrative
πρόσβαση σε προστατευμένο host αξίζει να καταγράφεται· η συνηθισμένη χρήση μιας
service όχι.

### S9 — SNMP agent, v3

**Πηγή:** συμπέρασμα από τον κανόνα 6 του 2.7.2 και το 2.10.4.

**Κανένα έγγραφο δεν δηλώνει ότι οι servers εκτελούν SNMP agent.** Το υποστάδιο
2.10.5 περιγράφει SNMP configuration για infrastructure devices χωρίς να
αναφέρει ρητά τους servers. Η απαίτηση προκύπτει από δύο δεδομένα.

Ο κανόνας 6 του core ACL επιτρέπει σε infrastructure devices να φτάσουν τον
monitoring server:

```text
| 6 | Infrastructure devices | 10.0.50.30 | SNMP 162, Syslog UDP 514 | permit |
```

Και το 2.10.4 περιλαμβάνει τη **διαθεσιμότητα server** στα metrics που καλύπτει
ο monitoring design, με performance monitoring μέσω SNMP polling.

Η παρακολούθηση CPU, memory και interface state ενός server απαιτεί agent σε
εκείνον τον server. Χωρίς agent μπορεί να επιβεβαιωθεί μόνο η ICMP reachability
— αν απαντά το μηχάνημα — όχι αν λειτουργεί σωστά.

**Ειδικά η έκδοση 3**, για τον λόγο του 2.10.5: τα v1 και v2c μεταδίδουν το
community string σε plaintext.

**Προτεινόμενη συνέχεια.** Το υποστάδιο 2.10.5 πρέπει να δηλώσει ρητά ότι οι
servers περιλαμβάνονται στο SNMP regime, ώστε μελλοντικός αναγνώστης να μη
χρειαστεί να επαναλάβει αυτό το συμπέρασμα. Καταγράφεται εδώ αντί να αλλάξει
σιωπηρά — η ίδια μεταχείριση εφαρμόστηκε στα access points στο 3.1.5 (W11).

## Παραγωγή απαιτήσεων — DS1, DNS Server

### S1a — Authoritative για internal records

**Πηγή:** 2.6.4.

> *«Ένας internal DNS server συνεχίζει να επιλύει τα δικά του records χωρίς
> καθόλου Internet access — το internal name resolution δεν επηρεάζεται.»*

Ο server διατηρεί records για εσωτερικά συστήματα και απαντά απευθείας στα
queries τους. Αυτή η λειτουργία είναι ανεξάρτητη από την εξωτερική συνδεσιμότητα,
που είναι το σημείο του 2.6.4: η απώλεια upstream access υποβαθμίζει την υπηρεσία
και δεν τη διακόπτει.

### S1b — Forwarding εξωτερικών queries

**Πηγή:** 2.6.4.

> *«Αυτό που χάνεται είναι η επίλυση **εξωτερικών** ονομάτων, επειδή ο server
> δεν διατηρεί αυτά τα records και πρέπει να ερωτήσει έναν upstream resolver για
> να τα αποκτήσει.»*

Όταν ένας client ζητά όνομα για το οποίο ο server δεν είναι authoritative, πρέπει
να προωθήσει το query και όχι να αποτύχει. Χωρίς forwarding, κάθε user VLAN θα
είχε άδεια για Internet access (firewall rule 4), αλλά δεν θα μπορούσε να
επιλύσει κανένα external name — κατάσταση όπου το δίκτυο φαίνεται χαλασμένο
παρότι λειτουργεί σωστά.

### S1c — Ρυθμιζόμενη λίστα upstream forwarders

**Πηγή:** κανόνας 1 του 2.7.3.

```text
| 1 | 10.0.50.10 (DNS) | Approved upstream resolvers | UDP/TCP 53 | permit | ✓ |
```

Ο κανόνας firewall περιορίζει τον **προορισμό**, όχι απλώς το protocol. Το
υποστάδιο 2.7.3 εξηγεί γιατί: η άδεια για port 53 προς οποιαδήποτε διεύθυνση
αφήνει διαθέσιμο κανάλι data exfiltration, καθώς ένας compromised DNS server θα
μπορούσε να κωδικοποιεί δεδομένα σε queries προς nameserver που ελέγχει ο
attacker.

Ο έλεγχος είναι αποτελεσματικός μόνο αν ο ίδιος ο DNS server έχει ρυθμισμένη
καθορισμένη λίστα forwarders. Ένας server που ερωτά απευθείας root servers ή
δέχεται αυθαίρετη forwarder configuration είτε θα αποτύγχανε απέναντι στον
firewall rule είτε θα παρέκαμπτε τον έλεγχο που αυτός υλοποιεί.

**Συνέπεια για την υλοποίηση.** Οι διευθύνσεις των forwarders πρέπει να
καταγραφούν στην τεκμηρίωση configuration, επειδή εμφανίζονται σε δύο σημεία —
στο server configuration και στον firewall rule — και πρέπει να ταιριάζουν.

### S1d — Εξυπηρέτηση queries από τέσσερα VLANs

**Πηγή:** 2.4.7 — τα DHCP scopes.

Και τα τέσσερα corporate scopes διανέμουν το `10.0.50.10` ως DNS server. Ο
server επομένως δέχεται queries από τα VLANs 10, 20, 30 και 40.

**Το VLAN 60 εξαιρείται.** Οι Guest clients λαμβάνουν public resolver (2.4.7),
επειδή ο internal DNS server βρίσκεται στο VLAN 50 και το Guest δεν έχει
διαδρομή προς αυτό. Δεν πρόκειται για παράβλεψη: η υπόδειξη του internal server
στους Guest clients είτε θα αποτύγχανε είτε θα απαιτούσε άνοιγμα διαδρομής που ο
σχεδιασμός σκόπιμα δεν διαθέτει.

Ο DNS server επομένως δεν πρέπει να ρυθμιστεί ώστε να δέχεται queries από το VLAN
60 — δεν θα λάβει κανένα και η διαμόρφωσή του γι’ αυτά θα υπέθετε ότι υπάρχει
διαδρομή.

## Παραγωγή απαιτήσεων — DS2, Web Server

### S2a — HTTP και HTTPS

**Πηγή:** κανόνας 4 του 2.7.2.

```text
| 4 | VLAN 10, 20, 30, 40 | 10.0.50.20 (Web) | TCP 80, 443 | permit | — |
```

Και οι δύο θύρες επιτρέπονται. Το HTTPS είναι το κατάλληλο protocol για κάθε
περιεχόμενο που χρειάζεται προστασία· το HTTP παραμένει επιτρεπτό, κάτι που
αξίζει να σημειωθεί ως σκόπιμη επιλογή και όχι παράλειψη — αν όλο το περιεχόμενο
πρόκειται να παρέχεται μέσω HTTPS, ο κανόνας 4 θα μπορούσε να περιοριστεί μόνο
στη θύρα 443 και η policy θα ήταν αυστηρότερη.

Αυτή είναι η μόνη απαίτηση ειδικά για τον DS2. Ο web server είναι ο απλούστερος
από τους τρεις και ο κατάλογος απαιτήσεών του το αντικατοπτρίζει.

## Παραγωγή απαιτήσεων — DS3, Monitoring / Syslog Server

Ο DS3 έχει περισσότερες απαιτήσεις από τους άλλους δύο μαζί, επειδή εκτελεί τρεις
διαφορετικές λειτουργίες συλλογής.

### S3a — Syslog collector, UDP 514

**Πηγή:** 2.10.6.

Ο collector λαμβάνει μηνύματα από κάθε infrastructure device σε severity level
6 (2.10.6). Πρέπει να δέχεται remote Syslog μέσω UDP 514 και να αποθηκεύει όσα
λαμβάνει.

Το υποστάδιο 2.10.6 δίνει τον λόγο για τον οποίο έχει σημασία η κεντρική
συλλογή: logs που παραμένουν τοπικά σε μια συσκευή μπορούν να διαγραφούν από
attacker που την παραβιάζει, ενώ τα μηνύματα που έχουν ήδη προωθηθεί είναι έξω
από την εμβέλειά του.

### S3b — SNMPv3 manager, polling UDP 161

**Πηγή:** 2.10.5, 2.10.4.

Ο DS3 λειτουργεί ως **manager** στο μοντέλο SNMP και ερωτά agents σε
infrastructure devices για CPU, memory και interface utilisation (2.10.4).

Πρόσεξε την κατεύθυνση: είναι **outbound** από τον DS3 προς τις infrastructure
devices, αντίθετα από το μεγαλύτερο μέρος της server traffic. Ο core ACL rule 6
καλύπτει devices που αναφέρουν προς τα μέσα· το polling κινείται προς την άλλη
κατεύθυνση.

### S3c — Λήψη SNMP traps, UDP 162

**Πηγή:** 2.10.5.

Τα traps είναι το event-driven μισό του SNMP: οι συσκευές τα στέλνουν χωρίς
προτροπή όταν συμβεί μια συνθήκη, αντί να περιμένουν να ερωτηθούν μέσω polling.

Το υποστάδιο 2.10.4 εξηγεί γιατί χρειάζονται και οι δύο μηχανισμοί. Το polling
καθιερώνει baseline και επιβεβαιώνει ότι οι συσκευές είναι ενεργές, αλλά έχει
latency ανίχνευσης — μια βλάβη αμέσως μετά από ένα poll δεν φαίνεται μέχρι το
επόμενο. Τα traps αναφέρουν αμέσως, αλλά δεν λένε τίποτα για συσκευή που έχει
αποτύχει πλήρως.

### S3d — ICMP polling για availability

**Πηγή:** 2.10.4 και §10, που απαιτεί *«ping / basic availability checks»*.

Ο απλούστερος από τους τρεις μηχανισμούς και αυτός που απαντά στο πιο βασικό
ερώτημα: είναι η συσκευή καθόλου προσβάσιμη;

### S3e — Αποθήκευση και retention logs

**Πηγή:** 2.10.6.

Η αποθήκευση υπονοείται και δεν δηλώνεται ως συγκεκριμένο μέγεθος. Το υποστάδιο
2.10.6 σημειώνει ότι τα logs είναι χρήσιμα μόνο όσο διατηρούνται και ότι τα
περιστατικά συχνά ανακαλύπτονται εβδομάδες μετά την έναρξή τους.

**Δεν ορίζεται περίοδος retention στη Φάση 2.** Αυτό είναι κενό που αξίζει να
καταγραφεί: μια περίοδος retention που επιλέγεται σκόπιμα είναι προτιμότερη από
μια περίοδο που προκύπτει από ό,τι τυχαίνει να χωράει η αποθήκευση. Η απόφαση
ανήκει στη φάση implementation ή operations, αλλά πρέπει να είναι απόφαση και
όχι default.

## Η αρνητική απαίτηση

### S8 — Οι DS2 και DS3 δεν έχουν outbound Internet access

**Πηγή:** κανόνας 2 του 2.7.3, με τη λογική του 2.6.4.

```text
| 2 | VLAN 50 (Servers) | any | any | deny | ✓ |
```

Αυτός είναι ο πρώτος **περιορισμός** αντί για δυνατότητα σε αυτή τη φάση. Κάθε
άλλη καταχώριση στο 3.1 δηλώνει τι πρέπει να μπορεί να κάνει μια συσκευή· αυτή
δηλώνει τι δεν πρέπει να κάνουν δύο από τους servers.

**Εξαιρείται μόνο ο DS1**, και μάλιστα περιορισμένα: ο κανόνας 1 του επιτρέπει
DNS queries προς approved resolvers και τίποτα άλλο. Οι DS2 και DS3 δεν έχουν
κανένα permit rule και καταλήγουν στον κανόνα 2.

### Γιατί δηλώνεται ως απαίτηση

Η απουσία permit rule είναι ο μηχανισμός, οπότε τίποτα στη firewall configuration
δεν θα αναφέρει τους DS2 και DS3. Χωρίς καταγραφή εδώ, ο περιορισμός θα υπήρχε
μόνο ως απουσία — και οι απουσίες δεν ελέγχονται.

Έχει επίσης συνέπεια για την υλοποίηση που ένας firewall rule δεν μπορεί να
εκφράσει: οι servers πρέπει να **λειτουργούν** χωρίς outbound access. Software
που περιμένει να φτάσει update repositories, licence servers ή telemetry
endpoints κατά την κανονική λειτουργία θα συμπεριφέρεται απρόβλεπτα όταν αυτές οι
συνδέσεις αποτυγχάνουν.

### Η operational συνέπεια

Το υποστάδιο 2.6.4 καταγράφει ειλικρινά το trade-off:

> *«Αυτό αφαιρεί μια outbound διαδρομή αλλά εισάγει operational risk: το manual
> patching εξαρτάται από την τήρηση μιας διαδικασίας. Ένας unpatched server είναι
> μεγαλύτερη έκθεση από έναν server με αυστηρά ελεγχόμενη outbound access.»*

Έτσι προκύπτει μια **procedural requirement** από network constraint:

```text
Το IT κατεβάζει και επαληθεύει updates
        ↓
ελεγχόμενη μεταφορά στον server
        ↓
εφαρμογή update σε καθορισμένο schedule
```

Το υποστάδιο 2.6.4 αποδέχεται την προσέγγιση **υπό την προϋπόθεση** ότι η
διαδικασία τεκμηριώνεται και εκτελείται σε καθορισμένο schedule. Η προϋπόθεση
είναι απαίτηση του σχεδιασμού και όχι προαιρετική πρακτική και ανήκει στην
operational documentation που παράγεται μαζί με το build.

Σε production scale η προσέγγιση θα ήταν διαφορετική — ένα internal update
repository θα εξυπηρετούσε πολλούς servers χωρίς να δίνει σε καθέναν Internet
access. Για τρεις servers είναι αναλογική και διατηρεί τη security policy
κατανοητή.

## Προτεραιότητα επιλογής και υλοποίησης

| Προτεραιότητα | Απαιτήσεις | Συνέπεια αν δεν ικανοποιηθούν |
|---------------|------------|--------------------------------|
| **Essential** | S5 | Κάθε αναφορά σε διεύθυνση server διακόπτεται· οι αστοχίες εμφανίζονται ως δυσλειτουργίες services |
| **Essential** | S1a, S1b | Αποτυγχάνει το name resolution εσωτερικά ή εξωτερικά για κάθε user VLAN |
| **Essential** | S2a, S3a | Η service για την οποία υπάρχει ο server δεν λειτουργεί |
| **Important** | S1c | Ο περιορισμός προορισμού του firewall rule 1 δεν μπορεί να επιβληθεί από την πλευρά του server |
| **Important** | S3b, S3c, S3d | Χάνεται μία κατηγορία monitoring· το §10 ικανοποιείται μόνο μερικώς |
| **Important** | S6 | Τα timestamps των logs δεν μπορούν να συσχετιστούν — το πρόβλημα εμφανίζεται κατά τη διερεύνηση |
| **Important** | S7, S9 | Οι servers δεν μπορούν να διαχειρίζονται ή να παρακολουθούνται με συνέπεια προς το υπόλοιπο estate |
| **Constraint** | S8 | Δύο servers αποκτούν outbound διαδρομή που ο σχεδιασμός σκόπιμα τους στερεί |
| **Open** | S3e | Η περίοδος retention είναι ακαθόριστη· πρέπει να αποφασιστεί και όχι να αφεθεί ως default |

Η S6 τοποθετείται πάνω από τη φαινομενική σημασία της για τον λόγο που δίνεται
στην παραγωγή της: ένα ανακριβές ρολόι στον monitoring server δεν προκαλεί
ορατή αστοχία και ανακαλύπτεται μόνο όταν χρειάζονται τα logs.
