# 3.1.4 Απαιτήσεις συσκευής — Edge Router

Ποσότητα: **1** (§11)

Το παρόν έγγραφο καθορίζει τις δυνατότητες που πρέπει να διαθέτει ο edge
router. Δεν επιλέγει μοντέλο — αυτό γίνεται στο 3.3. Κάθε απαίτηση προκύπτει
από απόφαση που έχει ήδη ληφθεί στη Φάση 1 ή στη Φάση 2 και η παραγωγή της
παρουσιάζεται ώστε καμία απαίτηση να μη βασίζεται σε υπόθεση.

Ο edge router έχει λιγότερες απαιτήσεις από οποιαδήποτε άλλη συσκευή υποδομής
σε αυτόν τον σχεδιασμό. Αυτό είναι συνέπεια του τρόπου κατανομής των ρόλων και
όχι παράλειψη — βλ. τη σημείωση στο τέλος.

---

## Σύνοψη απαιτήσεων

| # | Απαίτηση | Πηγή | Τρόπος παραγωγής |
|---|----------|------|------------------|
| E1 | Τουλάχιστον 2 interfaces | 2.1.2, 2.5.4 | Υπολογισμός |
| E2 | Static routes, χωρίς διαδρομή που παρακάμπτει το firewall | 2.5.4 | Ανάγνωση + περιορισμός σχεδιασμού |
| E3 | NTP client **και** server | 2.6.5, 2.10.7 | Ανάγνωση |
| E4 | SSH server· δυνατότητα απενεργοποίησης του Telnet | 2.10.3 | Ανάγνωση |
| E5 | SNMPv3 agent, Syslog client | 2.10.5–6 | Ανάγνωση |
| E6 | Dynamic routing (OSPF) | trigger μετάβασης 2.5.2 | Μελλοντική απαίτηση |
| E7 | Δυνατότητα σχηματισμού redundant pair | §12, 2.5.2 | Μελλοντική απαίτηση |

---

## Παραγωγή απαιτήσεων

### E1 — Τουλάχιστον 2 interfaces

**Πηγή:** 2.1.2 (τοπολογία), 2.5.4 (πίνακας δρομολόγησης).

Προκύπτει μετρώντας τι συνδέεται στον edge router:

| Interface | Συνδέεται με | Πηγή |
|-----------|--------------|------|
| WAN / outside | ISP | 2.1.2 — S8 WAN Edge ↔ S9 Internet |
| LAN / inside | Firewall | 2.1.2 και η σύνδεση `10.0.254.4/30` στο 2.5.4 |

Τα δύο είναι το ελάχιστο και, για την τρέχουσα τοπολογία, ο ακριβής αριθμός.
Τίποτα άλλο δεν συνδέεται σε αυτή τη συσκευή: το core, τα access switches και
οι servers βρίσκονται όλοι πίσω από το firewall.

**Συνέπεια για την επιλογή συσκευής.** Ο **τύπος** του WAN interface έχει
μεγαλύτερη σημασία από το πλήθος. Πρέπει να ταιριάζει με αυτό που παρέχει ο
πάροχος, περιορισμός που επιβάλλεται από το εξωτερικό της σχεδίασης και δεν
προκύπτει από αυτήν. Αυτό πρέπει να επιβεβαιωθεί και όχι να θεωρηθεί δεδομένο,
επειδή μια ασυμβατότητα δεν επιλύεται με configuration.

### E2 — Static routes, χωρίς διαδρομή που παρακάμπτει το firewall

**Πηγή:** 2.5.4 — ο πίνακας δρομολόγησης του edge router.

```text
Directly connected:
  10.0.254.4/30    link to firewall
  <ISP subnet>     link to ISP

Static:
  10.0.0.0/8   →   10.0.254.5   (firewall)
  0.0.0.0/0    →   <ISP gateway>
```

Η υποστήριξη static routing είναι το απλό μέρος. Η απαίτηση περιλαμβάνει ένα
δεύτερο στοιχείο που είναι **περιορισμός σχεδιασμού και όχι δυνατότητα της
συσκευής**, και το 2.5.4 το δηλώνει ρητά:

> *«Η διαδρομή προς το εσωτερικό δίκτυο δείχνει στο firewall και όχι πέρα από
> αυτό. Επομένως η επιστρεφόμενη κίνηση υπόκειται στο ίδιο σημείο επιβολής με
> την εξερχόμενη κίνηση και ο edge router δεν έχει διαδρομή που το παρακάμπτει.»*

Αυτό έχει σημασία λόγω αυτού που **δεν** ζητείται από τον edge router. Το
υποστάδιο 2.1.3 καθιερώνει το firewall ως το μοναδικό σημείο επιβολής πολιτικής
και αυτό ισχύει μόνο αν δεν υπάρχει διαδρομή γύρω από αυτό. Μια διαδρομή από τον
edge router απευθείας σε εσωτερικό δίκτυο — που προστέθηκε για ευκολία ή
κληρονομήθηκε από template — θα δημιουργούσε μονοπάτι προς το εσωτερικό δίκτυο
χωρίς έλεγχο και μάλιστα αθόρυβα.

**Συνέπεια για την επιλογή συσκευής.** Δεν απαιτείται ειδική δυνατότητα. Ο
περιορισμός αφορά τον τρόπο διαμόρφωσης της συσκευής και πρέπει να καταγραφεί
στην τεκμηρίωση configuration, ώστε μελλοντικός μηχανικός να μην προσθέσει τη
«missing» διαδρομή.

Το dynamic routing δεν απαιτείται προς το παρόν — το 2.5.2 τεκμηριώνει γιατί —
αλλά βλ. E6.

### E3 — NTP client και server

**Πηγή:** 2.6.5 (η απόφαση για τον συγχρονισμό χρόνου), 2.10.7.

Αυτή είναι η μοναδική απαίτηση που αφορά ειδικά αυτή τη συσκευή και είναι
ασυνήθιστη: ο edge router λειτουργεί **ταυτόχρονα και στους δύο ρόλους**.

```text
              external NTP source
                      ↓
                 Edge Router          ← client (receives)
                      ↓
        ┌─────────────┼─────────────┐ ← server (distributes)
        ↓             ↓             ↓
      Core        Switches      Servers
```

Το υποστάδιο 2.6.5 απέρριψε την εναλλακτική κάθε συσκευή να ερωτά ανεξάρτητα
μια εξωτερική πηγή, για δύο λόγους.

**Λιγότερες εξερχόμενες ροές.** Τέσσερις εξωτερικές εξαρτήσεις γίνονται μία.
Κάθε εξερχόμενη σύνδεση είναι μια διαδρομή που πρέπει να επιτραπεί και θα
μπορούσε να χρησιμοποιηθεί καταχρηστικά, ενώ ο κανόνας 3 του 2.7.3 δίνει αυτή
την άδεια μόνο σε αυτή τη συσκευή.

**Κοινή πηγή χρόνου.** Αυτός είναι ο σημαντικότερος λόγος και το 2.10.7
εξηγεί γιατί η διάκριση δεν είναι σχολαστική. Σκοπός του συγχρονισμένου χρόνου
είναι η συσχέτιση logs — η ανακατασκευή της σειράς των γεγονότων κατά τη
διερεύνηση. Συσκευές που συγχρονίζονται ανεξάρτητα με διαφορετικές πηγές μπορεί
να είναι η καθεμία ακριβής και παρ’ όλα αυτά να διαφωνούν μεταξύ τους, που είναι
ακριβώς η περίπτωση όπου η σειρά γίνεται αμφίβολη. Συσκευές που παίρνουν χρόνο
από μία εσωτερική πηγή μοιράζονται όποιο offset έχει αυτή η πηγή, οπότε τα
**σχετικά** διαστήματα παραμένουν σωστά ακόμη και αν ο απόλυτος χρόνος
μετατοπίζεται.

**Συνέπεια για την επιλογή συσκευής.** Η συσκευή πρέπει να λειτουργεί ως NTP
server και όχι μόνο ως client. Η παροχή χρόνου είναι διαφορετική λειτουργία από
την κατανάλωσή του, και μια συσκευή που υποστηρίζει μόνο τον ρόλο client δεν
μπορεί να ικανοποιήσει αυτόν τον σχεδιασμό.

**Συνέπεια για τη διαθεσιμότητα.** Έτσι συγκεντρώνεται μια εξάρτηση. Αν ο edge
router δεν είναι διαθέσιμος, οι εσωτερικές συσκευές σταδιακά θα αποκλίνουν μεταξύ
τους. Το υποστάδιο 2.6.5 σημειώνει ότι το αν θα ήταν προτιμότερη μια dedicated
εσωτερική υπηρεσία χρόνου είναι ερώτημα υλοποίησης που πρέπει να επανεξεταστεί
αν το δίκτυο μεγαλώσει ή αν η ακρίβεια χρόνου αποκτήσει βάρος συμμόρφωσης.

### E4 — SSH server· δυνατότητα απενεργοποίησης του Telnet

**Πηγή:** 2.10.3 — *«| Routers | SSH (TCP 22) | IT management workstations |
Telnet disabled |»*

Από μία γραμμή προκύπτουν δύο απαιτήσεις: πρέπει να υποστηρίζεται SSH και το
Telnet πρέπει να μπορεί να **απενεργοποιηθεί**, όχι απλώς να παραμείνει χωρίς
ρύθμιση. Το υποστάδιο 2.10.3 αντιμετωπίζει τα μη κρυπτογραφημένα management
protocols ως ελάττωμα και όχι ως επιλογή, επισημαίνοντας ότι η διαθεσιμότητά
τους σε μια συσκευή αποτελεί από μόνη της κίνδυνο ακόμη και όταν δεν
χρησιμοποιούνται.

**Γιατί έχει μεγαλύτερο βάρος εδώ από ό,τι αλλού.** Ο edge router βρίσκεται
εκτός του firewall και λαμβάνει αφιλτράριστη κίνηση από το Internet. Το Telnet
μεταδίδει διαπιστευτήρια σε plaintext· σε εσωτερικό switch είναι κακή πρακτική,
αλλά σε συσκευή με interface στραμμένο προς το δημόσιο Internet είναι σοβαρή
έκθεση.

Η ίδια λογική επεκτείνεται πέρα από το Telnet. Η πρόσβαση management δεν πρέπει
να είναι προσβάσιμη καθόλου από το WAN interface και οι υπηρεσίες που δεν
χρησιμοποιεί ο σχεδιασμός πρέπει να απενεργοποιούνται αντί να παραμένουν σε
λειτουργία. Αυτό είναι απαίτηση configuration και όχι δυνατότητα, αλλά ανήκει
στη συσκευή επειδή η έκθεση αποτελεί ιδιότητα της θέσης της.

### E5 — SNMPv3 agent, Syslog client

**Πηγή:** 2.10.5, 2.10.6.

- **SNMPv3** — το 2.10.5 απορρίπτει τα v1 και v2c επειδή το community string
  μεταδίδεται σε plaintext και απενεργοποιεί την SNMP write access, ώστε οι
  αλλαγές configuration να γίνονται μόνο μέσω authenticated, καταγεγραμμένων
  SSH sessions
- **Syslog** προς `10.0.50.30` με severity level 6 (2.10.6), με προώθηση σε
  remote collector αντί να διατηρείται τοπικά

Ο κανόνας 6 του core ACL (2.7.2) επιτρέπει στις συσκευές υποδομής να φτάνουν τον
monitoring server και ο edge router ανήκει σε αυτή την κατηγορία.

Το NTP καλύπτεται ξεχωριστά από το E3, επειδή ο ρόλος αυτής της συσκευής
διαφέρει από τον ρόλο κάθε άλλης συσκευής.

**Σημείωση για το scope.** Η απαίτηση SNMPv3 εφαρμόζεται με τον ίδιο τρόπο στο
core switch (C10), στα access switches (A8) και στο firewall (F14). Αν το
περιβάλλον υλοποίησης υποστηρίζει μόνο v2c, η έλλειψη αφορά ολόκληρο το estate
και όχι μία συσκευή και πρέπει να καταγραφεί μία φορά ως περιορισμός σε επίπεδο
estate αντί για τέσσερις φορές.

### E6 — Dynamic routing (μελλοντική απαίτηση)

**Πηγή:** 2.5.2 — το trigger μετάβασης.

Το static routing επιλέχθηκε επειδή η τοπολογία έχει ακριβώς μία διαδρομή προς
κάθε προορισμό. Το υποστάδιο 2.5.2 διατυπώνει καθαρά το κριτήριο: τα dynamic
routing protocols υπάρχουν για να αποφασίζουν *ποια από τις διαθέσιμες
διαδρομές θα χρησιμοποιηθεί και τι θα συμβεί όταν μία αποτύχει*, και όταν
υπάρχει μόνο μία διαδρομή αυτό το πρόβλημα δεν εμφανίζεται.

Αυτό παύει να ισχύει σε οποιαδήποτε από τις δύο προγραμματισμένες επεκτάσεις.
Ένα branch office (§5) εισάγει πολλαπλά δίκτυα που απαιτούν χειροκίνητες
διαδρομές και στις δύο πλευρές και αυξάνονται με κάθε νέο segment. Η high
availability (§12) εισάγει πραγματικές εναλλακτικές διαδρομές, οπότε το
automatic failover γίνεται ολόκληρος ο σκοπός. Το υποστάδιο 2.5.2 προτείνει
**OSPF** σε εκείνο το στάδιο — open standard, με γρήγορο convergence, επιλογή
διαδρομών με cost που προκύπτει από το bandwidth και single-area deployment
αρκετό για το μέγεθος που θα έχει τότε το δίκτυο.

**Γιατί μια μελλοντική δυνατότητα ανήκει σε σημερινό κατάλογο απαιτήσεων.** Ένας
router χωρίς υποστήριξη OSPF θα έπρεπε να **αντικατασταθεί** όταν φτάσει το
trigger και όχι απλώς να επαναρυθμιστεί. Το κόστος της παράλειψης κατά την
επιλογή μετριέται σε hardware και όχι σε προσπάθεια.

Η απαίτηση είναι ίδιας φύσης με την C14 του core switch. Και οι δύο συσκευές θα
χρειαστεί να συμμετέχουν στο ίδιο routing domain, άρα και οι δύο πρέπει να το
υποστηρίζουν ή καμία μετάβαση δεν είναι δυνατή.

### E7 — Δυνατότητα σχηματισμού redundant pair (μελλοντική απαίτηση)

**Πηγή:** §12 (επέκταση high availability), 2.5.2.

Η αρχιτεκτονική του §12 ζευγαρώνει συσκευές αντί να προσθέτει interfaces:

```text
                 Internet
                /        \
             ISP 1      ISP 2
               |          |
          Edge-R1      Edge-R2
               \        /
             FW-1    FW-2
                \    /
              Core Network
```

Το υποστάδιο 2.5.2 επιβεβαιώνει αυτή την ανάγνωση: *«Ένας δεύτερος edge
router, ένα δεύτερο firewall και ένας δεύτερος ISP δημιουργούν πραγματικές
εναλλακτικές διαδρομές.»*

**Τι σημαίνει για την τρέχουσα επιλογή.** Η σύνδεση του δεύτερου ISP έρχεται με
**δεύτερο router**, όχι σε εφεδρικό interface του υπάρχοντος. Επομένως η
απαίτηση δεν είναι περισσότερα WAN interfaces, αλλά η δυνατότητα συμμετοχής σε
redundant pair.

Αυτό μπορεί να επιτευχθεί με δύο μηχανισμούς:

| Μηχανισμός | Πώς λειτουργεί |
|------------|----------------|
| **First-hop redundancy protocol** (HSRP, VRRP) | Δύο routers παρουσιάζουν μία virtual address· το firewall δείχνει στη virtual address και το failover είναι διαφανές |
| **Dynamic routing** | Το firewall μαθαίνει routes και από τους δύο routers και επιλέγει μεταξύ τους |

Ο πρώτος είναι η συνηθέστερη προσέγγιση ειδικά για first-hop redundancy και
συνήθως απλούστερη όταν η downstream συσκευή είναι firewall και όχι router.

**Συνέπεια για την επιλογή συσκευής.** Όπως και στο E6, μια συσκευή που δεν
μπορεί να συμμετέχει σε redundant pair θα πρέπει να αντικατασταθεί και όχι να
συμπληρωθεί όταν προστεθεί το redundancy. Τα E6 και E7 είναι συνέπειες της ίδιας
μελλοντικής απόφασης και ένα μοντέλο που δεν υποστηρίζει κανένα από τα δύο
δεσμεύει τον σχεδιασμό σε αντικατάσταση hardware κατά την επέκταση high
availability.

## Τι **δεν** κάνει αυτή η συσκευή

Ο edge router έχει επτά απαιτήσεις, ενώ το firewall έχει δεκαπέντε και το core
switch δεκατέσσερις. Αξίζει να δηλωθεί ρητά, επειδή ένας σύντομος κατάλογος
μπορεί να εκληφθεί ως ελλιπής.

| Λειτουργία | Πού υλοποιείται | Πηγή |
|------------|-----------------|------|
| Επιβολή security policy | Firewall | 2.1.3 — μοναδικό σημείο επιβολής πολιτικής |
| Network address translation | Firewall | 2.5.6 |
| Τερματισμός VPN | Firewall | DD-1, 2.9.2 |
| Inter-VLAN routing | Core switch | 2.5.3 |
| Access control lists | Core switch και firewall | 2.7.2, 2.7.3 |
| DHCP | Core switch και firewall | 2.4.7, C8, F12 |

Ο edge router εκτελεί ακριβώς δύο λειτουργίες: **συνδεσιμότητα με τον πάροχο**
και **διανομή χρόνου**. Όλα τα υπόλοιπα ανατέθηκαν σκόπιμα αλλού.

Ο περιορισμένος ρόλος αποτελεί ένδειξη σαφούς κατανομής ευθυνών και όχι
υποχρησιμοποιούμενης συσκευής. Κάθε λειτουργία αυτού του σχεδιασμού έχει μία
θέση, πράγμα που σημαίνει ότι η απάντηση στο «πού επιβάλλεται αυτό;» είναι μία
και μοναδική — και αυτή η ιδιότητα κάνει τον σχεδιασμό ελέγξιμο.

## Προτεραιότητα επιλογής

| Προτεραιότητα | Απαιτήσεις | Συνέπεια αν δεν ικανοποιηθεί |
|---------------|------------|-------------------------------|
| **Essential** | E1, E2 | Η συσκευή δεν μπορεί να συνδεθεί ή η κίνηση δεν έχει διαδρομή |
| **Essential** | E3 (ρόλος server) | Δεν υπάρχει εσωτερική πηγή χρόνου· κάθε συσκευή πρέπει να λαμβάνει χρόνο εξωτερικά, προσθέτοντας εξερχόμενες ροές και χάνοντας την κοινή αναφορά που κάνει αξιόπιστη τη συσχέτιση logs |
| **Important** | E4, E5 | Το management εκτίθεται μέσω μη κρυπτογραφημένου protocol ή η συσκευή δεν μπορεί να παρακολουθείται |
| **Future** | E6, E7 | Λειτουργεί σήμερα· απαιτεί αντικατάσταση hardware στο trigger μετάβασης |

Το E3 καταγράφεται ως essential και όχι important επειδή η απουσία του δεν
αφαιρεί απλώς μια ευκολία. Χωρίς εσωτερικό NTP server, είτε κάθε συσκευή
αποκτά εξωτερική εξάρτηση — σε αντίθεση με την απόφαση του 2.6.5 και με ανάγκη
για νέους firewall rules — είτε οι συσκευές αποσυγχρονίζονται, υπονομεύοντας τη
συσχέτιση logs που υπάρχει για να υποστηρίζει ο σχεδιασμός monitoring.

Κάθε απαίτηση που δεν μπορεί να ικανοποιηθεί πρέπει να καταγραφεί ως περιορισμός
υλοποίησης στο 3.3, μαζί με τη συνέπειά της — όχι να παραλειφθεί σιωπηρά.
