# 3.4 Physical Topology

This sub-stage records which devices connect to which and where they are located.
It translates the logical structure from Phase 2 and the equipment selection from
3.3 into a build plan.

Two agreed implementation changes are reflected here:

1. VLAN 60 uses **Layer 2 transit through the core**, with no VLAN 60 SVI on the
   core and one gateway, `10.0.60.1/24`, on the firewall.
2. Packet Tracer uses **one Cisco 3504 WLC and two LAP-PTs** because its
   autonomous AP model cannot implement the required five SSIDs.

> **Revised after implementation.** The items this document deliberately left
> **TBD** — the Core→ASA Guest handoff mode, the WLC and LAP control path, and the
> firewall's management termination — were resolved during the build and are now
> recorded with the evidence for each. The amendment record at the end lists every
> change; the deviations themselves are set out in 3.6.

## 3.4.1 Physical Versus Logical

Sub-stage 2.1 produced a logical diagram: segments and the relationships between
them. This sub-stage produces a physical one: devices and cables.

| | Logical (2.1) | Physical (3.4) |
|---|---------------|----------------|
| **Shows** | Segments and relationships | Devices and cables |
| **Answers** | What is permitted | What exists |
| **Elements** | VLANs, zones | Equipment |

In this design, VLANs 10, 20, 30, 40, 60 and 99 reach each access switch over one
core trunk. VLAN 50 remains local to the core because the three servers connect
directly to it. VLAN 60 then crosses the core only at Layer 2 and is handed to the
firewall; it is never routed by the core.

The Packet Tracer wireless implementation adds one physical WLC connection to the
core. This is an implementation-only addition and does not change the autonomous
two-AP target of the real design.

**How to read the Guest path:** the two access switches carry VLAN 60 on their
normal core trunks. The core forwards those frames at Layer 2 out of `Gi1/0/4`, an
untagged access port, to the single ASA Guest interface (`Gi1/3`). The core has no
VLAN 60 SVI and does not own `10.0.60.1`.

**How to read the wireless path:** the real design target is two autonomous APs.
In Packet Tracer the two LAP-PTs are controlled by the 3504 WLC on `Gi1/0/9`. All
three wireless-facing links use native VLAN 99 rather than 999, for the reason
recorded in 2.3.7.

**How to read the management path:** the firewall's `Management1/1` terminates on
core `Gi1/0/10`, an untagged access port in VLAN 99. The firewall is therefore
reachable at `10.0.99.30` through the management VLAN like every other
infrastructure device. The edge router is the one exception to that model and is
reached at `203.0.113.6` instead (2.4.6).

The centre path is the routed backbone. The Core→ASA Guest connection is separate
from the routed inside link: it carries only the Guest broadcast domain to the
firewall.

- Rows 5 and 6 include VLAN 60. They exclude VLAN 50 because the servers attach
  directly to the core.

## 3.4.4 Guest VLAN 60 Transit and Termination

**Selected: Layer 2 transit through the core, with a single Guest gateway on the
firewall.**

VLAN 60 follows this physical path:

```text
LAP / wireless client → access switch → core (Layer 2 only) → ASA Guest interface
```

The addressing remains exactly as defined in Phase 2:

| Property | Value |
|----------|-------|
| Guest subnet | `10.0.60.0/24` |
| Default gateway | `10.0.60.1/24` on the ASA |
| Core VLAN 60 SVI | **None** |
| DHCP scope | One scope on the ASA |

### Why the previous physical arrangement changed

The earlier dedicated-uplink arrangement brought one VLAN 60 cable from each
access switch to the ASA. Preserving one subnet and one gateway would then require
the two ASA interfaces to be bridged into one Layer 2 domain. The Packet Tracer
ASA does not provide the required bridge-group/BVI implementation.

Splitting the `/24` into two `/25` networks was not selected because it would
change the addressing plan, create two DHCP scopes and produce two Guest networks
where the design defines one.

Layer 2 transit preserves the single subnet and gateway while using the normal
access-to-core trunk from each switch. The core forwards VLAN 60 frames but never
routes them.

### Isolation condition

The core must not have a VLAN 60 SVI. The existing firewall rule that denies Guest
traffic to RFC1918 destinations remains defence in depth if an SVI is ever added
by mistake; it does not replace the no-SVI requirement.

**Verified.** `show interfaces status` on the core reports `Gi1/0/4` as an access
port in VLAN 60, and the routing table holds no entry for `10.0.60.0/24` (2.5.4).
Guest isolation was confirmed by test: every probe from a Guest client toward
`10.0.0.0/16` was denied, with the hit counter on the firewall's deny rule
identifying which rule stopped it.

### Handoff mode — resolved *(D3)*

This document previously recorded the Core→ASA handoff as **mode TBD**, with an
untagged access port and a tagged trunk/subinterface as the two candidates, to be
decided after verifying the firewall's capabilities.

**The tagged option was attempted first and rejected by the platform.** The
firewall does not implement subinterfaces: `interface GigabitEthernet1/3.60`
returns an error.

**Selected: untagged access port.** Core `Gi1/0/4` in VLAN 60 to firewall `Gi1/3`
holding `10.0.60.1/24`. Only one VLAN crosses the link, so no information is lost
by not tagging, and the native-VLAN consideration of 2.3.7 does not arise — an
access port carries no native VLAN. 3.5 is updated consistently.

The TBD was handled as this document specified: verify, choose, then reflect in
3.5. The choice was made by the platform rather than on merit, which is the
ordinary outcome when one of two options is unavailable.

## 3.4.5 Device Placement

### Groupings

| Group | Devices | Rationale |
|-------|---------|-----------|
| **Equipment area** | Core, firewall, edge router, WLC, 3 servers | Serve no users directly; concentrated for physical security, environmental control and short interconnects |
| **Distributed** | Access switches | Must be near the users they serve, or every user cable becomes a long run |
| **Ceiling or wall mounted** | LAP-PT access points | Positioned for radio coverage; PoE avoids requiring nearby mains power |

### Distance constraint

Cat6 carries 10 Gbps to approximately 55 metres. The design specifies 10 Gbps
access-to-core uplinks, even though Packet Tracer implements them at 1 Gbps.
Therefore each access switch should be within 55 metres of the core by cable run;
otherwise Cat6a is required for that uplink.

No floor plan, building layout or cable distances were supplied. Those facts are
not invented here and must be confirmed before physical deployment.

### A placement consequence found by failure testing

The WLC sits in the equipment area and connects to the core, which is correct for
a controller: it is infrastructure rather than user-facing, and it belongs where
the other infrastructure is.

The consequence is that **a core failure removes the entire wireless estate**, not
only the wired network. The access points lose their controller and drop their
clients. The Phase 1 SPOF analysis did not anticipate this, because the controller
did not exist when it was written; the severity of SPOF-3 is correspondingly wider
than recorded there. This does not argue for placing the WLC elsewhere — there is
nowhere better in this topology — but it belongs in the record of what the
placement costs.

## 3.4.6 Clarifications to Earlier Requirements

### F2 — firewall interfaces remain four

The Layer 2 transit decision changes only how VLAN 60 reaches the firewall. It
does not remove or merge the management interface.

```text
outside + inside + one Guest interface + management = 4 interfaces
```

The two Guest paths aggregate at Layer 2 before reaching the firewall, so only one
Guest interface is required. Management architecture and addressing remain as
previously specified, and the interface is cabled to the core in VLAN 99 (row 11).

All four are in use in the implementation; `Gi1/4` through `Gi1/8` are shut down
with no nameif and no address.

### Core-to-access trunk VLANs

Both core-to-access trunks carry VLANs **10, 20, 30, 40, 60 and 99**. VLAN 60 is
present because it now transits the core at Layer 2. VLAN 50 is absent because the
servers connect directly to the core.

### Wireless design versus implementation

The design remains two autonomous APs with static per-SSID VLAN assignment. The
Packet Tracer implementation uses a WLC 3504 and two LAP-PTs solely because the
autonomous AP model exposes one SSID. This adds one device, one core connection and
an implementation-only wireless SPOF.

**The control path is now resolved** *(D10)*. The controller is managed at
`10.0.99.40` over HTTPS and connects to core `Gi1/0/9` by an 802.1Q trunk with
native VLAN 99. The access points obtain addresses by DHCP from the VLAN 99 scope
(2.4.7) and connect to `Fa0/24` on their access switch, also by trunk with native
VLAN 99.

The access points operate in **FlexConnect mode** and cannot be changed to Local
mode. Each WLAN is configured with FlexConnect Local Switching and FlexConnect
Local Auth, so client traffic is switched locally at the access switch rather than
tunnelled to the controller.

This matters to the physical design rather than only to the wireless design. In
Local mode, all client traffic would traverse the core twice — once to reach the
controller and once to return — and the controller's single uplink would carry the
whole wireless load. In FlexConnect, the controller carries configuration and
association only, and the WLAN VLANs on `Gi1/0/9` exist for the controller's own
interfaces rather than for client traffic. **The link is therefore a control path,
not a data path**, which is why one trunk port is sufficient.

## 3.4.7 Verification at Implementation — Resolved

Every item this document listed as requiring verification has been resolved. The
status column records what was found rather than what was planned.

| Item | Resolution | Evidence |
|------|------------|----------|
| **Core→ASA Guest handoff** | **Untagged access port.** The tagged alternative was attempted and rejected: the firewall does not implement subinterfaces *(D3)* | `show interfaces status` reports `Gi1/0/4` as access VLAN 60; `interface Gi1/3.60` returns an error on the firewall |
| **WLC/LAP control path** | Controller on core `Gi1/0/9`, trunk with **native VLAN 99**, managed at `10.0.99.40` over HTTPS. LAPs on `Fa0/24` of each access switch, trunk with native VLAN 99, addressed by DHCP from the VLAN 99 scope | `show interfaces status`; the native VLAN was established by failure — the controller was unreachable with native 999, and both LAPs dropped to `DOWN` with VLAN 99 tagged *(D8)* |
| **10 Gbps access uplinks** | Unavailable. Lab links operate at 1 Gbps; the 10 Gbps real-design requirement stands | `show interfaces status` reports `a-100` on the access uplinks |
| **2960 port types** | Confirmed: 24 FastEthernet access ports plus 2 Gigabit uplinks. `Gi0/1` carries the single core uplink; `Gi0/2` is parked in VLAN 999 and shut down | `show interfaces status` on both access switches |
| **Guest client isolation (W6)** | **Not verifiable.** The controller exposes no per-SSID client isolation setting, so the limitation is recorded rather than worked around — as this table instructed | 2.8.6 |
| **Firewall management termination** | Core `Gi1/0/10`, untagged access port in VLAN 99. The firewall is reachable at `10.0.99.30` through the management VLAN | `show interfaces status` reports `Gi1/0/10` as access VLAN 99, connected |
| **SW2 `Fa0/23`** | No department assigned. The port remains named `RESERVED`, shut down, in VLAN 999 | `show interfaces status` on ACC-SW2 |

Two of these were resolved by the platform refusing the preferred option rather
than by a choice on merit, which is recorded as such: the Guest handoff mode and
the native VLAN on the three wireless-facing links. The instruction this table gave
in each case — verify, then record the limitation rather than inventing a
workaround — was followed.
