# 3.5 Port Mapping

This sub-stage assigns ports to the connections defined in 3.4 and records the
state of unused ports. It reflects the two approved changes:

- VLAN 60 transits the core at Layer 2, so each access switch uses one uplink and
  the core has one separate Guest handoff to the ASA.
- Packet Tracer uses one 3504 WLC and two LAP-PTs instead of two autonomous APs.

> **Revised after implementation.** Every item this document marked **TBD** — the
> Core→ASA Guest handoff mode, the WLC port and control path, the LAP port modes,
> the firewall's management termination, and the SW2 growth port — has been
> resolved and is recorded with the evidence for each. The boundary addressing in
> 3.5.6 and 3.5.7 has also been corrected. The amendment record at the end lists
> every change; the deviations themselves are set out in 3.6.
>
> Port states throughout were verified against `show interfaces status` on all
> three switches after the build was complete.

---

## 3.5.1 Conventions

### Infrastructure ports remain predictable

The access-switch uplink uses `Gi0/1`; `Gi0/2` is no longer needed for Guest and
is parked in VLAN 999. Core infrastructure connections use the first available
ports. This keeps user and infrastructure cabling distinguishable.

### Department ranges remain contiguous

Each department occupies a continuous range. The A9 distribution remains
unchanged: 20 users on SW1 and 22 users on SW2, with every department represented
on both switches.

### Unused ports are explicitly secured

Unused switch ports are assigned to VLAN 999 and administratively shut down where
supported. Unused routed interfaces on the firewall and router are also shut
down.

### Ports carry descriptive names

Every port in service or reserved carries a `description` identifying its role —
`HR`, `SERVERS`, `WLC-1 trunk`, `FW-1 management`, `RESERVED`, `UNUSED`. This is
not decoration: `show interfaces status` becomes self-documenting, and a port's
purpose is visible without consulting this table.

---

## 3.5.2 Design Scope Versus Packet Tracer Implementation

The user-port ranges describe the full deployment, even though the lab may use
fewer endpoint devices.

The wireless port role differs between design and implementation:

| Scope | Wireless attachment |
|-------|---------------------|
| Real design | Each autonomous AP connects to its access switch by an 802.1Q trunk carrying VLANs 10, 20, 30, 40 and 60 |
| Packet Tracer | Each LAP-PT connects to an access switch by an 802.1Q trunk; the WLC connects to the core on its own trunk |

**The two converge more closely than expected.** The implemented access points run
in FlexConnect Local Switching mode *(D10)*, so each one tags client frames by SSID
and hands them to its access switch — exactly what the real design specifies. The
WLC trunk carries the controller's own interfaces rather than client traffic, which
is why the lab adds one core port rather than a data path (3.4.6).

The lab trunks differ from the design in one respect: they also carry VLAN 99, and
their native VLAN is 99 rather than 999, because both the controller and the access
points send management traffic untagged *(D8)*.

### The two ports this document previously left open

**`Gi1/0/9` — the WLC.** The port was not assigned in the original version because
the controller's management configuration had not been approved. It is now a trunk
carrying the same VLAN set as the access uplinks, with **native VLAN 99**. The
native VLAN is not a preference: with native 999 the controller was unreachable
(`ping` 0/5), and the setup wizard's own Management VLAN ID field had no effect on
its behaviour *(D8)*.

**`Gi1/0/10` — the firewall's management interface.** The original version recorded
the termination as TBD, deliberately refusing to assign it to a core port without
confirmation. It terminates on this port as an untagged access port in VLAN 99, so
the firewall participates in the in-band management model of 2.10.2 like every
other infrastructure device. The edge router remains the single exception (2.4.6).

Ten of twenty-eight ports are allocated. C13 set a nine-port design minimum —
seven data connections, one future File Server and one spare — which the selected

## 3.5.6 Firewall — ASA 5506

| Interface | Status | Zone | Address / role | Connects to |
|-----------|--------|------|----------------|-------------|
| Gi1/1 | In use | outside | `203.0.113.5/30` | Edge router `Gi0/0/1` |
| Gi1/2 | In use | inside | `10.0.254.2/30` | Core `Gi1/0/3` |
| Gi1/3 | In use | guest | `10.0.60.1/24`; **untagged access** | Core `Gi1/0/4` |
| Management1/1 | In use | management | `10.0.99.30`; `management-only` | Core `Gi1/0/10`, access VLAN 99 |
| Gi1/4–8 | Unused / shutdown | — | `no nameif`, `no ip address` | — |

There is no BVI and no second Guest interface. The ASA has one Guest Layer 3
interface and remains the only gateway for `10.0.60.0/24`.

The management interface is not removed or merged with inside, and it carries the
`management-only` keyword, which prevents it from being used for transit traffic.

### Corrections to this table

**The outside address was wrong twice over** *(D1, D2)*. The original table gave
`Gi1/1` the address `10.0.254.6/30`, which was incorrect in two independent ways.

First, it was the **wrong end of the link**. Sub-stage 2.4.4 assigns `.5` to the
firewall and `.6` to the edge router, and 3.5.7 gave `.5` to the edge router — the
two documents had the pair reversed relative to Phase 2. The Phase 2 assignment was
retained because the routing tables in 2.5.4 depend on it.

Second, it was in the **wrong address space**. The firewall-to-edge link is a
boundary link and carries public space, not `10.0.254.0/24`. The link is now
`203.0.113.4/30`, and the reasoning is set out in 2.4.4.

Of the two errors, the second was the consequential one: with an RFC 1918 address
at the outside end, translated traffic left the network with a source the provider
could not route, and every reply was discarded upstream.

### Handoff mode — resolved *(D3)*

`Gi1/3` receives Guest traffic on an **untagged access port**. The tagged
alternative was attempted first and rejected: the firewall does not implement
subinterfaces. Both ends are configured consistently — core `Gi1/0/4` as an access
port in VLAN 60, firewall `Gi1/3` holding the gateway address.

### Management termination — resolved

`Management1/1` terminates on core `Gi1/0/10` as an untagged access port in VLAN
99. The original version left this open rather than assigning it without
confirmation; the arrangement built matches what 2.10.2 specifies for every other
infrastructure device.

| Gi0/0/1 | In use | `203.0.113.6/30` | ASA `Gi1/1` outside |
| Gi0/0/2 | Unused / shutdown | — | — |

Both interfaces carry public address space, because both are boundary links
(2.4.4). `Gi0/0/0` was previously recorded as "provider-assigned" and is now
stated explicitly; `Gi0/0/1` was previously `10.0.254.5/30` and is corrected for
the two reasons given in 3.5.6.

### Roles carried by this device

This router carries more than the two interfaces suggest, and the concentration is
worth recording at port level because it is not visible from the interface table:

| Role | Where it lives |
|------|----------------|
| Internet path | `Gi0/0/0` outbound, `Gi0/0/1` inbound |
| PAT for all internal traffic *(D13)* | `ip nat outside` on `Gi0/0/0`, `ip nat inside` on `Gi0/0/1` |
| Remote-access VPN termination *(D11)* | Crypto map on `Gi0/0/0` |
| Network time reference *(D19)* | `ntp master 3` |

Failure testing confirmed the consequence: losing this device removes Internet
access, remote access and time synchronisation estate-wide. The SPOF severity
ranking was revised upward for the edge router as a result.

## 3.5.8 Unused Ports and Native VLAN

| Device | Unused ports | Treatment |
|--------|--------------|-----------|
| Core 3650 | `Gi1/0/11–24` and `Gi1/1/1–4` — eighteen in total | VLAN 999 and shut down |
| Access SW1 | `Gi0/2` | VLAN 999 and shut down |
| Access SW2 | `Gi0/2` | VLAN 999 and shut down |
| ASA 5506 | `Gi1/4–8` | Shut down, `no nameif`, `no ip address` |
| Edge 4331 | `Gi0/0/2` | Administratively shut down |

Two ports are **reserved** rather than unused, and the distinction is recorded in
their descriptions:

| Port | Reserved for | State |
|------|--------------|-------|
| Core `Gi1/0/8` | Future File Server (`10.0.50.40`) | VLAN 50, shut down |
| SW2 `Fa0/23` | Department growth, unassigned | VLAN 999, shut down |

A reserved port is held in the VLAN it will use where that is known, and in 999
where it is not. The File Server's VLAN is known, so `Gi1/0/8` sits in VLAN 50; no
department has been chosen for `Fa0/23`, so it sits in 999. Both are shut down,
which is what makes the reservation safe either way.

### Native VLAN — confirmed, with three exceptions

| Links | Native VLAN |
|-------|------------:|
| Core ↔ Access SW1, Core ↔ Access SW2 | 999 |
| Core `Gi1/0/9` ↔ WLC | **99** |
| SW1 `Fa0/24` ↔ LAP-PT 1 | **99** |
| SW2 `Fa0/24` ↔ LAP-PT 2 | **99** |

The original version of this document declined to assert a native VLAN for the
wireless-facing links and the Guest handoff, pending confirmation. All four are now
settled.

The Guest handoff needs no native VLAN at all: `Gi1/0/4` is an access port, and an
access port carries no native VLAN. The three wireless-facing links required 99 for
the reason recorded in 2.3.7 *(D8)* — the controller and both access points send
management traffic untagged and offer no VLAN identifier field. The residual risk
is assessed there.

### A naming inconsistency

Core `Gi1/0/11` is shut down in VLAN 999 like its neighbours but carries no
description, where every other unused port is named `UNUSED`. The port's state is
correct; only its label is missing. It is recorded here because 3.5.1 treats port
descriptions as part of the configuration rather than as commentary — a port whose
purpose cannot be read from `show interfaces status` is an exception to that
convention, however minor.

## 3.5.10 Verification Before Configuration — Resolved

| Item | Resolution | How it was established |
|------|------------|------------------------|
| **Core→ASA Guest handoff** | Untagged access port, core `Gi1/0/4` ↔ ASA `Gi1/3` | The tagged alternative was attempted and rejected — the firewall does not implement subinterfaces *(D3)* |
| **WLC connection** | Core `Gi1/0/9`, trunk, native VLAN 99, controller at `10.0.99.40` | Native 999 left the controller unreachable; the wizard's Management VLAN ID field had no effect, confirmed by reverting *(D8)* |
| **LAP connections** | `Fa0/24` on each access switch, trunk, native VLAN 99 | Both LAPs dropped to `DOWN` with VLAN 99 tagged *(D8)*. FlexConnect Local Switching and Local Auth were required before any SSID was broadcast *(D10)* |
| **ASA management** | Core `Gi1/0/10`, access VLAN 99, `management-only` retained | Separate from inside, as instructed; not merged |
| **SW2 `Fa0/23`** | No department assigned; held in VLAN 999, shut down, described as reserved | A deliberate non-decision — see 3.5.5 |
| **2960 physical ports** | Confirmed: 24 FastEthernet + 2 Gigabit. `Gi0/1` carries the sole core uplink; `Gi0/2` parked | `show interfaces status` on both access switches |
| **Port naming** | Labels applied throughout; one omission on core `Gi1/0/11` (3.5.8) | `show interfaces status` on the core |

Every instruction this table gave was followed: verify before choosing, apply the
choice consistently at both ends, and never create a core VLAN 60 SVI. The core
holds no VLAN 60 SVI, which 2.5.4 confirms by the absence of a routing entry for
`10.0.60.0/24`.
