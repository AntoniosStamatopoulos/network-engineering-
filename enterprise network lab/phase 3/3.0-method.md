# Phase 3 — Method

How device requirements are derived, and why the phase is structured this way.

> This note explains the **method**. The requirements themselves are in 3.1.1
> through 3.1.6, one file per device type.

---

## 1. What Phase 3 Does

Phase 3 translates **decisions** into **specifications**.

```text
Phase 2:  "inter-VLAN routing happens on the core"
              ↓
Phase 3:  "therefore the core must be a Layer 3 switch"
              ↓
          "which available model is a Layer 3 switch?"
```

Phase 2 decided what the network does. Phase 3 determines what implements it.

---

## 2. The Governing Question

There are two ways to select equipment, and the difference is not stylistic.

**The unreliable approach:** *"I need a switch. Which switch should I get?"* This
leads to general feature lists and a choice that seems reasonable. Its weakness is
that there is no criterion — the selection cannot be shown to be correct because
nothing defines what correct would mean.

**The approach used here:** *"What have I already decided this switch does?"* This
leads back into the project's own documents. Selection then becomes a **check**
rather than a judgement: fourteen requirements, either satisfied or not.

The governing question for every entry in Phase 3 is therefore:

> **Not "what does this device need?" but "what have I already decided this device
> does?"**

The first question is answered by searching outside the project. The second is
answered by reading the project.

---

## 3. The Five Sub-Stages

```text
3.1 Device requirements   ← what each device must be capable of
       ↓
3.2 Technology and media  ← speeds, cabling
       ↓
3.3 Device selection      ← which model satisfies 3.1
       ↓
3.4 Physical topology     ← what connects to what, where
       ↓
3.5 Port mapping          ← which port, specifically
```

The order is binding, because each stage consumes the previous one. Port mapping
cannot be done before the port count is known; a device cannot be selected before
its requirements are stated.

**3.1 is the foundation.** An error there propagates through everything that
follows, and is expensive to correct once equipment has been selected or a
topology drawn.

---

## 4. How a Requirement Is Derived

Four mechanisms, in ascending order of difficulty. Each requirement in 3.1 is
labelled with the one that produced it.

### Reading

A statement exists in a document and is translated into a requirement.

```text
Document:    "Telnet is disabled on every device"
                 ↓
Requirement: SSH server; Telnet disableable
```

Most requirements are of this kind. The work is locating the statement, not
reasoning about it.

### Calculation

Nothing states the figure; it is counted.

```text
Topology:    core ↔ firewall, core ↔ SW1, core ↔ SW2, core ↔ 3 servers
                 ↓
Requirement: at least 6 ports
```

**This is the mechanism most prone to error.** Logical topology diagrams show
*segments*, not cables — several VLANs may reach a device over one physical link,
and a single line on a diagram may represent two devices. Counting from a logical
diagram without accounting for this produces figures that are too low.

Any calculated requirement should be recalculated independently rather than
accepted on first reading.

### Implicit assumption

A document **presupposes** a capability without stating it.

```text
Document:    "rules are written only for the direction that initiates
              a connection"
                 ↓
Question:    what must be true for that to work?
                 ↓
Requirement: stateful inspection
```

These are the hardest to find and the most damaging to miss. Nothing in the
document says "a stateful firewall is required" — but the policy is unworkable
without one, and if the capability is absent the policy **appears to function
while permitting more than intended**.

They are found by asking, of each decision: *what must be true for this to work?*

### Migration trigger

A document states that something will change under defined conditions.

```text
Document:    "when a branch office is added → OSPF"
                 ↓
Requirement: OSPF support (future)
```

**Why a future capability belongs in a present requirement list:** a device
lacking it must be **replaced** when the trigger arrives, rather than
reconfigured. The cost of omitting it from selection is measured in hardware
rather than effort.

Future requirements are marked as such and placed in their own priority band, so
they are visible without competing with requirements needed today.

---

## 5. What the Method Achieves

**Selection becomes defensible.** "I chose this because it seemed suitable" and "I
chose this because it satisfies thirteen of fourteen requirements; the one it does
not meet is C10, and this is the consequence" are different claims. Only the
second can be examined.

**Problems surface before they are expensive.** The worst case is discovering
mid-implementation that a device cannot do something required. The requirement
list moves that discovery to before selection.

**Trade-offs become ordered.** Each file ends with a priority table:

| Band | Meaning |
|------|---------|
| Essential | Without it the design does not function |
| Important | A documented control or service is lost |
| Future | Functions today; costs hardware later |

Without this ordering, every compromise looks equivalent. They are not.

**Gaps become documented rather than hidden.** Where the implementation
environment cannot satisfy a requirement, there is vocabulary to describe it:

| Requirement | Design | Implementation | Consequence |
|-------------|--------|----------------|-------------|

The fourth column is the one that matters. It demonstrates understanding of what
the gap means, rather than merely noting that one exists.

**Traceability closes.** Every device characteristic traces back to a business
requirement:

```text
Requirement §10  →  decision 2.10  →  requirement C10  →  selection 3.3
```

---

## 6. The Test Every Entry Must Pass

> **Can the source be shown?**

If not, the requirement was added from habit and should be removed.

This is why every table in 3.1 carries a **Source** column. It is not decorative —
it is the evidence that the list came from the design rather than from somewhere
else.

---

## 7. The Opposite Error

The reverse failure is a requirement that **should** exist and does not.

It is caught by scanning documents systematically rather than working from memory.
If a Phase 2 decision produced no requirement, either it has no hardware
implication or it was overlooked — and the difference matters.

Two examples from this phase:

- **A10** (second uplink per access switch) appears only in 2.8.4, not in the
  topology diagram. Reading the topology alone would have missed it.
- **W10** (configurable native VLAN on the access point trunk) was absent from the
  first draft of the access point list and found on a second pass.

Both were found by scanning, not by recalling.

---

## 8. Summary

| Principle | Statement |
|-----------|-----------|
| **Governing question** | Not "what does this device need?" but "what have I decided it does?" |
| **Four mechanisms** | Reading, calculation, implicit assumption, migration trigger |
| **Most error-prone** | Calculation — logical diagrams show segments, not cables |
| **Most dangerous to miss** | Implicit assumptions — absence produces silent failure |
| **Why future requirements count** | Their omission is paid in hardware replacement |
| **The test** | Every entry must show its source |
| **The opposite error** | Caught by scanning documents, not by recalling them |
