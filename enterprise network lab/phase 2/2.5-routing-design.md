# 2.5 Routing Design

This sub-stage defines how traffic moves between the subnets established in 2.4,
and how it reaches the Internet. It covers the routing method, the routing tables
of each Layer 3 device, address translation, and the conditions under which the
chosen approach should be revisited.

> **Revised after implementation.** Points marked with a reference such as *(D13)*
> were amended following the build. The amendment record at the end of this
> document lists every change; the deviations themselves are set out in 3.6.

---

## 2.5.1 Routing Requirements

Four distinct routing problems exist in this design:

| #   | Problem                          | Handled by                               |
| --- | -------------------------------- | ---------------------------------------- |
| 1   | Traffic between internal VLANs   | Core switch (inter-VLAN routing)         |
| 2   | Internal traffic to the Internet | Core → Firewall → Edge Router → ISP      |
| 3   | Guest traffic to the Internet    | Core (L2) → Firewall → Edge Router → ISP |
| 4   | Remote VPN traffic to internal   | Edge Router (tunnel) → Firewall → Core   |

The third is separate because of design decision DD-2 (2.1): Guest traffic crosses
the core only at Layer 2 and is routed by the firewall, not by the core.

The fourth is separate because the tunnel terminates on the edge router rather
than the firewall *(D11)*. The path still passes the firewall, which is the
property that matters; 2.9.2 records how that is guaranteed.

## 2.5.2 Routing Method: Static

**Selected: static routing.**

### The selection criterion

The decision between static and dynamic routing rests on one question: **are there
multiple paths to the same destination?**

Dynamic routing protocols exist to solve a specific problem — _which of the
available paths should be used, and what happens when one fails_. Where only one
path exists, that problem does not arise, and a dynamic protocol contributes
complexity without function.

### Applying it to this design

The current topology contains one edge router, one firewall, one core layer, and a
single ISP connection (§11). Consequently:

- There is **exactly one path** from any internal segment to any other.
- There is **exactly one path** from the internal network to the Internet.
- There are **no alternative routes** for a protocol to select between, and none
  for it to fail over to.

A dynamic protocol running on this topology would exchange hello packets,
construct a topology database, and run a shortest-path calculation in order to
arrive at the only routes that exist. It would add configuration complexity, CPU
and bandwidth overhead, and an additional attack surface requiring authentication,
in exchange for no operational benefit.

### What this does not mean

Static routing is chosen here because it fits **this** topology, not because
dynamic routing is inferior. Static routing has a genuine and significant
weakness: **it does not adapt to failure**. If a link goes down, a static route
continues to point at it and traffic is lost until an engineer intervenes.

That weakness is acceptable at present precisely because there is no alternative
path to fail over to. When a link fails in this topology, connectivity is lost
regardless of the routing method — the SPOF analysis documents exactly this, and
the failure testing confirmed it. A dynamic protocol would not preserve
connectivity; it would only reconverge onto the same absent alternatives.

### Migration trigger

The correct point to introduce a dynamic protocol is when the conditions that
justify it appear. Two planned Phase 2 extensions create them:

| Extension                   | Why it changes the calculation                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Branch Office (§5)**      | A second site introduces multiple networks that would otherwise require manual routes at both ends, growing with every new segment      |
| **High availability (§12)** | A second edge router, second firewall and second ISP create genuine alternative paths — and automatic failover becomes the entire point |

**Recommended protocol at that stage: OSPF.** It is an open standard rather than
vendor-specific, converges quickly, selects paths by bandwidth-derived cost, and
scales through areas. A single-area deployment (area 0) would be sufficient at the
size this network would then be.

This is recorded as a design decision with a defined trigger rather than a
permanent choice: the routing method should be revisited when redundancy or a
second site is introduced, not before.

## 2.5.3 Inter-VLAN Routing

**Method: Layer 3 core switch with SVIs.**

Each routed VLAN has a Switched Virtual Interface on the core switch holding its
gateway address, as defined in 2.4.3.

### Alternatives considered

**Router-on-a-stick** — a router with per-VLAN subinterfaces on a single physical
link. Functional, but all inter-VLAN traffic would traverse one link, creating a
bottleneck as internal traffic grows.

**Routing on the firewall** — would force ordinary internal traffic (for example
HR reaching the internal web server) through the firewall, loading it with traffic
that requires no policy inspection and making it a performance bottleneck as well
as a single point of failure for internal communication.

The core switch routes in hardware at line rate and is the standard approach for
campus networks of this shape.

### The SVI table

|    VLAN | Network          | SVI address       | Routed by core     |
| ------: | ---------------- | ----------------- | ------------------ |
|      10 | 10.0.10.0/24     | 10.0.10.1         | Yes                |
|      20 | 10.0.20.0/24     | 10.0.20.1         | Yes                |
|      30 | 10.0.30.0/24     | 10.0.30.1         | Yes                |
|      40 | 10.0.40.0/24     | 10.0.40.1         | Yes                |
|      50 | 10.0.50.0/24     | 10.0.50.1         | Yes                |
|      99 | 10.0.99.0/24     | 10.0.99.1         | Yes                |
|  **60** | **10.0.60.0/24** | **none on core**  | **No — by design** |
| **999** | —                | **none anywhere** | **No — blackhole** |

The two absences have different roles. VLAN 999 is a true routing blackhole. VLAN
60, by contrast, is present on the core at Layer 2 and is forwarded toward the
firewall, but the core has no address or routing table entry for it. The missing
SVI prevents direct core routing; firewall rule 6 remains necessary because the
firewall is the Guest gateway and also has a route toward the internal networks.

### A consequence confirmed by failure testing

This placement decision has an effect on availability that the Phase 1 SPOF
analysis did not anticipate. Because inter-VLAN traffic is routed **and filtered**
on the core and never reaches the firewall, a firewall failure does not interrupt
internal communication. The SPOF analysis had described a firewall outage as
stopping "all policy-controlled transit traffic"; testing showed the internal
network continuing to operate under its full access policy, and the firewall's
severity ranking was revised downward as a result.

The sub-stage is unchanged by this. It is recorded here because the benefit was a
consequence of the decision rather than its motivation: 2.5.3 chose the core for
performance, and availability turned out to follow.

## 2.5.4 Routing Tables

### Core switch

```text
Directly connected:
  10.0.10.0/24     VLAN 10   (HR)
  10.0.20.0/24     VLAN 20   (Finance)
  10.0.30.0/24     VLAN 30   (Sales)
  10.0.40.0/24     VLAN 40   (IT)
  10.0.50.0/24     VLAN 50   (Servers)
  10.0.99.0/24     VLAN 99   (Management)
  10.0.254.0/30    link to firewall

Static:
  0.0.0.0/0    →   10.0.254.2   (firewall)
```

Note what is **absent**: there is no Layer 3 entry for `10.0.60.0/24`. VLAN 60 is
present in the switching table and traverses the core, but the core has no IP
interface in it and cannot route it.

The default route is the mechanism that enforces the single policy enforcement
point established in 2.1: anything the core does not recognise as internal is sent
to the firewall. Internal traffic is routed locally; everything else is compelled
to pass through the control point.

### Firewall

```text
Directly connected:
  10.0.60.0/24     Guest interface
  10.0.254.0/30    link to core
  203.0.113.4/30   link to edge router  (boundary link — see 2.4.4)

Static:
  10.0.0.0/16    →   10.0.254.1    (core)
  10.0.201.0/24  →   203.0.113.6   (edge router — VPN Finance pool)
  10.0.202.0/24  →   203.0.113.6   (edge router — VPN IT pool)
  0.0.0.0/0      →   203.0.113.6   (edge router)
```

A single summarized entry — `10.0.0.0/16` — covers every internal VLAN, rather
than seven separate routes. This is a direct consequence of the hierarchical
addressing chosen in 2.4: because all HQ subnets occupy one contiguous block, they
can be represented by one entry. The same property will allow the Branch Office
(`10.1.0.0/16`) to be added as one further route rather than several.

**The two VPN pool routes** exist because the tunnel terminates on the edge router
*(D11)*. Remote clients hold addresses from `10.0.201.0/24` and `10.0.202.0/24`,
which are inside the summarized block the firewall sends to the core. Without a
more specific route for each pool, replies to remote clients would be sent inward
to the core instead of outward to the edge router. A longer prefix wins, so these
two entries override the `/16` for VPN traffic only.

### Edge router

```text
Directly connected:
  203.0.113.4/30   link to firewall
  203.0.113.0/30   link to ISP

Static:
  10.0.0.0/8   →   203.0.113.5   (firewall)
  0.0.0.0/0    →   203.0.113.1   (ISP)

Local pools (not routes — host entries appear per connected client):
  10.0.201.100 – .199   VPN Finance
  10.0.202.100 – .199   VPN IT
```

The route back toward the internal network points at the firewall, not past it.
Return traffic is therefore subject to the same enforcement point as outbound
traffic, and the edge router has no path that bypasses it.

**This table is what makes the VPN relocation safe.** Since the tunnel now
terminates here *(D11)*, a remote client's traffic reaches this device before any
enforcement point. The single entry `10.0.0.0/8 → 203.0.113.5` is what prevents
that from being a bypass: the edge router holds no route to any internal VLAN
except through the firewall, so every packet from a VPN client toward an internal
destination is sent to the firewall and evaluated against rules 7 and 8. The
property required by 2.9.2 survives the change of termination point, and it
survives because of this route rather than by accident.

## 2.5.5 Traffic Paths

Each path traced end to end, confirming the routing design supports the Phase 1
traffic analysis.

**Internal — HR to the DNS server (§3.1)**

```text
PC 10.0.10.45
  → gateway 10.0.10.1        (core SVI, VLAN 10)
  → core: 10.0.50.0/24 is directly connected
  → DNS server 10.0.50.10
```

Routed entirely within the core. The firewall is not involved, because internal
server access requires no perimeter inspection.

**External — Sales to the Internet (§3.2)**

```text
PC 10.0.30.45
  → gateway 10.0.30.1        (core SVI, VLAN 30)
  → core: no match → default route → firewall
  → firewall: policy check
  → edge router: PAT          (see 2.5.6)
  → ISP → Internet
```

**Guest to the Internet (§3.2)**

```text
Guest device 10.0.60.45
  → Access switch → core       (VLAN 60, Layer 2 transit only)
  → gateway 10.0.60.1        (firewall interface, not the core)
  → firewall: Guest policy
  → edge router: PAT under a separate access list
  → ISP → Internet
```

The core appears only as a Layer 2 transit device. It never makes a routing
decision for VLAN 60.

**Management — IT to a network device (§3.4)**

```text
PC 10.0.40.45
  → gateway 10.0.40.1        (core SVI, VLAN 40)
  → core: 10.0.99.0/24 is directly connected
  → device management address 10.0.99.x
```

The edge router is the exception, reached at `203.0.113.6` through the firewall
rather than within VLAN 99 (2.4.6).

**Remote VPN (§3.6)**

```text
Remote user → Internet → ISP
  → edge router: tunnel termination, address from pool
  → edge router: 10.0.0.0/8 → firewall      (no other route inward exists)
  → firewall: rule 7 or 8 evaluated, then 10.0.0.0/16 → core
  → core → destination VLAN
```

Two devices now appear in this path where the original design had one. Encryption
and address assignment happen on the edge router; **policy is still enforced at
the firewall**, because the edge router has no route that avoids it *(D11)*.

## 2.5.6 Network Address Translation

Internal addressing uses RFC 1918 private space, which is not routable on the
Internet. Translation is therefore required at the boundary.

**Method: PAT (NAT overload)** — many internal addresses share one public address,
distinguished by port number. This is appropriate given a single public address
from the ISP and no requirement for inbound connections (§7 denies
Internet-to-internal by default).

**Location: the edge router** *(D13)*. The original design placed translation on
the firewall; the reason it moved, and what that costs, are set out below.

**Separate translation contexts for corporate and Guest traffic.** Keeping the two
distinct means Guest activity is identifiable in translation logs, and allows
different treatment (rate limiting, separate public addressing) to be introduced
later without redesign. This requirement is preserved: translation is driven by
two access lists, one for the four corporate VLANs and one for Guest.

No static NAT entries are defined, because no internal service is published to the
Internet in the current scope. If that changes — for example if the web server
were made externally reachable — a static translation and a corresponding
permitted inbound rule would be added together, and would need to be reflected in
the firewall policy design (2.7).

### Why translation is not on the firewall *(D12, D13)*

Traffic between VPN clients and internal networks is not Internet-bound and must
not be translated. On any firewall this is expressed as a NAT exemption: a rule
stating that these particular source-destination pairs are excluded from
translation.

That exemption could not be expressed on the implemented firewall. The consequence
was visible rather than theoretical: replies from corporate VLANs toward the VPN
pools were translated, so a remote client received answers from an address it had
never queried and discarded them. With no way to exempt the traffic, the only way
to stop the firewall translating it was to stop the firewall translating at all.

### How separation is preserved

Translation on the edge router is driven by two access lists, each of which
**denies** translation toward the VPN pools before permitting it toward everything
else:

```text
List 150 — corporate
  deny   10.0.10.0/24 → 10.0.201.0/24, 10.0.202.0/24     (and the same for
  deny   10.0.20.0/24 → 10.0.201.0/24, 10.0.202.0/24      VLANs 30 and 40)
  permit 10.0.10.0/24 → any
  …

List 151 — Guest
  deny   10.0.60.0/24 → 10.0.201.0/24, 10.0.202.0/24
  permit 10.0.60.0/24 → any
```

A `deny` in an access list used for NAT does not drop the packet. It means *do not
translate this* — the packet is forwarded with its original addresses. The deny
entries are therefore the exemption that the firewall could not express, and they
sit above the permits because the first match wins.

Two lists rather than one preserve the requirement above: corporate and Guest
translations remain distinguishable, each under its own list.

### What this costs

The original placement was chosen for a specific reason: policy and translation
applied at the same boundary appear together in the same logs, so an investigator
can see in one place both who attempted what and how it was translated. **That
correlation is lost.** Policy is recorded on the firewall and translation on the
edge router, and reconstructing a session now requires reading two devices.

The loss is larger than it first appears, because the firewall in this
implementation produces no logs at all *(D16)*. In a deployment where it did, this
would be a correlation problem; here it means translation records exist and policy
records do not.

Nothing about the policy itself changes. Every rule in 2.7.3 applies as written,
to the same traffic, in the same place.

## 2.5.7 Routing and Security

The design uses two different mechanisms to restrict traffic, and the distinction
matters when defending it.

| Restriction                              | Mechanism                                                                         | Strength                   |
| ---------------------------------------- | --------------------------------------------------------------------------------- | -------------------------- |
| Guest cannot reach internal networks     | Firewall rule 6 denies RFC 1918; no core SVI prevents a direct core-routed bypass | Rule-based + architectural |
| Unused ports lead nowhere                | **No route exists** — VLAN 999 has no SVI                                         | Structural                 |
| HR/Finance/Sales cannot reach each other | ACL on the core                                                                   | Rule-based                 |
| Only IT may reach management (VLAN 99)   | ACL on the core                                                                   | Rule-based                 |
| VPN clients cannot bypass the firewall   | **No route exists** — the edge router's only path inward is `10.0.0.0/8 → 203.0.113.5` | Structural                 |

VLAN 999 is enforced entirely by absence. Guest isolation is deliberately layered:
the firewall deny is the policy control, while the missing core SVI prevents the
core from becoming an alternative Guest router.

The last row was added after implementation *(D11)*. It belongs in this table
because it is the same kind of control as VLAN 999: the restriction holds because
a route does not exist, not because a rule forbids it. When the VPN termination
point moved outside the firewall, this is what kept the enforcement model intact —
and it is worth noting that the protection is structural rather than rule-based,
which makes it stronger than the arrangement it replaced depended on.

The two ACL rows are enforced by rules, because they are **selective** rather than
absolute. VLAN 99 must be reachable from VLAN 40 and from nowhere else, and the
department VLANs must reach the servers while not reaching each other. Selective
access requires a mechanism that can distinguish sources — that is what ACLs do,
and routing cannot express it.

This is a deliberate allocation, not an inconsistency: absolute isolation is
enforced structurally, selective access is enforced by rules. The specific rules
are defined in 2.7.
