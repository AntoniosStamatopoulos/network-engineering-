# 2.6 Security Zone Design

This sub-stage classifies the network by **trust level** rather than by technical
segmentation, and defines what may cross the boundaries between zones. Segments
and VLANs answer *what exists*; zones answer *how much each is trusted, and what
is allowed between them*.

The specific rules that implement these decisions are defined in 2.7.

---

## 2.6.1 Zero Trust Scope Statement

This design applies **Zero Trust principles**. It does not claim a full Zero Trust
architecture, and the distinction is stated deliberately rather than left
ambiguous.

**Applied:**

| Principle | How it appears here |
|-----------|---------------------|
| **Deny by default** | Anything not explicitly permitted in the interaction matrix is denied |
| **Least privilege** | Each zone receives only the access its function requires — e.g. remote Finance reaches Finance resources and required servers, nothing else |
| **No implicit trust between zones** | HR, Finance and Sales are all "internal" and still cannot reach one another |

**Not applied — out of scope for this lab:**

| Element | Why excluded |
|---------|--------------|
| Identity-based access | Rules are based on address and VLAN, not user identity; no identity infrastructure exists |
| Micro-segmentation | Isolation is at zone level, not per workload or host |
| Continuous verification | Access is evaluated at connection time, not re-evaluated during a session |
| Device posture assessment | No mechanism to check patch level or security software before granting access |

Stating this explicitly matters: a design that claims full Zero Trust while
enforcing address-based rules would not survive scrutiny. Applying the principles
where they are achievable is defensible; overstating the architecture is not.

## 2.6.2 Zone Model

| Zone | Trust level | Contents | VLAN |
|------|-------------|----------|-----:|
| **Z1 HR** | Trusted | HR user endpoints | 10 |
| **Z2 FINANCE** | Trusted | Finance user endpoints | 20 |
| **Z3 SALES** | Trusted | Sales user endpoints | 30 |
| **Z4 IT** | Trusted (elevated) | IT user endpoints | 40 |
| **Z5 SERVERS** | Protected | DNS, Web, Monitoring/Syslog | 50 |
| **Z6 GUEST** | **Untrusted** | Visitor devices | 60 |
| **Z7 MGMT** | **Restricted** | Device management interfaces | 99 |
| **Z8 VPN-FINANCE** | Semi-trusted | Remote Finance users (UC6) | — |
| **Z9 VPN-IT** | Semi-trusted | Remote IT users (UC7) | — |
| **Z10 EXTERNAL** | **Untrusted** | The Internet | — |

### Three modelling decisions worth stating

**Why HR, Finance and Sales are three zones rather than one.** All three sit at
the same trust level — they are ordinary corporate users — so a single "internal
users" zone would be the intuitive grouping. It is rejected because §6 requires
them to be isolated *from each other*. A single zone implies free movement within
it, which is precisely what the requirement forbids. Trust level alone does not
determine zone boundaries; an isolation requirement creates a boundary even
between peers.

**Why Z7 (Management) is the most restricted zone, not Z5 (Servers).** Intuition
suggests servers are the most sensitive asset. But compromising a server yields
one server, whereas compromising the management plane yields control of the
infrastructure — including the ability to disable the controls protecting
everything else. Management is therefore classified above servers in
restrictiveness (§10).

**Why remote users are separate zones rather than part of Z2 and Z4.** A remote
Finance user is the same person as an on-site Finance user, but arrives from an
untrusted network and — per §9 — is granted a narrower scope than they would have
on site. Same person, different trust context, therefore a different zone.

## 2.6.3 Zone Interaction Matrix

Read **row → column**: the row is where traffic originates, the column is where it
is destined. A cell answers "may this zone initiate communication with that one?"

| From ↓ / To → | Z1 HR | Z2 FIN | Z3 SAL | Z4 IT | Z5 SRV | Z6 GST | Z7 MGT | Z10 EXT |
|---------------|:-----:|:------:|:------:|:-----:|:------:|:------:|:------:|:-------:|
| **Z1 HR** | — | ✗ | ✗ | ✗ | ✓ | ✗ | ✗ | ✓ |
| **Z2 FINANCE** | ✗ | — | ✗ | ✗ | ✓ | ✗ | ✗ | ✓ |
| **Z3 SALES** | ✗ | ✗ | — | ✗ | ✓ | ✗ | ✗ | ✓ |
| **Z4 IT** | ✓ | ✓ | ✓ | — | ✓ | ✗ | ✓ | ✓ |
| **Z5 SERVERS** | ✗ | ✗ | ✗ | ✗ | — | ✗ | ✗ | ⚠ |
| **Z6 GUEST** | ✗ | ✗ | ✗ | ✗ | ✗ | — | ✗ | ✓ |
| **Z7 MGMT** | ✗ | ✗ | ✗ | ✗ | ✓ | ✗ | — | ✗ |
| **Z8 VPN-FIN** | ✗ | ✓ | ✗ | ✗ | ✓ | ✗ | ✗ | — |
| **Z9 VPN-IT** | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ | ✓ | — |
| **Z10 EXTERNAL** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | — |

`✓` permitted · `✗` denied · `⚠` permitted under stated conditions (see 2.6.4)

### Reading the matrix

**The Z10 row is entirely denied.** Nothing on the Internet may initiate a
connection inward. This is §7's deny-by-default, and it has no exceptions because
no internal service is published externally — there are no Internet-facing servers
in this design and therefore no DMZ.

**The Z6 row is denied except for the Internet.** Guest traffic reaches the
Internet and nothing else (§4).

**The Z7 column has only two permitted entries** — from Z4 (IT) and Z9 (remote
IT). Every other zone is denied. This is §10.

**The Z4 row is almost entirely permitted**, which is a signal worth recording
rather than passing over. A row full of permissions means high privilege, and high
privilege means a large blast radius if that zone is compromised. It is justified
by §6 and §10, which give IT administrative access, but it is accepted with the
risk noted in 2.6.6.

**Asymmetry is visible and intentional.** Z1→Z5 is permitted while Z5→Z1 is
denied: users open connections to servers, but servers have no reason to initiate
connections toward workstations. A compromised server therefore cannot reach back
into user segments. Return traffic for a permitted session is handled by stateful
inspection and does not require a rule in the reverse direction.

**Z7→Z5 is permitted** because infrastructure devices send SNMP and Syslog data to
the monitoring server (§3.5). This is the management plane reporting inward, not
users reaching outward.

---

## 2.6.4 The Conditional Cell: Z5 → Z10

One cell in the matrix is neither a plain permit nor a plain deny, because the
decision is finer-grained than the zone.

**The condition:**

| Server | Outbound Internet access | Purpose |
|--------|--------------------------|---------|
| DS1 — DNS | **Permitted**, restricted | DNS resolution to approved upstream resolvers only, UDP/TCP 53 |
| DS2 — Web | **Denied** | No functional need; patching handled as maintenance |
| DS3 — Monitoring/Syslog | **Denied** | Time synchronisation obtained internally; patching as above |

### Why the DNS server needs it

An internal DNS server continues to resolve its **own** records without any
Internet access — internal name resolution is unaffected. What is lost is the
resolution of **external** names, because the server does not hold those records
and must query an upstream resolver to obtain them.

So the consequence of denying it is not that DNS fails, but that users cannot
resolve external names — the network degrades rather than breaks. That degradation
is still unacceptable given that every user zone is permitted Internet access, so
outbound DNS is granted.

### Why "approved resolvers" rather than "port 53 anywhere"

Permitting `DS1 → any address on port 53` is looser than the requirement needs,
and the risk is concrete rather than theoretical. **DNS tunnelling** allows data to
be encoded inside DNS queries and sent to an attacker-controlled nameserver. If
port 53 is open to any destination, that channel exists.

Restricting the destination to a defined set of upstream resolvers means a
compromised DNS server can only send queries to servers the organisation chose —
not to one the attacker controls. The principle generalises: **constrain the
destination, not only the protocol.**

### Why DS2 and DS3 have no outbound access

Neither has a functional need. Their only requirement was patching, which is
handled as a maintenance procedure rather than by granting standing outbound
access:

```text
IT downloads and verifies updates
        ↓
controlled transfer to the server
        ↓
update applied
```

**The trade-off, stated honestly.** This removes an outbound path but introduces
an operational risk: manual patching depends on a process being followed. An
unpatched server is a greater exposure than a server with narrowly controlled
outbound access. The approach is therefore accepted **on condition** that the
maintenance procedure is documented and performed on a defined schedule.

At production scale this would not be the chosen approach — an internal update
repository or proxy would serve many servers without giving each one Internet
access. For three servers in a lab, manual handling is proportionate and keeps the
security policy legible.

## 2.6.5 Time Synchronisation

Time synchronisation is treated as a design decision because it would otherwise
create several outbound flows.

**Rejected:** each device querying an external time source independently.

```text
Switch   ─────→ external NTP
Server   ─────→ external NTP
Firewall ─────→ external NTP
Router   ─────→ external NTP
```

**Selected:** a single external dependency at the edge, with internal devices
synchronising from it.

```text
              external NTP
                   ↓
             Edge Router
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Core     Switches    Servers
```

**Why.** It reduces four outbound flows to one, and it gives every device a
**common** time source. The second point matters for Syslog: log correlation
across devices is only meaningful if their timestamps agree. Devices synchronised
to a single source agree with each other even if that source drifts, whereas
devices synchronised independently may not.

**Noted for implementation.** Whether the edge router is the best internal time
source, or whether a dedicated internal NTP service is preferable, is an
implementation question. For a network of this size the router is adequate and
keeps the design simple; the decision should be revisited if the network grows or
if time accuracy becomes a compliance requirement.

## 2.6.6 Boundary Enforcement

Each boundary is enforced by one of two mechanisms, and the allocation is
deliberate.

| Boundary | Mechanism | Enforced at |
|----------|-----------|-------------|
| Z6 Guest → all internal zones | Rule-based deny, reinforced by no core SVI | Firewall + core architecture |
| VLAN 999 → anywhere | **Structural** — no SVI anywhere | — |
| Z1 ↔ Z2 ↔ Z3 | Rule-based (ACL) | Core |
| Any zone → Z7 MGMT | Rule-based (ACL) | Core |
| Internal ↔ Z10 External | Rule-based | Firewall |
| Z8 / Z9 VPN scope | Rule-based | Firewall |
| Z5 → Z10 conditional | Rule-based | Firewall |

**Layered enforcement for Guest.** VLAN 60 traverses the core at Layer 2 and uses
the firewall as its gateway. Firewall rule 6 is therefore the primary control
that denies Guest traffic toward RFC 1918 space. The core has no VLAN 60 SVI, so
it cannot provide an alternative routed path under the intended configuration.
An accidental SVI remains a documented configuration risk and is checked during
review.

**Rule-based where access is selective.** VLAN 99 must be reachable from VLAN 40
and from nowhere else; the department zones must reach the servers while not
reaching each other. Selective access requires a mechanism that can distinguish
sources, which is what access control lists do and what structure cannot express.

### Accepted risks

**Z4 (IT) holds broad privilege.** The IT zone can reach every internal zone
including management. This follows from §6 and §10, but it means a compromised IT
workstation inherits wide access. Mitigations available within the current scope:
restricting management access to specific IT hosts rather than the whole VLAN, and
logging all access into Z7. Recorded here as a known and accepted characteristic
of the design.

**Z7 management is rule-based.** The management VLAN is routed by the core, so a
path exists and is closed by ACL. Guest is also denied by policy, but at a
different enforcement point: the firewall, reinforced by the absence of a Guest
SVI on the core. For management, selective IT access makes a rule unavoidable.
Out-of-band management would provide stronger structural separation and is noted
as a future improvement.

---

## 2.6.7 Exception Handling

Two situations were identified where a permitted-by-default path might appear
necessary, and both are handled as procedure rather than by relaxing the matrix.

**IT troubleshooting the Guest network.** Z4 → Z6 remains denied. Diagnosing the
Guest network does not require entering it: IT manages the devices that serve it —
firewall interface, access points, switches — through Z7, which is already
permitted. The Guest network is administered *from the infrastructure*, not from
inside the zone.

**Security incident response.** If an incident requires access that the matrix
denies, the correct response is a documented, time-limited exception applied and
then removed — not a standing permission held in case it is needed. Standing
permissions are available to an attacker at all times; temporary ones are not.

# 2.7 Firewall Policy Design

Sub-stage 2.6 established **which** zones may communicate. This sub-stage defines
**how** — the specific rules, with protocols and ports, that implement each
permitted interaction from the zone interaction matrix.

Every rule below traces back to a cell in that matrix. Rules without a documented
origin are how policies decay; each entry here is accountable to a decision
already made.

---

## 2.7.1 Enforcement Placement

Not all rules are enforced in the same place. The rule is enforced **where the
traffic passes**.

| Traffic | Enforced by | Location |
|---------|-------------|----------|
| Internal, between VLANs | Access control lists | Core switch |
| To and from the Internet | Firewall policy | Firewall |
| Guest | Firewall policy | Firewall |
| Remote VPN | Firewall policy | Firewall |
| Guest → internal | Firewall rule 6 | Firewall |
| Unused ports | **No rule required** | Structural (VLAN 999 has no SVI) |

**Why internal traffic is not policed at the firewall.** When a user reaches an
internal server, the path is `user → core → server`. The firewall is not on that
path and cannot inspect traffic it never sees. Forcing internal traffic through
the firewall would also load it with traffic requiring no perimeter inspection,
creating both a bottleneck and a single point of failure for internal
communication.

---

## 2.7.2 Core Access Control List

Rules are evaluated top to bottom, first match wins. Exceptions therefore appear
**above** the broader rules they modify.

| # | Source | Destination | Service | Action | Log |
|--:|--------|-------------|---------|--------|:---:|
| 1 | VLAN 40 (IT) | VLAN 99 (MGMT) | SSH 22, SNMP 161 | permit | ✓ |
| 2 | any | VLAN 99 (MGMT) | any | **deny** | ✓ |
| 3 | VLAN 10, 20, 30, 40 | 10.0.50.10 (DNS) | UDP/TCP 53 | permit | — |
| 4 | VLAN 10, 20, 30, 40 | 10.0.50.20 (Web) | TCP 80, 443 | permit | — |
| 5 | VLAN 40 (IT) | VLAN 50 | SSH 22 | permit | ✓ |
| 6 | Infrastructure devices | 10.0.50.30 (Monitoring) | SNMP 162, Syslog UDP 514 | permit | — |
| 7 | VLAN 40 (IT) | VLAN 10, 20, 30 | SSH 22, ICMP | permit | ✓ |
| 8 | VLAN 10, 20, 30 | VLAN 10, 20, 30 | any | **deny** | ✓ |
| 9 | VLAN 50 | VLAN 10, 20, 30, 40 | any | **deny** | ✓ |
| 10 | any | any | any | **deny** | ✓ |

### Rule commentary

**Rules 1–2 — management access.** Rule 1 permits IT to reach the management
plane using SSH for device administration and SNMP for monitoring. Rule 2 denies
every other source.

The order is essential. IT is also part of "any" in rule 2; if rule 2 came first,
IT traffic would match it and be dropped, and rule 1 would never execute. The
exception must precede the barrier. Both are logged, because access to the
management plane is the most sensitive event in the network and attempts from
other zones are inherently suspicious.

**Rules 3–4 — users reaching servers.** All four department VLANs reach the two
services they need. The destinations are **specific hosts** rather than the whole
of VLAN 50: writing `VLAN 50` would also grant users access to the monitoring
server, which they have no reason to reach. Neither rule is logged — this is
routine, high-volume traffic whose logs would obscure meaningful events.

**Rule 5 — IT administering servers.** Distinct from rules 3–4 in kind, not just
in source: those permit *use* of a service, this permits *administration* of the
host. Logged for that reason.

**Rule 6 — devices reporting to monitoring.** Infrastructure devices send SNMP
traps and Syslog messages inward to the monitoring server (§3.5). Note the
direction: devices report to the server; the server does not poll outward under
this rule.

**Rule 7 — IT troubleshooting user segments.** SSH for administrative access and
ICMP for the basic availability checks required by §10.

**Rule 8 — department isolation.** HR, Finance and Sales cannot reach one another
(§6). Logged: an attempt from HR toward Finance is either a misconfiguration or
something worse, and either is worth knowing about.

**Rule 9 — servers cannot initiate toward users.** A server has no legitimate
reason to open a connection to a workstation; if it does, it has likely been
compromised and is attempting to spread. Responses to user-initiated sessions are
unaffected — those are handled by connection state, not by a rule in this
direction.

**Rule 10 — explicit default deny.** Anything unmatched is dropped. The behaviour
is automatic even without this line, but the implicit rule does not log. Writing it
explicitly means dropped traffic is visible.

## 2.7.3 Firewall Policy

| # | Source | Destination | Service | Action | Log |
|--:|--------|-------------|---------|--------|:---:|
| 1 | 10.0.50.10 (DNS) | Approved upstream resolvers | UDP/TCP 53 | permit | ✓ |
| 2 | VLAN 50 (Servers) | any | any | **deny** | ✓ |
| 3 | Edge router | Approved external NTP | UDP 123 | permit | — |
| 4 | VLAN 10, 20, 30, 40 | Internet | TCP 80, 443; UDP/TCP 53 | permit | — |
| 5 | VLAN 60 (Guest) | Internet | TCP 80, 443; UDP/TCP 53 | permit | — |
| 6 | VLAN 60 (Guest) | RFC 1918 ranges | any | **deny** | ✓ |
| 7 | VPN-FINANCE pool | VLAN 20; 10.0.50.10, .20 | Application, DNS, HTTPS | permit | ✓ |
| 8 | VPN-IT pool | VLAN 10–50, 99 | SSH, SNMP, application | permit | ✓ |
| 9 | Internet | Any internal | any | **deny** | ✓ |
| 10 | any | any | any | **deny** | ✓ |

### Rule commentary

**Rules 1–2 — the server outbound decision.** These two rules implement 2.6.4 in
full, and their order carries the whole decision.

Rule 1 permits the DNS server outbound, and constrains it three ways at once: one
source host, one protocol, and a defined set of destinations. The destination
constraint is the significant one. Permitting port 53 to any address would leave a
viable **DNS tunnelling** channel — data encoded inside DNS queries and sent to a
nameserver the attacker controls. Restricting the destination to approved
resolvers means a compromised DNS server can only query servers the organisation
chose.

Rule 2 then denies all server outbound traffic. Because rule 1 sits above it, the
DNS server's approved queries have already been permitted and never reach rule 2;
everything else from VLAN 50 — including any other traffic from the DNS server
itself — is dropped here.

The Web and Monitoring servers have no permit rule at all. They fall through to
rule 2 and receive no outbound access, as decided in 2.6.4. This is the intended
result and the reason no rule mentions them: **absence of a permit is the
mechanism**, not an omission.

Reversing these two rules would silently break external name resolution. The DNS
server would match rule 2 first and be denied, and rule 1 would never execute.

**Rule 3 — time synchronisation.** A single device holds the external time
dependency (2.6.5). Every other device synchronises from the edge router
internally, so no other outbound NTP rule exists. This is the design decision
expressed as a rule: one outbound flow instead of four, and a common time source
so Syslog timestamps correlate across devices.

**Rules 4–5 — corporate and Guest Internet access.** The permitted services are
identical, but the rules are kept separate deliberately. Separation makes
corporate and Guest traffic distinguishable in logs, and it provides a place to
apply differentiated treatment — rate limiting, separate translation, restricted
hours — without restructuring the policy.

**Rule 6 — Guest denied toward private address space.** This is a **required
policy rule**. The firewall is the configured gateway for VLAN 60 and also has a
route toward the internal networks through the core, so without this deny it
could route Guest traffic inward. The absence of a VLAN 60 SVI on the core is the
second layer: it prevents a direct core-routed path from existing under the
intended configuration.

If an SVI were added to the core accidentally while clients continued to use the
firewall gateway, rule 6 would still block their traffic. A client deliberately
using the unintended SVI could bypass the firewall, which is why SVI and trunk
configuration review remains necessary. The destination is expressed as the RFC
1918 ranges rather than specific subnets, so it remains effective even if
internal addressing changes.

**Rules 7–8 — the two VPN scopes.** These implement the asymmetry required by §9.
Remote Finance reaches its own VLAN and two named servers, and nothing else.
Remote IT reaches the internal VLANs and the management plane, reflecting an
administrative role. Both are logged in full: remote access is the highest-value
target in the design, and a record of who connected and what they reached is the
minimum needed to investigate an incident.

**Rule 9 — inbound denied.** No connection may be initiated from the Internet
toward any internal zone (§7). There are no exceptions because no internal service
is published externally; the design contains no Internet-facing servers and
therefore no DMZ. Should a service be published later, this rule would require a
specific exception above it, together with a static translation.

**Rule 10 — explicit default deny.** As in the core ACL, written out for logging.

---

## 2.7.4 What Requires No Rule

**Return traffic.** The firewall performs stateful inspection: when a permitted
connection is established, the response is recognised as belonging to a known
session and allowed automatically. Rules are therefore written **only for the
direction that initiates** a connection.

This is what makes the asymmetry in the zone matrix implementable. A permitted
`users → servers` with a denied `servers → users` does not prevent replies; it
prevents servers from **opening** connections toward users. Writing rules in both
directions would grant exactly the initiation right the design intends to withhold.

**Structurally isolated traffic.** Traffic from VLAN 999 requires no rule because
that VLAN has no SVI or gateway anywhere. Guest traffic is different: it has a
gateway on the firewall and therefore requires rule 6. The missing core SVI is an
additional architectural safeguard, not a substitute for the firewall rule.

---

## 2.7.5 Applied Control Techniques

The policy applies two of the four standard firewall control techniques, and the
two it does not apply are absent for a stated reason.

| Technique | Applied | How, or why not |
|-----------|:-------:|-----------------|
| **Service control** | ✓ | Every rule specifies protocol and port; no rule permits unrestricted services |
| **Direction control** | ✓ | Servers may receive but not initiate (core rule 9); DS2 and DS3 have no outbound path (firewall rule 2) |
| **User control** | ✗ | Requires identity infrastructure and authentication integration; out of scope per 2.6.1 |
| **Behaviour control** | ✗ | Requires application-aware inspection; out of scope per 2.6.1 |

Service and direction control are achievable with address- and port-based rules.
User and behaviour control require capabilities this design does not have, which is
consistent with the Zero Trust scope statement rather than an oversight.

---

## 2.7.6 Logging Policy

| Category | Logged | Reason |
|----------|:------:|--------|
| All deny rules | ✓ | Dropped traffic is the primary signal of both attacks and misconfiguration |
| Management plane access | ✓ | Highest-privilege activity in the network |
| Remote VPN sessions | ✓ | External origin; required for incident investigation |
| Server administration | ✓ | Privileged access to protected hosts |
| Routine user traffic | ✗ | High volume, low value; would obscure meaningful entries |

The balance is deliberate. Logging everything buries significant events in noise;
logging too little leaves no record when one is needed. The criterion applied here
is to record **what would be needed after an incident** rather than everything that
occurs.

---

## 2.7.7 Policy Maintenance

Firewall policies decay. A rule is added for a specific need, the need lapses, and
the rule remains because nobody remembers why it exists or is willing to remove
something they do not understand. Over time the policy grants more access than the
organisation believes it does.

Three practices are adopted to prevent this:

**Documented intent.** Every rule in 2.7.2 and 2.7.3 has commentary explaining what
it does and which requirement it serves. A rule whose purpose cannot be stated is a
rule that should be questioned.

**Traceability to the zone matrix.** Each permit rule corresponds to a permitted
cell in 2.6.3. A rule with no corresponding cell has no design basis and should be
removed rather than retained.

**Time-limited exceptions.** Access required for an incident or a specific task is
granted temporarily and withdrawn, never held as a standing permission (2.6.7). A
permanent rule is available to an attacker at all times; a temporary one is not.
