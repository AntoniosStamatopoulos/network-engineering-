# 2.3 VLAN Design

This sub-stage turns the logical segments defined in 2.1 into **VLANs** — the
mechanism that actually implements segmentation. Without VLANs, segments S1–S7
would remain a drawing; VLANs are what make the separation real on the wire.

IP addressing for each VLAN is defined in 2.4.

> **Revised after implementation.** Points marked with a reference such as *(D8)*
> were amended following the build. The amendment record at the end of this
> document lists every change; the deviations themselves are set out in 3.6.

---

## 2.3.1 Why VLANs

A VLAN divides a physical switch into multiple logical networks. Devices in
different VLANs **cannot communicate directly** — traffic must be routed to pass
between them. Three consequences matter here:

**Isolation.** Placing HR and Finance in different VLANs means they cannot see
each other at Layer 2 at all. The separation becomes structural rather than a rule
that has to be maintained.

**Broadcast containment.** Each VLAN is its own broadcast domain, so broadcast
traffic in one segment does not reach the others.

**Location independence.** A user belongs to a VLAN because of who they are, not
where they sit. Logical grouping is decoupled from physical wiring.

---

## 2.3.2 Numbering Principles

**VLAN 1 is not used.** It is the default VLAN on every switch and a well-known
attack target. It is left empty and unused throughout the design.

**Gaps are left between IDs.** Numbering in tens (10, 20, 30…) allows new
departments to be inserted later without renumbering anything — required by §12.

**Numbers indicate role.** IDs outside the user range signal immediately that a
VLAN is not an ordinary department, which helps during troubleshooting and when
reading configurations.

## 2.3.4 The Three Special VLANs

Most VLANs in the plan are ordinary user segments. Three are not, and each exists
for a specific reason.

### VLAN 99 — Management

**What it contains.** Not users. It contains the *management interfaces of
infrastructure devices*: the core switch, both access switches, the firewall's
management interface, the wireless controller, the access points, and the server
management addresses. When an administrator opens an SSH session to a switch, they
are talking to the device itself, not to a user behind it.

The edge router is the one infrastructure device **not** present in VLAN 99. It
sits outside the firewall and is managed at its firewall-facing address; the
reasoning is in 2.4.6 *(D18)*.

**Why it is separate.** The reason is blast radius. If a workstation is
compromised and management interfaces sit on the same plane as ordinary user
traffic, the compromised machine can reach and attack the switches, the router and
the firewall. The attacker moves from "one PC" to "control of the infrastructure".

With a separate management VLAN, the management plane is a different network that
the compromised machine has no route to at all. This principle is called
**management plane separation** and is among the most basic hardening practices in
network design.

**Why the number 99.** Convention, but a useful one: it sits outside the user
range (10–60), so seeing 99 in a configuration or a log immediately signals "this
is not a department". Any number outside the user range would work — 900, 199 —
what matters is that it does not look like another user VLAN.

**Who can reach it.** VLAN 40 (IT) only. VLANs 10, 20, 30 and 60 have no path to
it. This implements §10.

### VLAN 999 — Parking

**The problem it solves.** A switch has 24 or 48 ports; perhaps 30 are in use. By
default, every unused port belongs to VLAN 1 and is active.

That creates a straightforward attack: someone walks into the office — a visitor,
a contractor, anyone — sees a free network socket, plugs in a laptop, receives an
address, and is on the network. No password, no check. This is the classic *rogue
device* scenario and one of the simplest ways to breach a network.

**How parking solves it.** Every unused port is assigned to VLAN 999, which:

- has **no SVI** — no gateway address anywhere, therefore no routing
- connects to nothing — no servers, no Internet, no other VLAN
- is a **blackhole**: a device can link up, but has nowhere to go

A laptop plugged into a free socket lands in an empty network and sees nobody.

**Why "parking".** Ports are parked there while unused. When a port is needed, it
is assigned to its proper VLAN.

**Its second role: native VLAN.** VLAN 999 also serves as the native VLAN on trunk
links — on all of them in the design, and on all but three in the implementation
*(D8, recorded in 2.3.7)*. The native VLAN is the one that travels **untagged**
across a trunk. By default this is VLAN 1, which enables a **VLAN hopping** attack:
an attacker crafts double-tagged frames to jump into another VLAN. Setting the
native VLAN to an unused VLAN removes the destination that attack depends on.

**Is this excessive for a lab?** No. It costs one configuration line and reflects
standard hardening practice.

### VLAN 60 — Guest

**Why it breaks the pattern.** Every other VLAN follows the same path:

```text
VLAN → Access switch → CORE (routing) → destination
```

Guest does not, because of design decision DD-2 in 2.1:

```text
VLAN 60 → Access switch → CORE (Layer 2 only) → FIREWALL → Internet
                          ✗ never routed by the core
```

**What that means in practice.** VLAN 60 **exists** on the access switches — it
must, because that is where the access points broadcasting the Guest SSID connect.
A visitor associates with the Guest SSID and the access point places their traffic
into VLAN 60. The frames then cross the core as Layer 2 traffic and are handed to
the firewall at a dedicated port.

But **the core has no SVI for VLAN 60**.

This is the critical point. An SVI (Switched Virtual Interface) is a VLAN's
gateway address on the core — the thing that makes routing possible. Without one:

- the core has **no address** in VLAN 60
- the core has **no way** to move traffic between VLAN 60 and any other VLAN
- there is no routed path to block, because routing requires an interface in both
  networks and the core has one in only the other

The core forwards Guest frames between two ports in the same broadcast domain,
which is switching, not routing. A Guest client's default gateway is `10.0.60.1`
on the firewall; the core is not a hop on that path at all.

**Why this is stronger than rules.** Compare the two approaches:

*If Guest were routed by the core:* a path to HR, Finance and Sales would exist and
would be closed with an ACL. That works — until someone writes a rule incorrectly,
deletes it, or changes the order of entries. Security then depends on
configuration being correct and staying correct.

*With this design:* there is no routed path, so there is no rule to break. Even if
every ACL were deleted, Guest still reaches nothing internal, because the core
holds no address from which it could forward Guest traffic into another VLAN.

This is the difference between **structural** isolation and **rule-based**
isolation. Structural isolation does not depend on human accuracy.

**The one way it could fail, stated honestly.** The physical path was settled in
3.4.4: VLAN 60 transits the core at Layer 2 rather than reaching the firewall over
a dedicated uplink from each access switch. That decision has a consequence for
this argument. The isolation no longer rests on the core being *unaware* of VLAN
60 — it carries the VLAN — but on the core having *no gateway* in it. If an SVI
for VLAN 60 were ever created on the core, by mistake or by someone unfamiliar
with the design, the isolation would break silently.

Firewall rule 6 (2.7.3) is what guards that case. It was written as defence in
depth against a scenario the original physical design made impossible; under the
arrangement actually built it is no longer redundant but the second line of a real
defence. 3.4.4 records the same condition: *the core must not have a VLAN 60 SVI.*

**The trust model it expresses.** A visitor is not an internal user with
restrictions; a visitor is untrusted, like anyone on the Internet. Sitting inside
the building does not change that. VLAN 60 terminates on the firewall exactly as
an external connection would — the same treatment, because the same trust level.

**How to read it.** Guest traffic travels from the access points, across the
access-to-core trunks, through the core as Layer 2 only, and out of a single port
to the firewall, where its gateway lives. The note "✗ NO SVI for VLAN 60" on the
core is the mechanism that makes this isolation structural: the core carries the
VLAN but holds no address in it, so it cannot forward Guest traffic into any other
VLAN. VLAN 50 is absent from the access trunks because the servers connect to the
core directly.

## 2.3.7 Trunk Configuration Notes

Points that follow from the VLAN plan, as implemented in the physical build:

- **Core ↔ access trunks carry VLANs 10, 20, 30, 40, 60 and 99.** VLAN 60 is
  present because it transits the core at Layer 2 (3.4.4). VLAN 50 is absent
  because the three servers attach directly to the core and the VLAN is therefore
  local to it (3.4.3).
- **The Guest handoff to the firewall is an untagged access port**, not a tagged
  trunk: core `Gi1/0/4` in VLAN 60 to firewall `Gi1/3`. The tagged option was
  specified as an alternative in 3.4.4 and could not be used, because the firewall
  does not implement subinterfaces *(D3)*. Only one VLAN crosses the link, so
  tagging would convey no information.
- **Access-point links are 802.1Q trunks** carrying VLANs 10, 20, 30, 40, 60 and
  99, one per access switch on `Fa0/24` *(D10)*.
- **The native VLAN is 999 on all trunks except three.** The exception is recorded
  below.
- All unused access ports are assigned to VLAN 999 and left in that state until
  explicitly needed.

### Native VLAN exception on wireless-facing links *(D8)*

| Link | Native VLAN | Reason |
|------|------------:|--------|
| Core ↔ wireless controller | **99** | The controller sends its management traffic untagged and offers no VLAN identifier on its management interface. With native 999 it was unreachable |
| Access SW1 ↔ AP-1 | **99** | With VLAN 99 tagged, the access point loses its address and drops to `DOWN` |
| Access SW2 ↔ AP-2 | **99** | As above |
| All other trunks | 999 | As designed |

**Residual risk.** The VLAN-hopping mitigation is absent on these three links. The
risk is low and bounded: each terminates on a controlled infrastructure device
rather than a user-accessible port, and double-tagging requires an attacker
positioned on the native VLAN of a trunk they can inject into. Untagged management
on the native VLAN is also the conventional arrangement for controller
deployments. The exception is recorded here rather than left as a blanket claim
that the implementation does not meet.

# 2.4 IP Addressing Design

This sub-stage assigns an IP subnet to each VLAN defined in 2.3, and establishes
the conventions that govern how addresses are allocated within those subnets.

---

## 2.4.1 Address Space Selection

**Selected: `10.0.0.0/8`**

| Range | Assessment for this network |
|-------|-----------------------------|
| `192.168.0.0/16` | **Rejected** — collides with the home networks of VPN users (§9) |
| `172.16.0.0/12` | Workable, but offers no advantage over 10/8 here |
| `10.0.0.0/8` | **Selected** — room for multiple sites (§5), avoids VPN collision |

Two requirements drove this. **Remote access (§9):** a remote user's home network
is almost certainly `192.168.0.0/24` or `192.168.1.0/24`; if the corporate network
used the same range, the user's machine would have two routes to the same
destination and the VPN connection would fail in ways that are hard to diagnose.
**Branch Office (§5):** a second site needs its own address block, which 10/8
accommodates without contortion.

This selection governs the **internal** network. Addresses at the provider-facing
boundary are not part of it; see 2.4.4.

## 2.4.2 Addressing Structure

```text
    10  .  0  .  30  .  45
    │      │     │      │
    │      │     │      └── host
    │      │     └───────── VLAN ID  (30 = Sales)
    │      └─────────────── site     (0 = HQ, 1 = Branch)
    └────────────────────── private space
```

**The third octet equals the VLAN ID.** Reading `10.0.30.45` identifies the
address immediately: HQ, VLAN 30, Sales — no lookup table required. In log
analysis and troubleshooting this is the difference between seconds and minutes
per event.

| VLAN | Name | Subnet | Gateway | Gateway located on | Usable |
|-----:|------|--------|---------|--------------------|-------:|
| 10 | HR | 10.0.10.0/24 | 10.0.10.1 | Core SVI | 254 |
| 20 | FINANCE | 10.0.20.0/24 | 10.0.20.1 | Core SVI | 254 |
| 30 | SALES | 10.0.30.0/24 | 10.0.30.1 | Core SVI | 254 |

| 50 | SERVERS | 10.0.50.0/24 | 10.0.50.1 | Core SVI | 254 |
| 60 | GUEST | 10.0.60.0/24 | 10.0.60.1 | **Firewall interface** | 254 |
| 99 | MGMT | 10.0.99.0/24 | 10.0.99.1 | Core SVI | 254 |
| 999 | PARKING | — | **none** | — | — |

The last two rows carry the structural security controls established in 2.3.4:
Guest's gateway lives on the firewall rather than the core, and PARKING has no
gateway at all.

**Why /24 for every segment.** The third-octet-equals-VLAN-ID scheme only works
with /24 boundaries; under VLSM the IT segment would become something like
`10.0.10.48/29`, and the number would no longer carry meaning. A /24 also provides
254 usable addresses — roughly ten times current requirements — so segments can
grow substantially without renumbering (§12). The counter-argument is wasted
address space, but in a private range containing 16.7 million addresses, of which
this design uses under two thousand, the waste costs nothing that will ever be
needed.

## 2.4.4 Point-to-Point Links

Variable-length subnetting **is** appropriate here, because the number of
endpoints on a link is known and cannot grow.

Point-to-point links fall into two categories, and the distinction determines
which address space each uses. The original version of this sub-stage did not draw
it, and the omission caused a failure during implementation *(D2)*.

### Internal links

Both endpoints sit inside the perimeter. These use private space from
`10.0.254.0/24`, reserved for the purpose.

| Link | Subnet | Endpoints |
|------|--------|-----------|
| Core ↔ Firewall | `10.0.254.0/30` | `.1` core · `.2` firewall |

The remainder of `10.0.254.0/24` stays reserved for the additional internal links
introduced by the high-availability extension (§12).

### Boundary links

One or both endpoints face the provider. These carry **public** address space,
because the address at the outer end of such a link is what the Internet sees.

| Link | Subnet | Endpoints |
|------|--------|-----------|
| Firewall ↔ Edge Router | `203.0.113.4/30` | `.5` firewall (outside) · `.6` edge router |
| Edge Router ↔ ISP | `203.0.113.0/30` | `.1` ISP · `.2` edge router |

`203.0.113.0/24` is the RFC 5737 documentation range, used throughout this project
wherever a public address is required. It stands in for addresses a provider would
assign, and is reserved precisely so that documentation and lab work never
reference real public space.

### Why the firewall-to-edge link is not internal

The original table placed this link in `10.0.254.4/30`, treating it as one more
internal point-to-point link. It is not. It is the boundary at which the internal
network becomes externally visible, and 2.5.6 already assumed as much by stating
that translation uses a public address from the ISP.

The two statements were incompatible, and the consequence was concrete. Translated
traffic left the network carrying an RFC 1918 source address, which the provider
cannot route; every reply was discarded upstream *(D2)*. The link is a boundary
link and is addressed as one.

The distinction generalises beyond this network: **a link is internal or external
according to what is on the far side of it, not according to which rack it sits
in.** A link that terminates on a provider-facing device is part of the boundary
even when both devices belong to the organisation.

## 2.4.5 Allocation Within a Subnet

```text
        Anatomy of a /24 subnet   (example: 10.0.10.0/24)

   .0                                                        .255
   │                                                           │
   ├──┬───┬────┬──────────────────┬─────────────────┬──────────┤
   │.0│.1 │.2-9│    .10 – .99     │   .100 – .199   │ .200-.254│
   ├──┼───┼────┼──────────────────┼─────────────────┼──────────┤
   │NET│GW │ HA │     STATIC      │      DHCP       │ RESERVED │
   └──┴───┴────┴──────────────────┴─────────────────┴──────────┘
      ▲    ▲          ▲                   ▲              ▲
      │    │          │                   │              │
   always  │      servers,           workstations,     future
     .1    │      printers              laptops         use
           │
      headroom for
   second gateway (HA)

   ◄──────── STATIC ZONE ────────►◄─── DYNAMIC ───►
        (manually assigned)            (DHCP)
```

| Range | Use | Method |
|-------|-----|--------|
| `.1` | Gateway | Static — fixed convention across every VLAN |
| `.2 – .9` | Infrastructure | Static — headroom for a second gateway (HA) |
| `.10 – .99` | Servers, printers | Static or DHCP reservation |
| `.100 – .199` | User endpoints | DHCP |
| `.200 – .254` | Reserved | — |

**The static and dynamic zones must never overlap.** If a server were assigned
`.15` manually while the DHCP pool also began at `.10`, the DHCP server could
issue `.15` to a workstation, producing an address conflict that breaks both
devices. Separating the ranges is a rule, not a stylistic preference.

The `.2 – .9` block is deliberate foresight: when a second core device is added
under the high-availability extension, a second gateway address and a virtual
address will be required, and the space already exists.

**Wireless controller interfaces in the user VLANs** *(D10)*

The controller holds an address in every VLAN it serves, so these belong in this
table even though they are not in VLAN 99:

| Interface | VLAN | Address |
|-----------|-----:|---------|
| `vlan10` | 10 | `10.0.10.2` |
| `vlan20` | 20 | `10.0.20.2` |
| `vlan30` | 30 | `10.0.30.2` |
| `vlan40` | 40 | `10.0.40.2` |
| `vlan60` | 60 | `10.0.60.2` |
| `virtual` | — | `192.0.2.1` |

Each sits at `.2`, the first address of the infrastructure block reserved in
2.4.5. That block exists precisely so that a device added after the addressing
plan was written has somewhere to go without colliding with a gateway, a server
or a DHCP pool. The controller was added after the plan and took the space the
plan had kept for it.

**The `virtual` interface is not a real address.** It is the controller's internal
endpoint for client mobility and web authentication; no packet ever carries it on
the wire. `192.0.2.1` is the RFC 5737 documentation range, which is the correct
choice for an address that must exist and must never be routed.

**Note an overlap.** The ISP router's unused `Gi0/0/2` also carries `192.0.2.254`
in the same /24 (3.5.7). The two never meet — one is internal and unrouted, the
other is on an unconnected interface outside the perimeter — but two devices
holding addresses in one documentation range, for unrelated reasons, is the kind
of coincidence worth recording before someone later mistakes it for a design.

These are static rather than DHCP-assigned because other systems point at them:
every client is configured to reach DNS at `10.0.50.10`, and every infrastructure
device sends its logs to `10.0.50.30`. An address that other systems depend on
must not change.

The access points are the exception. They obtain their addresses by DHCP because
they must acquire one before they can discover and join the controller, and
nothing else in the network refers to them by address.

### The edge router is not in VLAN 99 *(D18)*

The original version of this table assigned `10.0.99.20` to the edge router. That
assignment is withdrawn, and the reason is a requirement rather than a
convenience.

The edge router sits outside the firewall and has no interface in VLAN 99. Giving
it one would mean a physical connection from an Internet-facing device into the
management segment — a path from outside the perimeter into the management plane
that bypasses the enforcement point entirely. Requirement E2 states that no route
may bypass that point.

**The edge router is therefore managed over SSH at `203.0.113.6`**, its
firewall-facing address. Access is restricted by SSH authentication, and the
device is reachable only from the IT VLAN by way of the firewall. Management
traffic to this one device does not traverse the management VLAN, which is a
recorded consequence rather than an oversight: the alternative was a management
path that violated E2.

The Guest scope differs in two ways, both following from its untrusted status:

- **Public DNS resolver rather than the internal server.** The internal DNS server
  sits in VLAN 50, which Guest has no access to (§4). Pointing Guest clients at it
  would either fail or require opening a path that the design deliberately does
  not have.
- **Shorter lease (2 hours).** Visitors leave; a shorter lease returns addresses
  to the pool promptly rather than holding them for departed devices.

### The management scope

The VLAN 99 scope did not appear in the original plan, because the original
wireless design used autonomous access points configured with static addresses
(2.8.5). The implementation uses a controller and two lightweight access points
*(D10)*, which must obtain an address before they can discover it. The scope exists
to serve them.

It is the only DHCP scope in a restricted VLAN, which is worth noting rather than
passing over: an address issued automatically in the management VLAN would be a
concern if any port in that VLAN were user-accessible. None is. VLAN 99 appears
only on infrastructure links and on the three wireless-facing trunks listed in
2.3.7.

## 2.4.8 Scalability

**Additional VLANs.** A new segment takes `10.0.<vlan-id>.0/24`. The scheme
already accommodates the ranges reserved in 2.3.3 without any change to existing
allocations.

**Branch Office (§5).** The second site uses `10.1.x.x` with identical internal
logic:

```text
10.1.10.0/24  →  HR at Branch
10.1.20.0/24  →  Finance at Branch
10.1.30.0/24  →  Sales at Branch
```

The same VLAN-to-third-octet mapping applies, so an engineer familiar with one
site can read the other immediately.

**Route summarization.** Because each site occupies a contiguous block, routing
can advertise one aggregate route per site instead of one per subnet:

```text
HQ      →  10.0.0.0/16     one route
Branch  →  10.1.0.0/16     one route
```

This produces smaller routing tables and faster convergence. It is possible only
because the addressing was designed hierarchically from the start; it cannot be
retrofitted onto an unstructured scheme.
